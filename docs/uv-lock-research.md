## Findings from official documentation

- [Universal resolution](https://docs.astral.sh/uv/concepts/resolution/) records a portable `uv.lock` for the declared Python range and platforms, potentially with different package versions by marker. This does not demonstrate ARM64 compatibility: inspect the actual target-specific graph, wheels, Python ABI and OS on a clean emulator. `required-environments` is not a general wheel-only guarantee: the [project configuration documentation](https://docs.astral.sh/uv/concepts/projects/config/) says it is relevant to packages without source distributions. Explicitly validate every target wheel and reject unreviewed source builds.
- [Locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/) explains that commands including `uv run` can lock and sync automatically. `--locked` checks lock consistency and fails if it needs updating; `--frozen` uses the lock without checking whether project metadata is current. `--no-sync` avoids synchronization but is not by itself a freshness check. A future workflow must test these exact semantics against the approved uv version, keep changes to the reviewed lock visible, and never assume a command is read-only.
- uv supports a [`required-version` setting](https://docs.astral.sh/uv/reference/settings/) to enforce the allowed uv version. Choose an exact release, verify official artifact provenance, integrity, license, support, Windows host and Linux ARM64 builds before requesting G-ARCH approval. Do not rely on auto-downloaded Python; the [CLI](https://docs.astral.sh/uv/reference/cli/) documents `--no-python-downloads`, whose behavior must be tested on the chosen release.
- The [CLI reference](https://docs.astral.sh/uv/reference/cli/) documents `--no-build` but says it may reuse cached wheels from source builds and does not prevent first-party or editable builds; editable build backends may execute arbitrary code. Resolution can also require source metadata builds. Therefore neither a lock nor that flag alone is a sandbox or proof of wheel provenance. Resolve in a controlled environment with approved sources, inspect artifacts and caches, and separately review any build backend or exception.
- For `uv pip` installs, the [CLI](https://docs.astral.sh/uv/reference/cli/) documents `--require-hashes`, which requires pinned requirements and matching hashes and has restrictions on editable, Git and local directory inputs. Build-dependency hashes are a separate setting and do not cover already installed packages or cached built wheels; the bundled `uv_build` backend is an exception. Do not assume the same flag applies to project sync or that a hash proves a package safe. Verify the selected artifact against the approved lock and define independent checks.
- uv can [export CycloneDX 1.5 JSON](https://docs.astral.sh/uv/concepts/projects/export/) from a project lock. The current [CLI reference](https://docs.astral.sh/uv/reference/cli/) also documents `uv audit`, which requires network access and checks published vulnerabilities and adverse statuses. Test target and group coverage, tool version, advisory source, SBOM completeness and failure handling; audit is not a substitute for license, provenance or independent supply-chain checks. Never ignore findings without review.
