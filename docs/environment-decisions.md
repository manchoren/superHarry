## Review order and evidence

1. Define the initial milestone and all direct inputs, intended platforms and candidate services. Refresh the candidate versions, licenses and security findings immediately before review; the existing documents are dated research, not proof of current status.
2. Finish the QEMU/firmware candidate security disposition, snapshot authentication/freshness and `uv` binary license/provenance review, or prepare an alternative where evidence cannot be established. Record any genuinely unresolved finding and its consequence; do not relabel missing evidence as a pass.
3. Prepare a concrete, separately reviewable G-ARCH/G-OPS request for a disposable resolver experiment, including exact versions and verified artifacts, guest image, isolation, permitted network endpoints, commands, failure conditions and cleanup. The experiment produces a **draft** graph only; it does not approve any resulting package.
4. Review exact direct and transitive packages, conditional artifacts, hashes, notices and advisories. Request G-ARCH approval for the reviewed graph and tools before installation or an authoritative lock. Request G-OPS approval for the exact VM/provisioning plan where applicable. Apply public/internal contract, security and other gates separately.
5. After approvals, demonstrate a clean ARM64 emulated installation, checks and startup with synthetic data; track failures and environment differences. Real Pi performance, thermals, HDMI and physical-isolation acceptance remain separate tasks.
