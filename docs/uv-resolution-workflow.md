# Proposed controlled uv resolution workflow

Status: design for T003/T014, 2026-10-30; not approved or executed. The owner selected `uv.lock` as a direction in [ADR 0008](adr/0008-python-lock-direction.md), not the resolver, packages, executable version, network controls or installation. Constitution baseline 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. This procedure concerns repository development, not the separately governed runtime sandbox or package guard.

## Inputs and approval gates

1. Under G-ARCH, review an exact guest OS/image digest, interpreter build and ABI, uv artifact and digest, direct production and development requirements, build backend, index identities, wheel-only policy, licenses and candidate security and SBOM tools. Under G-OPS, review the disposable ARM64 resolver environment, privileges, network enforcement and cleanup. The [uv candidate](uv-toolchain-proposal.md) and [dependency inventory](dependency-approval-inventory.md) are drafts, not approvals. Approve the exact test run and identify who owns its outputs before execution. An initial resolution for review cannot approve the resulting graph; installation requires separate graph approval.
2. Acquire artifacts only after authorized acquisition; compare their hashes to independently obtained official checksums and verify available provenance, logging exact source, verification method and outcome. A matching checksum alone does not establish that a package is safe. Stop on an unknown signer, unavailable provenance required by the approved policy, mismatch or an unresolved blocking advisory.
3. Prepare a fresh disposable ARM64 guest or approved equivalent with an unprivileged resolver account, no production data or credentials, no host mounts or shared credential sockets, and an empty per-run cache and working copy. Configure network access to the approved registry endpoints through an independently enforced OS boundary; test denial of other destinations. Specify DNS, TLS trust, redirects and what metadata/artifact hosts are allowed before the run. No runtime-sandbox permission or policy change follows from this development environment.

## Review run

4. Review the complete project metadata and all effective configuration and environment inputs before resolving: project requirements, groups, Python constraints, workspace members, build system, environment variables, indexes, direct URLs, VCS, local/editable paths, overrides and inherited settings. Initially propose one approved index, no direct/VCS/local/editable dependencies, no metadata overrides and no source builds. A resolver cannot safely be assumed code-free: [uv's resolution documentation](https://docs.astral.sh/uv/concepts/resolution/) states that source metadata can require invoking a build backend. Stop when metadata cannot be obtained from approved sources without unreviewed execution. Do not insert unverified static metadata merely to bypass the stop.
5. With authorization from step 1, execute the reviewed, version-specific `uv lock` command only in the disposable environment, capturing its complete command line, tool and interpreter versions, inputs, timestamps, exit status and sanitized logs. The exact command, allowed flags and failure behavior must be reviewed against the selected executable before the run; this document deliberately does not claim a command is approved or tested. Use an empty cache and independently enforced restrictions, disable automatic Python downloads, and avoid implicit project synchronization. The [uv CLI reference](https://docs.astral.sh/uv/reference/cli/) notes that `--no-build` can reuse cached wheels and that first-party builds can still occur: it is not a security boundary or proof of wheel-only behavior. `--no-index` permits direct URLs and `--offline` is not OS isolation. Config isolation must not accidentally discard required project metadata; review effective configuration rather than assuming `--no-config` retains it.
6. Treat the generated `uv.lock` as an unapproved draft. Preserve it and all inputs as review evidence, not as an authoritative lock or authorization to install. Inspect all branches, groups and markers, not only the development host; record each package's exact version, source, artifact hashes, license, security findings, dependencies and applicable platform. Verify Linux ARM64 wheel tags and the selected interpreter ABI separately; universal resolution is not proof of compatible wheels. Block unresolved dependencies, missing evidence, unsafe sources and unavailable compatible wheels; a source-build exception requires a separate reviewed decision.
7. Validate graph export and scanner/SBOM coverage against the exact candidate release and all conditional branches. [uv workspace metadata](https://docs.astral.sh/uv/reference/internals/metadata/) describes a graph export and cautions that lockfile format is not stable; do not assume it covers every required scan or use its `--sync` option without separate installation approval. Hashes establish artifact identity, not safety. Report packages whose advisories or license coverage could not be checked. Obtain explicit G-ARCH approval for the exact graph, artifact sources and tools before installation or making the lock authoritative.

## Reproduction after graph approval

8. Recreate the approved environment from its image digest and reviewed inputs; use a clean cache, verify approved artifacts, and verify that the lock is consistent with current project metadata. [uv locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/) distinguishes `--locked` freshness validation from `--frozen`, which skips that check. Do not use project commands that implicitly sync until their install behavior and approval are explicit. Confirm all platform branches and groups in scope, compare the graph and digests with the approved inventory, and record any repository or artifact drift. No new package or version is approved by a successful reproduction.
9. With separately approved installation and checks, exercise absent or altered artifacts, lock/metadata drift, missing index, unsupported ARM64 wheels, unavailable mandatory scanner and incomplete SBOM coverage. Each must produce a visible failure and no silent source build or unreviewed graph update. Track exact versions, logs and outcomes with synthetic data. Emulation supplies functional evidence only; real Pi performance, physical isolation and hardware acceptance remain separate.
10. Dispose of temporary environment and caches using approved bounded cleanup; retain only sanitized, reviewable evidence. Assign one lockfile owner and require review plus applicable approvals for changes to dependencies, sources, platform support or build tooling. Recheck advisories and licenses over time; an unchanged lock is not evidence that its dependencies remain safe.
