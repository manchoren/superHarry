## R1 - T182 memory encryption and key custody

| Choice | Accepted contract |
|---|---|
| Backend | SQLCipher Community via the tested sqlcipher3 0.6.5 binding as the implementation baseline; exact deployable artifact must match the target ABI and pass its applicable dependency review. D3 was an isolated experiment, not a production install approval. |
| Key | Dedicated cryptographically random 256-bit memory key. Admin password is used for reauthentication, never as the database key or its recovery substitute. Key version is recorded with encrypted datasets; key material never enters DB rows, prompts, logs, command arguments or environment variables. |
| Custody | Root-owned encrypted credential blob outside application-writable data, proposed path `/etc/credstore.encrypted/superharry-memory-key.cred`; deliver through systemd LoadCredentialEncrypted to the memory-owning application unit's read-only credential directory. Do not introduce a separate memory service solely for this proposal. Exact existing unit and systemd support must be inventoried before provisioning under T221. |
| Host binding | Use the VM's protected systemd host credential key; do not assume TPM availability. Keep that root-owned key outside downloadable backups. Verify boot/unlock behavior on the actual guest. A complete VM/disk compromise can expose both protection and encrypted data; automatic local unlock does not promise protection from privileged access. |
| Availability | Memory access fails closed with a visible error on absent, wrong or corrupt key. Other application features may remain available if they do not require memory; never create an empty replacement database or downgrade to plaintext automatically. |
| Recovery boundary | Initial supported restore is onto the same VM/key custody domain. No downloadable key or password-derived recovery is added. Losing both the required key material and its usable protected custody makes affected encrypted data unrecoverable; a data archive alone does not fix this. Cross-VM key recovery requires a separate protected custody proposal. |
| Rotation | Stage a new key version and verified encrypted replacement; preserve the prior protected key while retained supported recovery backups still require it. Key deletion is a separate explicit admin action with affected-backup disclosure. |

Given an admin requests enable/disable or rotation, when reauthentication and explicit confirmation succeed, then acquire a maintenance/write barrier, create and validate a protected recovery snapshot, and convert into a separate staged database using the verified SQLCipher export contract. Validate schema, record counts, relationships, user_version and logical/cipher integrity as applicable before switching. A readable staging database alone is insufficient (D3 observed an incomplete readable export).

Given a conversion failure, crash or restart, when recovery examines its durable operation journal, then keep or restore the last verified database and key version without resending an unknown operation automatically. Atomic promotion must occur on the same filesystem after durable staging; keep the old state until successful reopen and administrator-visible completion. Never attempt to reverse a partially converted live file in place.

Given encrypted memory, when temporary data or a derived embedding index is created, then keep sensitive temporary content in bounded memory where feasible and store durable sensitive indexes under the same protected memory boundary. Do not silently create a plaintext vector cache or disk spill. Verify WAL/journal/temp behavior and permissions. Disabling encryption intentionally creates plaintext only after the admin sees that risk and confirms. Deleting an old file is not a guarantee of forensic erasure from a VM image or its older backups.

Owner accepted R1's key custody, same-VM recovery limitation and conversion/rotation policy. Approval authorizes implementation within task prerequisites, not generating live keys, modifying service units, activating encryption or converting production data. T183/T225 and deployment approval remain separate. Functional missing/wrong-key, interruption, isolation and recovery tests remain required; performance benchmarks are waived by the later owner instruction.

## R2 - T188 downloadable data backups and staged restore

| Choice | Accepted contract |
|---|---|
| Scope | Versioned data-only ZIP container with a JSON manifest: application release/schema/format identity, stable owner IDs, dataset paths, byte lengths, SHA-256 digests and encryption/key-version identifiers without keys. Digests detect corruption; they do not authenticate an attacker-supplied archive. Treat uploads as untrusted. |
| Included | Allowlisted user memories, conversation/history data and approved persistent files needed to restore supported product data. Export only data for existing authorized principals. A whole application DB dump is not the downloadable format. |
| Excluded | .env, passwords/password verifiers, TOTP seeds/recovery codes, API/OAuth tokens, session/authentication material, all encryption keys/credential blobs, TLS/SSH/private CA keys, browser profiles/cookies, executable code and arbitrary host configuration. Do not package a complete VM image through the app. |
| Encrypted stores | Preserve encrypted memory in encrypted form; the existing matching key must be available before restore. No decrypt-to-plaintext download, key inclusion or portable password recovery is implied. Plaintext-mode data archives contain private user data; disclose that before download. New whole-archive encryption needs a separately specified approved format/dependency. |
| Consistency | Acquire a coordinated write/maintenance barrier across included stores and capture one declared recovery point. Never raw-copy a live SQLite DB or ignore WAL. SQLite online backup is a candidate for a plain data snapshot; SQLCipher snapshot/export semantics must be explicitly verified. Release writers only after snapshots are complete and validated. |
| Retention | Keep the latest verified server-local recovery backup protected and outside ordinary storage cleanup. A new snapshot replaces the previous retained recovery point only after validation succeeds. No scheduled backup/upload or remote storage provider is added. |
| Permissions | Admin-only creation, upload and restore, with recent reauthentication. Download uses the existing authenticated session and object authorization, never a public link or email attachment. Use a one-use, session-bound grant expiring after five minutes as the proposed download contract; no bearer token in a URL. |

Given restore upload, when staging begins, then validate manifest/format/schema compatibility, available key versions, quota/free space, file counts and total decompressed bytes against explicit implementation bounds, paths, duplicates, symlinks, archive bombs and digests before changing live data. Do not execute archived content. Reject unknown owner IDs rather than invent or elevate accounts. Preserve current user roles, passwords, authentication configuration and credentials.

Given validated staging, when the admin reviews datasets, owners, recovery-point time and data-loss scope and explicitly confirms restore, then enter maintenance, capture a verified pre-restore data recovery snapshot and import/switch only the allowed data. Multi-store changes require a durable journal and coherent rollback; do not claim a rename across separate stores is globally atomic.

Given rollback or historical data restore, when current audit, quota/reservation, job and external-action ledgers exist, then preserve their latest state and do not rewind them with historical content. Restored runnable jobs stay disabled pending reconciliation; no message, provider call or consequential action is replayed. Record restore progress/outcome outside the content being rolled back. R2 restores product data, not authentication identities, provider accounting or OS configuration.

Given failure before acceptance, then restore the complete pre-operation allowed-data state, expose the failure and retain evidence; a missing key, insufficient space or failed snapshot prevents live mutation. The owner narrowed T223's completed 2026-11-23 target-VM slice to Conversation/Message, with corruption, SQLite writer fencing, owner isolation, ChatTurn refusal and rollback evidence. Wrong/missing SQLCipher-key recovery remains under T182/T183; StoredFile remains under T233; the admin download/restore flow remains under T188. These excluded cases are not claimed as passed by T223. These are functional/security/recovery tests, not waived benchmarks.

Owner accepted R2's data-only archive, deliberate credential/authentication exclusions, same-VM/key-domain restore and retention/download contract. The initial T223 target-VM acceptance scope is the owner-approved Conversation/Message history slice; exact SQLCipher memory recovery and downloadable admin integration remain with their owning tasks. Implementation bounds and exact export schema belong in the task contract before coding; no unbounded archive handling is authorized. Production backup/restore remains an individually confirmed admin operation; T182/T183/T188/T233 and applicable service changes remain prerequisites.

## R3 - T189 staged application update and rollback

| Choice | Accepted contract |
|---|---|
| Release identity | Admin selects an explicitly approved release from the project's trusted distribution source with immutable version/commit, manifest and artifact digests. Verify a signed release manifest against an operator-provisioned trust key before privileged installation. Exact repository, signing key and distribution mechanism must be concretized with T221; arbitrary URLs or model-generated code are not update sources. |
| Preparation | Stage a separate release directory and isolated dependency environment; dependencies must match reviewed pinned artifacts. No package install script or custom hook supplied by a runtime model. The app cannot modify the installed code or its update broker. |
| Administrative action | Recent admin reauthentication and an explicit preview/confirmation showing versions, migrations, changes, downtime and rollback compatibility. No autonomous or unattended update activation. |
| Privilege boundary | A narrowly scoped, root-owned operator helper may switch only approved release paths and restart the inventoried native unit; it accepts a validated operation/release identifier, never arbitrary commands, paths or unit names. Helper/service provisioning requires separate T221 approval; no new web endpoint receives a generic privileged shell. |
| Data boundary | Maintenance barrier; take and validate a local recovery snapshot of all state the release may mutate. Authentication-store snapshots needed for code/migration rollback are local-only and inaccessible to download or model context; never include their verifiers/secret-bearing content in R2 archives. Retain required live key custody separately. |
| Promotion | Run approved application/configuration/context-hash checks and required tests in staging. Check migration compatibility on isolated snapshots, then apply to live data only in the explicitly confirmed maintenance transaction. Hold all user/job writes until post-start health and integrity checks pass. |
| Rollback | Before releasing writes, a migration/startup/health failure switches to the prior release and its coherent pre-update snapshots, with current action/audit ledgers preserved and no external replay. Prefer snapshot restoration over assuming every Django migration is reversible. Keep the prior release and latest verified recovery snapshot until acceptance. |

Given an update affects authentication, encryption, policy, model routing or protected directives, when staging compares it with the accepted baseline, then require the existing applicable approval and tests. A release signature alone does not authorize constitution or fixed-directive changes. Resolve the source-controlled constitution identity and require the separate administrative confirmation/audit contract; never silently change directives to make the update pass.

Given ambiguous or interrupted update state, when the operator helper recovers, then consult its protected durable journal and the actual active release/schema; do not rerun a possibly completed migration blindly. If rollback would overwrite newly accepted writes or cannot preserve external-action records, stop for an explicit recovery decision with the data-loss scope; never silently declare success or drop newer data.

Given update success, then record old/new release identities, migration plan, health checks, admin confirmation and final active version in the audit trail without secrets. Retain a user-visible failure/recovery status on unsuccessful attempts. T224 must verify failure injection and rollback on a VM copy. Owner benchmark waiver does not waive restart, migration, authentication, isolation or recovery checks.

Owner accepted R3's staged signed-release approach, protected operator helper, maintenance/rollback behavior and local-only update recovery snapshots. This authorizes only the design/implementation scope under this acceptance, not installing dependencies, provisioning a helper, restarting production or executing a release. T188/T225 and concrete T221 deployment authorization remain prerequisites.
