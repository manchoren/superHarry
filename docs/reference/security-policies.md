## 1. File Permissions for Sensitive Data

All files containing cryptographic keys, secrets, credentials, or sensitive configuration must follow these rules:

### 1.1 Permission Standards

| File Type | Permissions | Owner | Group | Location |
|-----------|-------------|-------|-------|----------|
| Encryption keys | `0400` (r--------) | `superharry` | `superharry` | `/var/lib/superharry/.*.key` |
| API credentials (legacy) | `0400` (r--------) | `superharry` | `superharry` | N/A - delegated to omniroute |
| SSH keys | `0400` (r--------) | `superharry` | `superharry` | `/var/lib/superharry/.ssh/` |
| Database files | `0600` (rw-------) | `superharry` | `superharry` | `/var/lib/superharry/*.db` |
| Configuration files | `0640` (rw-r-----) | `superharry` | `superharry` | `/etc/superharry/*.conf` |
| Backup archives | `0400` (r--------) | `superharry` | `superharry` | `/var/lib/superharry/backups/` |

### 1.2 Enforcement

- Set permissions immediately after file creation
- Verify permissions in automated tests
- Log permission changes in audit trail
- Block application startup if critical files have incorrect permissions

### 1.3 Example Implementation

```python
from pathlib import Path
import os

def create_secure_file(path: Path, content: str, perms: int = 0o400):
    """Create file with secure permissions atomically."""
    # Write to temp file first
    temp_path = path.with_suffix('.tmp')
    temp_path.write_text(content)
    
    # Set permissions before moving
    temp_path.chmod(perms)
    
    # Atomic rename
    temp_path.rename(path)
    
    # Verify
    stat = path.stat()
    actual_perms = oct(stat.st_mode)[-3:]
    expected = oct(perms)[-3:]
    if actual_perms != expected:
        raise SecurityError(f"Permission mismatch: expected {expected}, got {actual_perms}")
```

### 1.4 Additional Hardening (Optional)

For production deployments, consider:
- **AppArmor/SELinux:** Mandatory Access Control profiles
- **systemd credentials:** Encrypted credential storage
- **File capabilities:** Reduce privilege escalation surface

## 2. Credential Management - Delegation to omniroute

### 2.1 Scope

omniroute manages **ONLY** external AI model provider credentials:
- API keys for Nous Portal, OpenRouter, Groq, etc.
- OAuth tokens for Gemini
- Model provider authentication

### 2.2 What omniroute Does NOT Manage

- superHarry user accounts and passwords
- Django session tokens
- Database encryption keys
- SSH keys
- TLS certificates
- Email/WhatsApp credentials
- Any application-level secrets

### 2.3 Integration Rules

```
┌─────────────────────────────────────────┐
│ superHarry Application                  │
│ - Django auth (users, sessions)         │
│ - Memory encryption keys (local files)  │
│ - Database credentials (local)          │
└────────────┬────────────────────────────┘
             │
             │ API calls with omniroute API key
             ▼
┌─────────────────────────────────────────┐
│ omniroute Gateway                       │
│ - Nous API key                          │
│ - OpenRouter API key                    │
│ - Groq API key                          │
│ - Gemini OAuth tokens                   │
│ - Ollama endpoint config                │
└─────────────────────────────────────────┘
```

- superHarry stores ONE key: omniroute's API key (generated by omniroute)
- omniroute stores ALL model provider keys
- superHarry NEVER sees individual provider credentials

### 2.4 Credential Lifecycle

1. **Setup:** Admin configures providers in omniroute dashboard
2. **Generation:** omniroute generates an API key for superHarry
3. **Storage:** superHarry stores omniroute key in `.env` (0600 permissions)
4. **Usage:** All inference requests go through omniroute endpoint
5. **Rotation:** Admin rotates keys in omniroute; superHarry continues working
6. **Revocation:** Revoke omniroute API key to cut off all model access

## 3. Sandbox Isolation

### 3.1 Container Rules

Consolidation of sandbox isolation requirements:

| Resource | Limit | Enforcement |
|----------|-------|-------------|
| Wall-clock time | 60 seconds (configurable) | nsjail timeout |
| CPU | 1 core equivalent | cgroup cpu.shares |
| RAM | 512 MB (configurable) | cgroup memory.max |
| Disk | 256 MB (configurable) | tmpfs mount |
| Processes | 64 (configurable) | cgroup pids.max |
| Console output | 10 MB combined | Stream truncation |
| Network | None (air-gapped) | Network namespace disabled |

### 3.2 Filesystem Isolation

```
Sandbox root (read-only):
  /usr, /bin, /lib (minimal system)
  /opt/venv (pre-installed packages)

Writable mounts:
  /workspace (user-specific, quota enforced)
  /tmp (tmpfs, counted against disk limit)

Blocked mounts:
  /proc/kcore, /proc/kmem
  /sys (except read-only /sys/class)
  /dev (except /dev/null, /dev/zero, /dev/urandom)
```

### 3.3 Single Reference

All other specifications must reference this section instead of duplicating rules.

**Constitution reference:** "Run generated task code... in an isolated, resource-limited sandbox" → links here  
**Product requirements reference:** "See security-policies.md § 3 for detailed isolation rules"  
**Implementation reference:** Import limits from config, don't hardcode

## 4. Agent Context Delivery

### 4.1 Runtime Agents vs Development Agents

| Type | Constitution Delivery | Validation | Examples |
|------|----------------------|------------|----------|
| **Runtime agents** | Automatically injected as system prompt | Application validates presence before dispatch | Chat agent, memory agent, tool-calling agent |
| **Development agents** | Required to read via tool before acting | Agent logs constitution hash/version in first message | Kiro IDE agent, deployment agent, migration agent |

### 4.2 Runtime Agent Requirements

- Constitution injected as protected context (not user-modifiable)
- If constitution cannot fit in context window: **BLOCK dispatch** and return error
- Track constitution version/hash per request for audit
- Measure token overhead: `len(constitution) + len(tools) + len(history) + len(user_msg)`
- Never truncate constitution to fit other content

### 4.3 Development Agent Requirements

- Agent MUST call `read_constitution()` in first turn
- Agent logs: `"Using constitution version {hash} from {date}"`
- If constitution changes during session: agent notified and must re-read
- Validation: Check audit log contains constitution read before any write operations

### 4.4 Context Budget Formula

```python
def validate_context_budget(
    constitution_tokens: int,
    tools_schema_tokens: int,
    history_tokens: int,
    user_message_tokens: int,
    model_context_limit: int,
    reserved_output_tokens: int = 1000
) -> bool:
    """Return True if request fits in context."""
    total_input = (
        constitution_tokens +
        tools_schema_tokens +
        history_tokens +
        user_message_tokens
    )
    
    available = model_context_limit - reserved_output_tokens
    
    if total_input > available:
        # Truncate ONLY history, never constitution or current message
        max_history = available - constitution_tokens - tools_schema_tokens - user_message_tokens
        if max_history < 0:
            return False  # Cannot fit even with no history
    
    return True
```

## 5. Model Provider Configuration

### 5.1 Consolidated omniroute Integration

**Single source of truth for omniroute usage.**

All model requests flow through omniroute's OpenAI-compatible endpoint:

```
┌─────────────┐
│ superHarry  │
│ Django app  │
└──────┬──────┘
       │ POST /v1/chat/completions
       │ Header: Authorization: Bearer {omniroute_api_key}
       │ Body: {"model": "nous-ai/solar-mini-4", "messages": [...]}
       ▼
┌──────────────────────────────────────┐
│ omniroute (localhost:20128)          │
│                                      │
│ Routing logic:                       │
│ 1. Check quota for primary provider  │
│ 2. If exhausted, try fallback chain  │
│ 3. Log request (tokens, cost, time)  │
│ 4. Return response                   │
└──────────────────────────────────────┘
       │
       ├─► Nous Portal (primary)
       ├─► OpenRouter (fallback 1)
       ├─► Groq (fallback 2)
       └─► Ollama (local - qwen3.5:4b)
```

### 5.2 Model Routes Table

| Route | Provider | Model | Execution | Roles |
|-------|----------|-------|-----------|-------|
| External default | Nous Portal (via omniroute) | `solar-mini-4:free` | Cloud | `user`, `admin` |
| Memory agent | Nous Portal (via omniroute) | `solar-mini-4:free` (reasoning off) | Cloud | Internal |
| Local fallback | Ollama (via omniroute) | `qwen3.5:4b` | VM-local | All; sole route for `guest` |

### 5.3 omniroute Endpoints

- **Inference:** `http://localhost:20128/v1/chat/completions`
- **Health check:** `http://localhost:20128/health`
- **Usage stats:** `http://localhost:20128/usage`
- **Dashboard:** `http://localhost:20128` (password-protected)

### 5.4 Local Model via omniroute

omniroute proxies Ollama for local model:

1. Ollama runs on VM: `http://localhost:11434`
2. omniroute configured with Ollama provider
3. superHarry requests: `{"model": "ollama/qwen3.5:4b"}`
4. omniroute routes to Ollama endpoint
5. Consistent error handling and logging

**Advantages:**
- Unified interface (no separate Ollama client code)
- Consistent fallback logic
- Centralized usage logs
- Same retry/timeout policies

## 6. Package Installation Guard

### 6.1 Audit Scope

The package guard audits **ONLY directly requested packages**, not transitive dependencies.

**Example:**
```
User requests: install pandas
→ Guard audits: pandas==2.1.0
→ Dependencies (numpy, pytz, etc.): NOT separately audited
→ Decision: Approve pandas or reject pandas
```

**Rationale:**
- Transitive dependency graphs can be hundreds of packages
- Auditing each would make installation impractical
- Trust established packages to vet their dependencies
- Security updates handled by pinning and periodic review

### 6.2 When Dependencies ARE Audited

If the agent explicitly requests a dependency:
```
Agent: "Install numpy==1.24.0 for performance"
→ Guard audits: numpy==1.24.0 independently
```

### 6.3 Evidence Sources

Guard checks (for directly requested package only):

1. **Registry verification:** Package exists in PyPI/npm with matching hash
2. **Signature check:** GPG/PGP signature verification (if available)
3. **CVE database:** NVD, GitHub Security Advisories (past 2 years)
4. **Reputation:** Download count, package age, maintainer history
5. **Name analysis:** Typosquatting detection, namespace confusion
6. **Blocklist:** Known malicious packages (manual curated list)

### 6.4 Scoring Formula

```
Total score = Integrity (0-40) + Reputation (0-30) + Static (0-20) + Provenance (0-10)

Integrity:
  + 20: Hash verified in official registry
  + 15: Valid GPG signature
  + 5:  Publisher identity verified

Reputation:
  - 10: Each CRITICAL CVE in past 2 years
  - 5:  Each HIGH CVE in past 2 years
  - 2:  Each MEDIUM CVE in past 2 years
  + 10: >100k downloads/month
  + 8:  Package age >2 years
  + 5:  Security patch in last 6 months

Static Analysis:
  + 5:  No typosquatting risk
  + 5:  No namespace confusion
  + 10: No malicious code patterns

Provenance:
  + 5:  SLSA level 1+
  + 5:  Signed release artifacts
```

**Threshold:** Configurable, default 80/100

**Blocklist override:** Known malicious packages score 0 regardless of other factors

## 7. Path Configuration System

### 7.1 Dynamic Path Resolution

To avoid hardcoding deployment-specific paths in specifications:

1. Create `.env.paths` from `.env.paths.example`
2. Application reads paths at runtime
3. Specifications reference path variables, not literal paths
4. Agents check for `.env.paths`; if missing, prompt user for configuration

### 7.2 Path Variables

See `.env.paths.example` for complete list. Key variables:

- `VM_ROOT`: Base directory for VM-related files
- `CADDY_CONFIG_DIR`: Caddy configuration (can be dev or prod)
- `MEMORY_DB_PATH`: Encrypted memory database
- `SANDBOX_WORKSPACE_ROOT`: Per-user sandbox workspaces
- `OMNIROUTE_ENDPOINT`: omniroute API endpoint

### 7.3 Agent Behavior

When agent references a path variable:

```python
from pathlib import Path
import os

def get_config_path(var_name: str) -> Path:
    """Get path from environment, prompt if missing."""
    value = os.getenv(var_name)
    
    if not value:
        raise ConfigurationError(
            f"Path variable {var_name} not configured. "
            f"Please copy .env.paths.example to .env.paths and configure."
        )
    
    return Path(value)

# Usage
memory_db = get_config_path("MEMORY_DB_PATH")
```

### 7.4 Documentation Convention

In specifications, use:
- **Correct:** `${MEMORY_DB_PATH}` or "configured memory database path"
- **Incorrect:** `/var/lib/superharry/memory.db` (hardcoded)

Exception: Example commands may show literal paths if clearly marked as examples.
