# Security decisions for owner review

Status: accepted in part by the project owner on 2026-10-30; see [ADR 0004](adr/0004-security-decisions.md). Not implemented. Tasks T007–T008 and T026–T035; gates G-SECURITY and, for OS identities, proxy and secret delivery, G-OPS. Constitution baseline 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. This supplements the [authentication proposal](auth-policy-proposal.md), [bootstrap proposal](bootstrap-recovery-proposal.md), and [approved MFA recovery outcome](adr/0003-lost-mfa-recovery.md). Accepted guest limits, role boundaries and bootstrap token requirements remain binding. Concrete candidates below are approved within the limited scope recorded in ADR 0004; explicitly open details remain pending. Exact libraries, schemas, interfaces and OS mechanisms require separate approval.

## Decision package

| Topic | Candidate and tradeoff |
|---|---|
| Passwords | Require at least 15 Unicode code points for every account, including with optional MFA; allow at least 64, accept Unicode and spaces, and normalize to NFC consistently before checking and hashing. Avoid composition rules and periodic rotation; reject known compromised or common whole-password values. Set an upper input limit after denial-of-service testing; never truncate. A shorter minimum with MFA is more convenient but complicates disabling or recovering MFA. A maintained local blocklist avoids sending candidate passwords externally; fail closed for new or changed passwords if unavailable, while allowing existing login. On 2026-10-31 the owner authorized read-only public research into offline sources and selected [HIBP Pwned Passwords](https://haveibeenpwned.com/Passwords) as candidate for an offline import proposal only. The owner selected HTTPS to the official source, per-range same-source `Content-MD5` validation, a locally computed SHA-256 snapshot manifest, and a 90-day maximum data age; independent publisher signing is not required for this source. HIBP's [Terms of Use](https://haveibeenpwned.com/TermsOfUse) §1.3 permits lawful use of the downloadable hashes and says attribution is not required for Pwned Passwords. The terms also contain restrictions on distributing HIBP data and operating a substantially similar service; applicability requires legal review, and no redistribution is intended. No password corpus was fetched; snapshot/version, import process and final production-source approval remain open. Its linked downloader is separately BSD-3 licensed and requires .NET 10; it is not approved. [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html) supports these password practices; this is guidance, not a claim of federal assurance compliance. |
| Argon2id | Start with memory 19 MiB, iterations 2 and parallelism 1, with a unique random salt per password and encoded parameters. Measure target-device latency and contention before hardware acceptance; bound simultaneous verification and queue work. Rehash on successful login when approved parameters change. A stronger configuration may be preferable if measurements allow. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) lists this and other minimum cost tradeoffs. |
| Authentication throttling | The accepted starting point is a fixed 15-minute delay after five failures for an existing account within 15 minutes; the owner selected that attempts during the delay do not extend it and that all login attempts, including correct-password attempts, are blocked until expiry. A successful login outside an active delay resets that account's failure counter. Do not persist a per-account counter for unknown account names. On 2026-10-31 the owner selected retaining this account-level control without adding origin/IP limits until the trusted-proxy/origin boundary is approved. The owner selected service-wide admission before password verification using a continuously refilled token bucket with bounded burst; after restart, initialize the bucket empty and refill continuously, accepting temporary login unavailability; numeric rate/burst, exact response-body schema, trusted-origin limits, counter persistence/durability and retention remain open; NAT clients can share an origin. Avoid revealing account existence via responses or materially different processing. |
| Sessions | The owner selected a 256-bit random opaque cookie bearer token (32 random bytes encoded as canonical unpadded base64url, exactly 43 ASCII characters) with a server-side verifier: SHA-256 of the 32 decoded token bytes, not the raw bearer token. Reject padding, noncanonical encodings and other decoded lengths; never store, log, cache or return the token, which is distinct from the UUIDv4 `session_id`. Check an account's active-session quota only after valid credentials are verified; at the cap, reject a new session, preserve existing sessions, do not count a failed credential attempt, return the same external response as a failed login without quota-specific details, and emit an individual security-audit event for each rejection. Limit the event to authenticated `principal_id`, fixed event type/outcome, timestamp and `request_id`; exclude IP, Origin, credentials, token and quota/cap details; retain for 90 days subject to legal/operational review. If audit persistence fails, return `UNAVAILABLE`/503 instead of the normal quota response. The numeric cap remains open; event schema and failure/transaction behavior remain gated under T029/G-SECURITY. For pre-authentication sessions, the owner selected a quota key of Origin plus validated client IP using a fixed reverse-proxy topology and HTTP 429 `RATE_LIMITED` without `Retry-After` on exhaustion, with the standard error envelope, empty `parameters` and `request_id`, and no cap/expiry/quota-key details. Enforcement is blocked until Origin, proxy addresses/hops and trusted client-IP derivation are approved, and arbitrary forwarded-IP headers must not be trusted. Numeric cap, canonicalization and state lifecycle remain open. The selected cookie is `__Host-superharry_session` with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` and no `Domain`, over HTTPS. Rotate at login/privilege changes, revoke at logout/reset/disablement/role changes, and do not extend idle time from background polling or SSE. Guest sessions retain their separately accepted 24-hour expiry. Storage/schema, rate-limit counters and deployment remain unapproved. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) recommends server-side idle and absolute expiration tailored to risk. |
| TOTP | Candidate: 30-second steps, six digits, unique cryptographically random secret per account; accept current and one prior/next step, rate-limit attempts and atomically reject already accepted steps. Enroll after recent reauthentication and valid-code confirmation. Never log, expose the seed to the agent or include it in downloadable backups. The owner selected ten 128-bit single-use recovery codes per account, shown once and stored only as verifiers; an application admin may reset an ordinary user's factor after recent reauthentication, confirmation and audit, followed by user re-enrollment. Lost-admin recovery with no usable factor remains the OS-admin path in ADR 0003. [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) defines TOTP and requires rejection of an already accepted OTP. Encryption, key custody and clock/race handling remain open; TOTP is not phishing-resistant. |
| Sensitive actions | Propose reauthentication within five minutes using password and configured TOTP; use a random single-use confirmation bound to actor, session, action, target, exact parameters and current state, expiring after five minutes and invalidated by session revocation or state change. Stronger plan requirements prevail. Per-action reauthentication offers tighter assurance at a usability cost. The operation list and treatment of actions exceeding five minutes need approval. Recheck authorization at execution; a channel cannot grant administrative authority. |
| Password reset | Propose a 256-bit random single-use token with stored verifier and ten-minute expiration. Authenticate the approved recovery path and bind the token to the account; revoke sessions and outstanding tokens atomically after successful reset. Submit tokens in a protected body, never in a URL or log. An admin-assisted web flow versus authorized local OS-admin recovery requires selection; no mail or other channel is implied. Password reset must not silently remove or bypass an enrolled factor. |
| Lost MFA recovery | The owner approved OS-admin recovery with explicit confirmation, audit and mandatory fresh MFA enrollment. Candidate: an elevated local operation revokes existing sessions and factor, sets a durable re-enrollment-required state, and permits only password-verified, short-lived enrollment in the trusted web interface until a new factor is verified. No normal app actions or channel use during that state. OS-admin proof, privilege, enrollment deadline, restart behavior, bound enrollment credential and transactional audit remain open. OS-admin compromise can initiate recovery; fail closed if identity verification or durable audit is unavailable. |
| Proxy and origin | Accept forwarding information only from explicitly configured trusted immediate peers; the edge strips inbound client forwarding headers and creates its own. Derive normalized IPv4/IPv6 origin from a validated chain, rejecting ambiguous input. Direct loopback setup and LAN listeners remain separate. Trusted proxy identity, hop count, headers, Tailscale path, IPv6 handling and NAT policy require G-SECURITY/G-OPS and deployment tests. IP origin is a rate-limit signal, not person identity. No public exposure or port forwarding. |
| Audit and failure | Keep durable records of authentication and privileged attempts and outcomes without secrets or message content. Privileged changes fail closed when required audit persistence is unavailable; record intent before external side effects and reconcile uncertain outcomes instead of blindly retrying. For session lifecycle events (creation/login, explicit logout and revocation), the owner selected actor `principal_id` when authenticated or access-service identity for pre-authentication creation/login, plus canonical lowercase hyphenated UUIDv4 `session_id`, operation, outcome and timestamp; do not include IP address, cookie token or a separate revocation-reason field. Evaluate appending the event and mutating session state in one SQLite transaction when both records share that database; if not, require a separately reviewed durable coordination/recovery design and do not assume cross-database atomicity. If a required lifecycle event cannot be durably committed, abort the transition and return `UNAVAILABLE`/503; failed logout leaves the session unrevoked. For failed `auth.resolve_session`, use five failures associated with an identifiable account in a rolling 15-minute window as a security-signal threshold only, not a new delay rule; emit at most one signal per account per 15-minute interval with `principal_id` and an aggregate count, and repeat no sooner than 15 minutes later if the rolling threshold still holds. Do not infer an account from an unidentifiable cookie or add origin-based signals before GSEC-04 approval. Retention is 90 days for lifecycle events and qualifying failed-resolution signals, separate from diagnostic logs and other audit classes. If a qualifying signal cannot be persisted, the owner selected `UNAVAILABLE`/503 rather than `UNAUTHENTICATED`/401, with no context issuance or idle-activity update. Atomicity, transaction boundaries, retention, protection and partial-failure recovery require approved storage and operations design. Audit availability is independent of optional diagnostics. |
| Audit event protection and operator access | The owner selected evaluating the existing application `admin` role for a narrowly scoped audit read/export capability, authorized by the current admin session without additional password/TOTP step-up for each export; recheck current session and role on every request. | Proposal: use closed typed event schemas, core-only append and class-specific cleanup; deny read/write access to models, skills and ordinary users. The broad role and session-only authorization increase exposure if an admin session is compromised and require explicit G-SECURITY risk review; the gate may assess least-privilege alternatives. Exact event/access fields, filter/export bounds, OS enforcement, retention cleanup and legal holds remain for G-CONTRACT/G-SECURITY/G-OPS review; no endpoint or implementation is approved. |
| Audit export bounds | The owner selected deriving row-count, byte-size and time-range caps from synthetic-volume/performance tests before implementation; no numeric values have been selected. | Define representative test workloads, verify approved caps and pagination/truncation behavior, and obtain gate approval. No broad or unbounded export is authorized. |
| Legal-hold feature scope | The owner selected no general legal-hold feature in the initial scope. | This is not legal advice or a finding that preservation duties do not apply. Obtain applicable legal review before enabling purge; if a hold capability is required, pause that deletion scope and seek a separately approved design. |
| Password-login failures | The owner selected one minimal security-audit event for each failed password verification, retained for 90 days subject to operational/legal review. Attempts during an active account delay are rejected before verification, produce no individual failed-password event and do not change the counter. The owner selected evaluating a same-SQLite direction that commits the counter in one transaction before attempting the audit append in another. | Never include the submitted password, account-name text, verifier or other credential material; preserve generic credential errors. Include `principal_id` only for an existing attempted account; for an unknown account include only access-service identity, with no account correlation value. Count a failed verification for an existing account toward its five-failure delay even if event persistence fails and the request returns `UNAVAILABLE`/503; do not maintain a per-account counter for unknown names. The selected delay is fixed at 15 minutes from the fifth failure and is not extended by further attempts during the delay. The owner scoped the guarantee to audit-append failure while SQLite remains available: after the separate counter transaction commits, an audit-append failure leaves the counter committed and login returns `UNAVAILABLE`/503. A failed counter commit or unavailable shared database also returns `UNAVAILABLE`/503, but the attempt is not guaranteed counted. Exact failure semantics and recovery are unapproved. Counter durability, remaining event fields, retention approval and recovery remain open for T029/G-SECURITY/G-CONTRACT; the owner selected service-wide pre-verification admission using a continuously refilled token bucket with bounded burst; after restart, initialize the bucket empty and refill continuously, accepting temporary login unavailability; numeric rate/burst remain open; HTTP 503/`UNAVAILABLE`, a generic error body and no `Retry-After` are selected; numeric capacity, reset behavior and exact body schema remain open for synthetic-volume/G-SECURITY/G-CONTRACT review. |

| T029 implementation-boundary proposal | For failed `auth.resolve_session`, use a temporary timestamp ledger for attributable accounts, exact rolling 15-minute counts, and atomic signal + last-emitted marker writes; return `UNAVAILABLE`/503 if required signal persistence fails. For successful password login outside delay, propose atomically creating the session, resetting the counter and writing the required lifecycle event when co-located. Use generic equivalent public response shapes for blocked, wrong-password and unknown-account outcomes; measure timing differences and review residual enumeration risk. These are proposals, not gate approvals. The rolling timestamp ledger's size/overload controls remain deferred and block implementation until approved. |

## Required review and validation

The owner may accept or change individual rows; approval of one does not approve all. Record exact scope, reviewer, date and evidence in an ADR. Select and review exact implementations and dependencies separately; agree schema and contracts before changing them. Resolve breach-list provenance and license, encryption key custody and recovery, verifier algorithm, CSRF design, session and clock behavior, and MFA re-enrollment state before implementation. Verify no accepted plan requirement is weakened.

Synthetic negative tests must cover expired or reused tokens, concurrent redemption, OTP replay and clock changes, session fixation and revocation, interrupted enrollment and audit failure, forged forwarding headers, cross-owner access, guest restrictions, rate-limiter restart and shared-origin starvation. Measure password-verification latency and contention on the real Pi before final hardware acceptance. No integration, live credentials, implementation, installation or tests are claimed by this proposal.
