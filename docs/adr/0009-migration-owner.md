# ADR 0009: Python-owned SQL migration direction

Status: Accepted in part, 2026-10-30; SQLite process-access direction selected by owner 2026-10-31 and refined 2026-10-31. Task: T006. Gates: G-ARCH, G-CONTRACT, applicable G-SECURITY.

## Context

The project uses a TypeScript access server and a separate Python core, with SQLite storage. It needs one migration authority and a reviewable migration format before implementation. The constitution baseline is 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`.

## Decision and evidence

The project owner selected, in the coordinating conversation on 2026-10-30, the Python core as the sole migration owner, versioned SQL files as the migration format, and Python as the runner language. This records the owner's direction; it does not select or approve a third-party library or an in-repository runner implementation.

On 2026-10-31, the owner selected the Python core as the sole SQLite writer-service host and initially permitted direct TypeScript read-only reads subject to OS identity/ACL enforcement. After public SQLite WAL documentation showed that read-only WAL connections can still require write permission to `-shm`, the owner refined the direction: TypeScript must not open SQLite directly; all database reads and writes go through the Python core service. Separate OS service identities/ACLs must deny the TypeScript process access to the database and its associated files, not merely deny writes. If that boundary cannot be demonstrated, fail closed. This records a process-access direction only; it does not approve the Python read API, query/repository interfaces, schemas or authorization behavior.

On 2026-11-01, the owner selected resolving an mTLS peer's logical service identity through an explicit local mapping from its configured SHA-256 certificate-DER pin to that identity, stored in a local configuration file protected by OS permissions and readable by the service. CN/SAN values alone are not authoritative for service identity. The owner also selected keeping each service's private key in a separate file owned by and readable only to that service identity, with manual replacement by an OS operator; private keys must not be stored in the repository, logs or application database. The selected issuance direction is a locally provisioned self-signed leaf certificate per service, with ECDSA P-256/SHA-256, and the public certificate/pin distributed through an administrative out-of-band channel. Apply pin/certificate changes by controlled file replacement and service restart, without initial hot reload; validate the pin map and certificates before accepting connections, and prevent readiness/service acceptance if configuration is invalid. Support and behavior must be confirmed on the exact Node/Python/OpenSSL builds for the ARM64 target before approval; the TLS minimum version is deferred until that compatibility test, with no platform default implicitly selected. Pin overlap during manual rotation has an absolute deadline of no more than 48 hours, starting when the first verifier installs the new pin; do not extend it, remove the old pin when complete and reject it at expiry even if incomplete. Immediately revoke a pin if its key/certificate is suspected compromised, even during overlap, and fail closed until a replacement certificate/pin is installed and verified. Out-of-band revocation, evidence and recovery/availability procedure remain open. Exact file owner/ACLs, integrity, atomic replacement/restart procedure, validation/readiness tests, certificate profile, provisioning workflow and technical enforcement remain subject to G-SECURITY/G-CONTRACT/G-ARCH/G-OPS review; this does not approve TLS configuration or implementation.

## Scope and limits

These directions do not decide the physical SQLite/store layout, final Python read API or operation schemas, query/repository interfaces, migration execution process, transaction or cross-store atomicity mechanisms, identifiers and ordering policy, compatibility guarantees, failure/recovery policy, or dependency version/license. A draft named read-operation allowlist and candidate payload shapes are recorded in the [contracts proposal](../contracts-proposal.md#draft-python-read-operation-allowlist-proposal-only); owner-selected payload, session-activity, five-minute authenticated-context lifetime, non-disclosing object-denial, mTLS-only response-authentication and fail-closed read-failure directions there remain proposals, not approved interfaces. The selected context direction permits session/account/role revocation to remain unapplied until a valid context expires; exact object authorization, renewal, response envelope/correlation, operation schemas, transaction/audit effects and public failure semantics remain open. The core deadline, outer HTTP timeout and caller-initiated retry directions are recorded below; their implementation and enforcement require the applicable G-ARCH, G-CONTRACT and G-SECURITY review. The access server and other processes must not access the database directly, write, independently run migrations or bypass approved authorization/repositories.

**Additional owner-selected proposal directions (2026-10-31):** Python's five-second absolute deadline starts when the core receives the complete access-service request. Python starts a local monotonic timer at full request receipt; no deadline field is added to the signed envelope, and HMAC timestamp remains a separate freshness/replay check. The connection/request-transmission phase before core receipt inherits the outer HTTP timeout; no separate internal transport timeout is selected. A Python outage or expired core deadline must fail with `UNAVAILABLE`/503 without stale-cache or direct-SQLite fallback. The core must roll back uncommitted work and not commit effects after expiry. If a transaction commits before expiry but its response is lost, the caller may retry with the same `request_id` and receive the prior result; the access service does not retry automatically. Bind each principal/operation/request ID to a durable fingerprint of the validated payload through context expiry (at most five minutes); a changed payload returns `CONFLICT` even after an earlier operation attempt rolls back, while a matching payload may be retried if no result was committed. Retain the binding and any committed result only through authenticated-context expiry. The owner selected persistence across Python restarts, subject to separately approved schema/migration. Each separately signed attempt uses a fresh durable 256-bit nonce while preserving request ID and payload. Commit nonce consumption durably before checking deduplication; reject nonce reuse. For a new operation, commit its business effect and deduplication result atomically in one transaction. If that transaction rolls back or expires, the nonce remains consumed and the request/payload binding remains, but no operation result/effect is recorded; retry may use the same request ID and payload only with a fresh nonce. Timer enforcement feasibility, nonce-ledger schema/cleanup, request-binding schema/retention and review remain open; the selected nonce-retention window is through signed timestamp + 60 seconds.

**Owner-selected payload-fingerprint and preflight direction (2026-10-31):** use SHA-256 over the operation's validated, typed payload serialized with JSON Canonicalization Scheme (RFC 8785). Apply only semantic normalizations explicitly defined by that operation's schema before serialization; no implicit global trimming, case-folding or Unicode normalization. Ignore irrelevant JSON whitespace/key ordering and exclude request ID, principal/operation key fields, context, timestamp and nonce. In one durable preflight transaction, consume the fresh nonce and create or verify the request binding before checking deduplication. If an existing binding has a different fingerprint, durably consume the valid new nonce, leave the binding unchanged and return `CONFLICT`. Operation schemas, normalization rules, value constraints and Node/Python implementation compatibility remain subject to G-CONTRACT review; no package or storage/wire schema is approved.

**Owner-selected request-HMAC coverage direction (2026-11-01):** logically bind protocol version, sender and recipient/audience identities, `request_id`, operation, context, payload, transport timestamp and nonce in the request MAC; exclude the MAC itself. Derive/validate sender from the authenticated mTLS peer and ensure recipient/audience matches the local service. Full operation schemas, per-operation size limits and remaining validation details remain open for G-SECURITY/G-CONTRACT review. Responses remain authenticated by mTLS only per the separate owner selection; this does not add response HMAC.

**Owner-selected request-HMAC length-prefix direction (2026-11-01):** prefix each encoded field with its 4-byte unsigned big-endian byte length. Apply reviewed per-operation field-size caps before allocation and reject invalid/oversized lengths. Selected field order and encodings are recorded below; per-operation caps, cross-language test vectors and exact parser phases remain open; no implementation or schema is approved.

**Owner-selected request-HMAC structured-value encoding direction (2026-11-01):** serialize validated `context` and `payload` with RFC 8785 JSON Canonicalization Scheme encoded as UTF-8 before applying length prefixes. Apply only schema-defined semantic normalization. Parser constraints and Node/Python known-answer vectors remain open for G-CONTRACT/G-SECURITY review.

**Owner-selected request-HMAC field-order direction (2026-11-01):** encode protocol version, sender identity, recipient/audience identity, `request_id`, operation, context, payload, transport timestamp and nonce in that fixed order; JSON object-key order does not affect the sequence. Permitted scalar grammars remain schema-dependent and open for G-CONTRACT/G-SECURITY review; wire field names are recorded below.

**Owner-selected request-HMAC scalar-encoding direction (2026-11-01):** encode textual scalar fields (`version`, sender/recipient identities, `request_id`, and `operation`) as strict ASCII bytes; reject non-ASCII values and apply no normalization. Exact allowed grammars for these fields remain schema-dependent and open for review. This does not change UTF-8 RFC 8785 encoding for `context`/`payload` or binary timestamp/nonce encoding; cross-language vectors remain open for G-SECURITY/G-CONTRACT review.

**Owner-selected request-HMAC protocol-version direction (2026-11-01):** the initial internal envelope uses the exact ASCII string `v1`; accept only `v1` initially and reject other versions with the generic `UNAUTHENTICATED` response. Incompatible protocol changes require a new version identifier. This is separate from the public HTTP route version. Future multi-version transition policy and schema review remain open.

**Owner-selected request-HMAC service-identity matching direction (2026-11-01):** require `sender` to match exactly the service identity resolved from the authenticated mTLS certificate pin, and `audience` to match exactly the local service identity. Compare strict ASCII values without aliases, case folding or normalization; reject unknown/mismatched values with the selected cause-neutral `UNAUTHENTICATED` response. Configuration semantics and enforcement evidence remain open.

**Owner-selected request-HMAC rotation key-selection direction (2026-11-01):** do not add a wire `key_id`. During the approved old/new overlap, compute and constant-time compare the MAC against every currently permitted pairwise key without early exit; accept if any comparison matches. After the absolute overlap deadline, verify only with the new key and reject the old key. Key storage and rotation-operation evidence remain open.

**Owner-selected request-HMAC sender cutover direction (2026-11-01):** a sender continues signing with the old key until an explicit operator cutover before the absolute overlap deadline, then signs with the new key. A sender not cut over by expiry is rejected because the old key is no longer accepted. Exact operator procedure and recovery remain open.

**Owner-selected request-HMAC overlap-deadline direction (2026-11-01):** start the single absolute overlap deadline of no more than 48 hours when the first verifier installs and validates the new key. **Owner-selected request-HMAC verification-order direction (2026-11-01):** enforce body/field limits and strict parsing first; validate the mTLS peer identity and audience, then trusted-time status/freshness; construct the specified canonical framing and compare the MAC in constant time; durably consume the authenticated nonce before deduplication, semantic schema/authorization handling or operation effects. **Owner-selected request-HMAC timestamp direction (2026-11-01):** encode transport freshness as unsigned 64-bit big-endian Unix-epoch milliseconds and use the OS UTC wall clock as the time source; this is separate from context `issued_at`/`expires_at` and the five-second core deadline. **Owner-selected request-HMAC nonce encoding direction (2026-11-01):** represent the 32-byte random nonce on the wire as canonical unpadded base64url (43 ASCII characters); validate canonical form and exact decoded length, and frame/MAC the 32 decoded bytes. **Owner-selected request-HMAC digest encoding direction (2026-11-01):** represent the HMAC-SHA-256 digest as canonical unpadded base64url (43 ASCII characters), decode canonically to exactly 32 bytes and compare in constant time. **Owner-selected request-HMAC metadata placement direction (2026-11-01):** carry the transport timestamp, nonce and MAC in a sibling `auth` object in the internal envelope, separate from authorization `context`; include timestamp and nonce in the MAC input, excluding only the digest. A Python-owned SQLite sweeper deletes expired rows immediately at startup and at intervals no greater than five minutes while running. Rows may persist physically while Python is shut down until the next startup, but must be rejected as expired and never returned. **Owner-selected logical idempotency-record direction (2026-10-31):** one record keyed by principal/operation/`request_id` holds the payload fingerprint, expiry and optional committed result. Store the complete validated, allowlisted operation-result payload (not its transport envelope), with no secrets or unauthorized data, so retries return the previous result. The durable preflight creates/verifies the binding; the operation transaction records the result atomically with its SQLite effect. If that transaction rolls back, the binding remains and the result remains absent. Result schema/size bounds and physical schema remain unapproved.

**Owner-selected same-key concurrency direction (2026-11-01):** serialize the effect transaction for a principal/operation/`request_id` and recheck the stored idempotency result inside that transaction before executing the effect. Invalid/expired/revoked sessions and disabled accounts do not update activity. Physical transaction and audit details remain open under G-CONTRACT/G-SECURITY.

### Compatibility constraint and owner resolution

SQLite's official [WAL documentation](https://www.sqlite.org/wal.html#readonly) states that a read-only WAL-mode connection needs write permission to the existing `-shm` file, or write access to the containing directory if that file does not exist. SQLite URI [`mode=ro`](https://www.sqlite.org/uri.html) sets connection mode but does not grant or enforce OS permissions. Thus a direct TypeScript connection with OS denial to all SQLite files is not a suitable assumed design for live WAL reads. Public documentation identifies this compatibility constraint but does not prove target behavior for the selected SQLite build and filesystem.

On 2026-10-31, the owner selected the conservative resolution: remove TypeScript direct database access and serve all data requests through the Python core. This avoids granting the access process SQLite-file or WAL shared-memory access. The Python service must enforce requester-scoped authorization and return only typed, validated results over the reviewed authenticated internal contract. The draft candidate allowlist in the [contracts proposal](../contracts-proposal.md#draft-python-read-operation-allowlist-proposal-only) covers session resolution, authorized chat-event reads, and owner-scoped conversation listing/reads; the owner also selected candidate handling for the opaque session token, a typed pre-auth context, successful-access activity updates, normal authenticated-context trust until its maximum five-minute expiry without a per-operation session/account/role lookup, mTLS-only response authentication, a five-second core deadline starting on receipt of the complete request and enforced by a local monotonic timer, fail-closed reads without stale-cache or direct-database fallback when Python is unavailable, and same-`request_id` retry deduplication persisted in SQLite through context expiry across Python restarts. No deadline field is added to the signed request; the HMAC timestamp remains a separate freshness/replay check. The caller initiates retries; the access service does not retry automatically. Each new signed attempt uses a fresh 256-bit nonce with the same request ID/payload, and core consumes the nonce before checking deduplication. The principal/operation/request ID is durably bound to the validated-payload fingerprint through context expiry, so changed payloads conflict even after a rolled-back attempt. For new operations, the business effect and deduplication result commit atomically; if that transaction aborts, the nonce remains consumed and the binding remains, but the request ID may be retried with the same payload only using a fresh nonce. The core must not commit effects after its deadline; if it commits before expiry but the response is lost, a retry returns the prior result. The transport phase before core receipt inherits the outer HTTP timeout. These remain documentary directions only; the schema/migration is not approved.
