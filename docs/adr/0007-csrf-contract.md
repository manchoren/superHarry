# ADR 0007: Browser CSRF and pre-authentication contract

Status: Amended in part, 2026-11-02. Original approval: 2026-10-30; account-session timeouts selected by owner 2026-10-31. Tasks: T005, T007, T024, T026 and T035. Gates: G-CONTRACT and G-SECURITY, limited to the scope below.

## Context and decision

The owner approved the concrete scope described in [the CSRF contract proposal](../csrf-contract-proposal.md) on 2026-10-30, including the ten-minute absolute pre-authentication session and the specified token and multi-tab behavior. This extends the CSRF direction in [ADR 0006](0006-security-directions.md). The reviewed proposal specifies token issuance, validation and transition behavior, structured errors and negative test obligations. The complete constitution, baseline 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`, prevails.

On 2026-10-31, the owner separately selected a 60-minute idle timeout and 24-hour absolute timeout for authenticated admin/user sessions. This records those policy values only; it does not approve session storage, schema, rate limits, deployment or implementation. The ten-minute pre-authentication session lifetime remains unchanged.

On 2026-11-01, the owner selected the distinct `__Host-superharry_preauth` cookie for pre-authentication state, with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain` and HTTPS. Clear it with the same name/path and no `Domain` when transitioning successfully to the separate authenticated `__Host-superharry_session` cookie. This direction does not authorize implementation or deployment.

## Owner amendment: Django-native browser session and CSRF (2026-11-02)

The owner selected `amend_django`: replace the legacy two-cookie and `/v1/session/csrf` design above with Django-native browser sessions and CSRF. Use one host-only `__Host-superharry_session` cookie for an anonymous, privilege-free Django session before sign-in and for a new authenticated session afterward. On successful sign-in, flush the anonymous session rather than elevate or reuse it, establish a fresh authenticated session, and rotate CSRF state. Use Django's supported session and authentication mechanisms, `CsrfViewMiddleware`, and session-backed CSRF state (`CSRF_USE_SESSIONS`); do not add a custom token-issuance endpoint or token format. The cookie is `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, has no `Domain`, and is used over HTTPS.

This amendment supersedes the former endpoint, pre-authentication cookie, token encoding/storage, and two-cookie transition details. It does not change the separately selected 60-minute idle and 24-hour absolute authenticated-session limits, ten-minute pre-authentication lifetime, guest policies, or MFA decisions.

On 2026-11-02, the owner approved `accept_stock`: accept Django's standard database session backend, including its stock session-key generation properties and raw session key in the session table, as an explicit exception to the previously selected 256-bit/hash-only session-token policy. This is a bounded G-SECURITY policy exception for Django session keys; it does not authorize broader database access, weaken file permissions, or change audit/backup secret-handling requirements.

The owner selected `caddy_mdns` on 2026-11-02: preserve the accepted plan for Caddy to terminate HTTPS and serve the app at the configured `<hostname>.local` name using a locally trusted CA certificate. Do not use a dynamic-IP URL or direct Django HTTP as the browser-facing endpoint.

For unsafe requests, accept only one syntactically valid HTTPS `Origin` whose authority matches the validated Django request host (normalizing DNS case, IDNA and the default HTTPS port). In production, the allowed browser hostname is exactly `superharry.local` on HTTPS port 443. Reject missing, `null`, duplicate, malformed, non-HTTPS and nonmatching origins before CSRF/business processing; Django's HTTPS Referer fallback is not accepted. The check never trusts forwarded host or an IP-derived allowlist.

The application recognizes the HTTPS scheme either directly from the server or from an exact `X-Forwarded-Proto: https` header only when the immediate peer address is loopback. Non-loopback peers cannot make Django trust this header. Caddy must connect to a loopback-only Django backend and overwrite the forwarded scheme header; no forwarded host header is trusted. The owner approved this loopback trust boundary on 2026-11-02. The application does not set Django's global `SECURE_PROXY_SSL_HEADER`.

The application implements the strict Origin check fail-closed and has conformance tests for same-origin `https://superharry.local`, malformed/missing origins, and rejection of a forwarded-scheme spoof from a non-loopback peer. The deployment-specific Caddy upstream/listener configuration has not been installed or validated; until it binds Django to loopback and overwrites the forwarded scheme, browser mutations through Caddy remain unavailable. Safe methods remain available. T032/G-OPS deployment, certificate installation and real-device validation are not complete.

The implementation applies the selected timeouts using Django's server-side session expiry: an anonymous session carrying session-backed CSRF state expires ten minutes after creation without extension; an authenticated session expires at the earlier of 60 minutes after its last successful state-changing request and 24 hours after authentication. Read-only requests do not extend the idle deadline. Django's session login view is retained, with a narrow adapter that flushes anonymous state before a successful account or admin sign-in.

The owner selections above authorize the corresponding Django-native cookie/CSRF contract, stock database-session storage exception, selected timeout values, Caddy/`superharry.local` HTTPS browser endpoint direction, and loopback-only forwarded-scheme trust described above. They do not approve deployment changes beyond this app-side trust boundary, unrelated schemas or dependencies, or TOTP/authentication policy changes. Session/audit transaction and response-loss behavior remain open.

## Scope and remaining decisions

The 2026-10-30 approval applied to the concrete legacy CSRF proposal as reviewed; its wire details are superseded by the 2026-11-02 amendments above. The 2026-10-31 authenticated account-session timeout values, stock session-key storage exception and exact same-origin HTTPS policy are selected. Strict-Origin application checks and timeout enforcement are implemented as described above. The remaining deployment blocker is to configure and verify the Caddy-only loopback ingress and overwritten HTTPS scheme header on the selected OS; no deployment change is claimed. Session/audit transaction and response-loss behavior remain open. Other prior open decisions, including guest admission limits and the MFA transition, are unchanged.
