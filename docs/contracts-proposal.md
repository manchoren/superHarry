- **Owner-selected session-token encoding and verifier direction — 2026-11-01:** represent the 256-bit random cookie bearer token as canonical unpadded base64url of exactly 43 ASCII characters, decoding to exactly 32 bytes. Reject padding, noncanonical encodings and other decoded lengths. After canonical decoding, persist only SHA-256 of the 32 token bytes as the server-side verifier; never store the raw token or log/cache/return it, and never substitute it for the UUIDv4 `session_id`. The selected browser cookie is `__Host-superharry_session` with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` and no `Domain`. This does not approve a session schema or implementation.
- **Owner-selected account-session quota behavior — 2026-11-01:** after valid credentials are verified, if the account's active-session quota is reached, reject creation of a new session and preserve existing sessions; do not silently revoke/evict one or count the result as a failed credential attempt. Return the same external response as a failed login without quota-specific details, and emit an individual security-audit event for each rejection. The event direction is limited to authenticated `principal_id`, fixed event type/outcome, timestamp and `request_id`; exclude IP, Origin, credentials, token and quota/cap details. Retain the event for 90 days, subject to legal/operational review. If the event cannot be persisted, return `UNAVAILABLE`/503 rather than the normal generic quota response. The numeric quota remains open pending capacity evidence; event schema and failure/transaction behavior remain subject to T029 and G-SECURITY/G-CONTRACT review.
- **Owner-selected pre-auth session quota direction — 2026-11-01:** key the quota by Origin plus validated client IP, using a fixed reverse-proxy topology, and map exhaustion to HTTP 429 `RATE_LIMITED` without `Retry-After`, using the standard error envelope with `parameters: {}` and `request_id`; do not expose cap, expiry or quota-key details. Do not enforce it until the exact allowed-Origin set, proxy addresses/hops and trusted client-IP derivation are approved; never trust arbitrary forwarded-IP headers. Numeric cap, canonicalization and state lifecycle remain open for G-SECURITY/G-CONTRACT/G-OPS review.
- **Owner-selected global login-admission error direction — 2026-11-01:** when the service-wide pre-verification admission limit is exhausted, return HTTP 503 with `UNAVAILABLE`, a generic error body and no `Retry-After`. Use a continuously refilled token bucket with bounded burst; numeric rate/burst remain open. After restart, initialize the bucket empty and refill continuously, accepting temporary login unavailability. Reject before password verification; do not create a session, increment per-account failure state or emit a failed-verification audit event. The numeric limit, reset behavior and exact response-body schema remain open for synthetic-volume and G-SECURITY/G-CONTRACT review. This proposal does not extend the limited contract approval recorded in ADR 0002.
- **Owner-selected direction — 2026-10-31:** standard-library mTLS with static SHA-256 certificate-DER pins, <=90-day certificate validity and manual rotation with <=48-hour dual-pin overlap; add pairwise 32-byte HMAC-SHA-256 over a fixed length-prefixed request envelope with a +/-60-second timestamp window and durable 256-bit single-use nonce. HMAC key rotation is manual with a maximum 48-hour old/new key overlap, after which the previous key must be rejected. This direction does not approve implementation or schema.
- **Owner-selected HMAC coverage direction — 2026-11-01:** logically bind protocol version, sender and recipient/audience identities, `request_id`, operation, context, payload, transport timestamp and nonce in the request MAC; exclude the MAC itself. Derive/validate sender from the authenticated mTLS peer and ensure recipient/audience matches the local service, not an untrusted caller assertion. Full operation schemas, size limits and remaining validation/error details remain open for G-SECURITY/G-CONTRACT review.
- **Owner-selected HMAC length-prefix direction — 2026-11-01:** prefix each encoded field with its 4-byte unsigned big-endian byte length. Each field must also have a reviewed operation-specific size cap, checked before allocation; reject out-of-range or oversized lengths. Selected field order and encodings are recorded below; operation-specific caps and cross-language test vectors remain open for G-SECURITY/G-CONTRACT review.
- **Owner-selected HMAC structured-value encoding direction — 2026-11-01:** serialize validated `context` and `payload` values using RFC 8785 JSON Canonicalization Scheme encoded as UTF-8 before length-prefixing. Apply only schema-defined semantic normalization; do not add implicit global normalization. Parser constraints and Node/Python known-answer vectors remain open for G-CONTRACT/G-SECURITY review.
- **Owner-selected HMAC field-order direction — 2026-11-01:** encode fields in this fixed order: protocol version, sender identity, recipient/audience identity, `request_id`, operation, context, payload, transport timestamp, nonce. Do not depend on JSON object-key order. Permitted scalar grammars remain schema-dependent and open for G-CONTRACT/G-SECURITY review.

Treat time as trustworthy only while the OS time service reports synchronized; fail closed if synchronization is absent or not established, and do not silently substitute another clock. Future multi-version transition policy and schema review remain open.

- **Owner-selected HMAC service-identity matching direction — 2026-11-01:** require `sender` to match exactly the service identity resolved from the authenticated mTLS certificate pin, and `audience` to match exactly the local service identity. Compare strict ASCII values without aliases, case folding or normalization; reject unknown/mismatched values with the selected cause-neutral `UNAUTHENTICATED` response. Configuration semantics and enforcement evidence remain open.
- **Owner-selected HMAC rotation key-selection direction — 2026-11-01:** do not add a wire `key_id`. During the approved old/new overlap, compute and constant-time compare the MAC against every currently permitted pairwise key without early exit; accept if any comparison matches. After the absolute overlap deadline, verify only with the new key and reject the old key. Key storage and rotation-operation evidence remain open.
- **Owner-selected HMAC sender cutover direction — 2026-11-01:** a sender continues signing with the old key until an explicit operator cutover, which must occur before the absolute overlap deadline; after cutover it signs with the new key. A sender not cut over by expiry is rejected because the old key is no longer accepted. Exact operator procedure and recovery remain open.
- **Owner-selected HMAC overlap-deadline direction — 2026-11-01:** start the single absolute overlap deadline of no more than 48 hours when the first verifier installs and validates the new key. The owner accepts the residual risk that an endpoint not yet updated may continue accepting the compromised key until its own revocation is applied. Incident propagation, recovery and enforcement evidence remain open.

Protect the file with the OS so only the authorized service identity can read it. An operator installs/replaces each copy and exchanges key material through an administrative out-of-band channel. Never store keys in the repository, logs or SQLite. Exact ACLs, file lifecycle, atomic replacement, backup/recovery and enforcement evidence remain open.

Validate the key configuration before accepting connections and fail closed/not-ready if invalid. Exact atomic replacement, validation and recovery procedure remain open for G-OPS/G-SECURITY/G-ARCH review.

Reject unknown envelope and `auth` fields; reject unknown `context`/`payload` fields according to each operation's schema. Full schemas, parser constraints and cross-language vectors remain open for G-SECURITY/G-CONTRACT review; this is not parser or implementation approval.

## Ownership and authorization

The access server owns public request authentication, origin/CSRF enforcement, rate limiting and the public contract. The core owns execution and independently authorizes every operation and object. A designated contract owner reviews schemas and compatibility with both owners. Browser-supplied identity, role, channel or owner claims are never authoritative. The access server resolves them from a server-managed session or verified channel binding. The internal service authenticates the calling access service and accepts a bounded immutable request context only from it; the concrete transport and credential mechanism require G-SECURITY approval. Localhost alone is not authentication. Deny missing, expired, forged or inconsistent context and recheck current permission before consequential actions and resumed jobs. Channel roles are capped at user; guest uses local model without tools or persistent memory.

## Initial chat HTTP contract fragment

This reviewed fragment is deliberately limited to initial chat and is part of the limited basis in ADR 0002. Other modules require separately reviewed schemas. No payload limits, complete authentication scheme details or data-retention period are approved.

```yaml
openapi: 3.1.0
info:
  title: superHarry public chat API
  version: 1.0.0-draft
paths:
  /v1/chat/requests:
    post:
      operationId: createChatRequest
      description: Authenticated session required; server derives requester and channel.
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              additionalProperties: false
              required: [message, client_request_id]
              properties:
                message: {type: string, minLength: 1}
                client_request_id: {type: string, format: uuid}
      responses:
        '202':
          description: Accepted; same requester and client_request_id identify this operation.
          content:
            application/json:
              schema: {$ref: '#/components/schemas/Accepted'}
        '400': {$ref: '#/components/responses/Error'}
        '401': {$ref: '#/components/responses/Error'}
        '403': {$ref: '#/components/responses/Error'}
        '409': {$ref: '#/components/responses/Error'}
        '429': {$ref: '#/components/responses/Error'}
        '503': {$ref: '#/components/responses/Error'}
  /v1/chat/requests/{request_id}/events:
    get:
      operationId: streamChatEvents
      description: Owner-authorized SSE; Last-Event-ID resumes retained events.
      parameters:
        - {name: request_id, in: path, required: true, schema: {type: string, format: uuid}}
        - {name: Last-Event-ID, in: header, required: false, schema: {type: string}}
      responses:
        '200':
          description: Ordered event stream; see Event envelope below.
          content:
            text/event-stream:
              schema: {type: string}
        '401': {$ref: '#/components/responses/Error'}
        '403': {$ref: '#/components/responses/Error'}
        '404': {$ref: '#/components/responses/Error'}
        '409': {$ref: '#/components/responses/Error'}
  /v1/chat/requests/{request_id}/cancel:
    post:
      operationId: cancelChatRequest
      parameters:
        - {name: request_id, in: path, required: true, schema: {type: string, format: uuid}}
      responses:
        '202': {description: Cancellation requested; final event reports actual outcome.}
        '401': {$ref: '#/components/responses/Error'}
        '403': {$ref: '#/components/responses/Error'}
        '404': {$ref: '#/components/responses/Error'}
        '409': {$ref: '#/components/responses/Error'}
components:
  schemas:
    Accepted:
      type: object
      additionalProperties: false
      required: [request_id, status]
      properties:
        request_id: {type: string, format: uuid}
        status: {const: queued}
    Error:
      type: object
      additionalProperties: false
      required: [code, parameters, request_id]
      properties:
        code: {type: string, enum: [INVALID_INPUT, UNAUTHENTICATED, FORBIDDEN, NOT_FOUND, CONFLICT, RATE_LIMITED, UNAVAILABLE, EVENT_HISTORY_UNAVAILABLE, RESULT_TOO_LARGE]}
        parameters: {type: object, additionalProperties: {type: [string, number, boolean, 'null']}}
        request_id: {type: string}
  responses:
    Error:
      description: Stable code and safe parameters; no translated prose or secrets.
      content:
        application/json:
          schema: {$ref: '#/components/schemas/Error'}
```

Error parameters are allowlisted per code, never arbitrary exception text, content or credentials; the UI localizes codes through English and Spanish catalogs. Reusing an idempotency key with a different validated payload returns `CONFLICT`; same owner and same payload returns the existing request, never executes twice. Exact retention and allowed payload sizes require review. Status endpoints and full auth schemas remain future contracts, not implied interfaces.

## SSE event envelope and recovery

SSE frames use `id` as an opaque, monotonically ordered cursor scoped to a request, `event` as one of `state`, `delta`, `completed`, `cancelled`, `failed`, and `data` as JSON. Proposed common data fields: `request_id` (UUID), `sequence` (nonnegative integer), `type` (matching event), and `payload` (object). `state` contains `status` (`queued`, `running`, `cancelling`); `delta` contains `text` (string); `completed` contains final status only; `cancelled` contains final status only; `failed` contains the same stable error code and safe parameters. No generated text is executable. Each accepted request has at most one terminal event. If the server cannot retain or reconstruct requested events, return `EVENT_HISTORY_UNAVAILABLE` before beginning a stream; never silently restart or imply replay of side effects. Reconnect authorization and owner checks are repeated. Disconnection alone does not cancel work; cancellation is idempotent, races with completion, and cannot guarantee rollback of an already-issued external effect. Report unknown side effects and do not automatically repeat them. Exact replay retention and cross-restart durability are unresolved; T010 must define durable action semantics.

## Internal message envelope

For an authenticated access-service-to-core request, the versioned envelope is `{version, request_id, operation, context, payload}`. `context` has `{principal_id, role, channel, session_id, authorization_revision, issued_at, expires_at}`; fields are typed strings except timestamps, and `role` is one of `guest`, `user`, `admin`. The server derives and signs or otherwise integrity-protects this context using a transport mechanism selected and approved under G-SECURITY. Channel represents the verified entry point, not a user-supplied assertion. Core rejects unexpected versions, unknown fields or operations, invalid and expired context, replay outside agreed idempotency semantics, and role/channel inconsistencies. Operation-specific schemas validate `payload`; outputs use validated state/events or structured errors. Do not put session tokens, passwords, secrets or complete privileged credentials in model prompts or logs. Identity binding, credentials, key rotation, caller authentication and replay protection must be finalized and reviewed under G-SECURITY before implementation.

**Owner-selected authenticated-context proposal (2026-10-31):** Python validates the signed/integrity-protected context and its expiry but does not re-read current session, account or role state on each operation. The owner selected a maximum context lifetime of five minutes from `issued_at` to `expires_at`; the +/-60-second HMAC timestamp tolerance is separate and does not extend this lifetime. A revocation, account disablement or role/authorization revision change after context issuance may therefore remain unapplied until expiry. Python still independently validates each operation and enforces requester/object scope using the authenticated context; signature validation is not authorization. Exact timestamp/clock rules, whether renewal requires a fresh session resolution, and G-SECURITY/G-CONTRACT approval remain open.

**Owner-selected response-authentication proposal (2026-10-31):** authenticate Python-to-TypeScript responses using the established mTLS channel only; do not add response HMAC. The request HMAC does not authenticate a response. Each response must correlate to exactly one outstanding request using `request_id`; reject missing, mismatched or duplicate correlation IDs and invalid TLS peer identity. Exact response envelope/error schema, timeout and connection-reuse behavior remain subject to G-SECURITY/G-CONTRACT review.

**Owner-selected core-read failure and retry proposal (2026-10-31):** the core's five-second absolute deadline begins when Python receives the complete access-service request. Python starts a local monotonic timer at that point; the request envelope does not carry a deadline field, and the HMAC timestamp remains solely a replay/freshness check. The connection/request-transmission phase before core receipt inherits the outer HTTP request timeout; no separate internal transport timeout is selected. When Python is unavailable or the core deadline expires, the access service fails closed with `UNAVAILABLE` (public HTTP `503` where applicable). Do not fall back to direct SQLite access or serve stale cached results. The core must not commit operation effects after its deadline; uncommitted work is rolled back. If the operation commits before expiry but its response is lost, a caller-initiated retry with the same `request_id` retrieves the prior result without repeating effects. The access service does not retry automatically. Scope the deduplication key to the authenticated principal, operation and `request_id`; bind it to a durable fingerprint of the validated payload through context expiry (maximum five minutes), so a changed payload returns `CONFLICT` even if an earlier operation attempt rolled back. A matching payload may retry if no result was committed. Persist the request binding and, once committed, the deduplication result in SQLite only until the signed context's `expires_at`; retries using expired context are rejected. The owner selected persistence across Python restarts, subject to separate schema/migration approval. Each newly signed attempt must use a fresh, never-before-used 256-bit nonce while retaining the same `request_id` and payload. Python commits nonce consumption durably before checking the deduplication record; nonce reuse is rejected. For a new operation, the business effect and deduplication result must commit atomically in one transaction. If that transaction rolls back or expires, the nonce remains consumed, the request/payload binding remains, and no effect/result is recorded; a caller retry may use the same request ID and payload only with a fresh nonce. Timer enforcement feasibility, nonce-ledger schema/cleanup, request-binding schema/retention and transaction behavior remain unvalidated and require G-ARCH/G-CONTRACT/G-SECURITY review. This is a selected design threshold, not evidence that operations meet it on ARM64.

**Owner-selected retry fingerprint and preflight direction (2026-10-31):** calculate SHA-256 over the validated, typed payload serialized with JSON Canonicalization Scheme (RFC 8785). Apply only semantic normalizations explicitly defined by that operation's schema before serialization; do not apply implicit global trimming, case-folding or Unicode normalization. Ignore irrelevant JSON whitespace/key ordering; exclude `request_id`, principal/operation key fields, context, timestamp and nonce. In one durable preflight transaction, consume the fresh nonce and create or verify the request binding before checking the deduplication result. If the ID is already bound to another fingerprint, still commit consumption of the valid new nonce, leave the existing binding unchanged, and return `CONFLICT`. Per-operation schema validation, normalization rules, value constraints and Node/Python implementation compatibility must be reviewed; selecting RFC 8785 does not approve a package, wire format or storage schema.

**Owner-selected expiry cleanup direction (2026-10-31):** deduplication bindings/results are invalid exactly at the signed context's `expires_at`; nonce entries are invalid after signed timestamp + 60 seconds. A Python-owned SQLite sweeper deletes expired rows at startup and at intervals no greater than five minutes while the service is running. During shutdown, expired rows may remain physically in SQLite until the next startup, but the core must never treat or return them as valid. This cleanup/retention mechanism remains a proposal and needs schema/operations review.

| `chat.read_events` | `{request_id: UUID, after_cursor?: string}`. The cursor is opaque and scoped to the request; page size/response bytes are capped by reviewed server-side limits rather than permitting an unbounded caller-selected read. | `{events: Event[], next_cursor?: string, has_more: boolean, terminal: boolean}`. `Event` is the approved public SSE event envelope. Preserve ordering and return `EVENT_HISTORY_UNAVAILABLE` rather than silently restarting if retained history cannot be served. |
| `conversation.list` | `{after_cursor?: string, page_size?: integer}`; `page_size` is bounded by an explicit server-side maximum, still to be selected. | `{items: [{conversation_id: string, last_activity: timestamp}], next_cursor?: string}`. Contents are untrusted; do not expose hidden system instructions or credentials. A successful read updates last access for this conversation. Attachment metadata/bytes and deletion are outside this read operation and require separately reviewed operations. |

The owner selected the same non-disclosing `NOT_FOUND` response for an absent object and an existing object that the requester may not access. Apply this to object IDs in `chat.read_events` and `conversation.read`; do not include existence or ownership details in response parameters. Malformed identifiers/payloads still map to `INVALID_INPUT`; invalid sessions map to `UNAUTHENTICATED`; unavailable service maps to `UNAVAILABLE`; unavailable retained chat history maps to `EVENT_HISTORY_UNAVAILABLE`. Exact internal error/log handling and timing side-channel controls remain open. Never return SQL, filesystem paths, exception text or credential material. The selected caller-initiated same-`request_id` retry and core deadline rules are documented above; exact public mapping, operation effects and enforcement remain subject to contract/security review.

These are read-facing operations, not a decision that they are side-effect-free. The owner selected successful session resolution updating idle activity as the proposal direction; candidate behavior is to validate the session and update its activity in the same core operation, while invalid sessions do not update it. For T059, the owner selected successful `conversation.list` updating one user/history-list activity marker only (not each returned conversation), and successful `conversation.read` updating only the accessed conversation's last-access metadata. Transaction atomicity, clock source, concurrent updates, audit and retry behavior remain unapproved; denied or failed reads must not falsely record successful access.

#### T167 authentication and read schema refinements

The following are **agent-proposed schema drafts, 2026-11-01**, derived only from the accepted directions identified above, including the owner's explicit `null` representation for an absent cookie. They are intentionally bounded shapes, not JSON Schema, gate approvals, or implementation instructions.

For `auth.resolve_session`, the agent-proposed shape uses one closed request object and a distinct typed pre-auth context:

```text
context = {kind: "pre_auth"}
payload = {session_token: string | null}
```

The access service supplies this context only for `auth.resolve_session`; it does not carry `principal_id`, role, session ID, authorization revision, channel, or caller-asserted service identity. The authenticated mTLS peer supplies service identity. `session_token: null` represents an absent cookie; otherwise require the owner-selected canonical unpadded base64url encoding of exactly 32 bytes (43 ASCII characters). Reject unknown or duplicate fields, never log/cache/persist the raw token, and return the same typed `UNAUTHENTICATED` result with `parameters: {}` for absent, malformed, invalid, expired or revoked tokens and disabled accounts. On success, the candidate result is:

```text
{status: "active", principal_id: UUIDv4, role: "guest" | "user" | "admin",
 channel: "web", session_id: UUIDv4, authorization_revision: base64url-128}
```

Use canonical lowercase hyphenated UUIDv4 text (36 ASCII characters) for both IDs and canonical unpadded base64url of exactly 16 bytes (22 ASCII characters) for `authorization_revision`. The source of the result's `channel` value must not be a caller-supplied pre-auth claim and remains for G-SECURITY/G-CONTRACT review. The selected public mapping is HTTP 401 with the standard error envelope. Enforce the accepted 4,096-byte canonical result-payload cap. Successful resolution updates idle activity; unsuccessful resolution does not. This proposal deliberately does not choose token persistence columns, the pre-auth context's integrity/response binding, timestamps, or audit transaction layout. The selected `null` representation fixes only the absence encoding; schema and enforcement still require G-SECURITY/G-CONTRACT review.

For the remaining named reads, the safe draft boundary is a closed object with only the fields below; no owner selector, generic filter, SQL/table selector or caller-selected unbounded limit is allowed:

## Versioning and verification principles

`/v1` identifies the public major contract. Additive optional fields may only be introduced with documented forward compatibility; removals, changed meaning or authorization need a new major version and applicable approval. Internal version negotiation fails closed on incompatible versions. T024/T042 must test forged context, cross-owner stream/cancel, guest escalation, malformed payloads, duplicate IDs, cursor gaps, disconnect/reconnect, cancellation races, core outage and redacted errors. Threat cases TM-01, TM-02, TM-08 and TM-13 apply. No checks, implementation or service compatibility are claimed here. Consumers must stay within the limited approved basis and satisfy existing prerequisites; resolve open G-CONTRACT/G-SECURITY questions and obtain applicable approval before implementing other or changed contract details.
