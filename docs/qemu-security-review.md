Confirm source, build inputs and all relevant advisories at approval time. ## Proposed device and host constraints for review

QEMU's [ARM system-emulation example](https://www.qemu.org/docs/master/system/introduction.html) says its `virt` platform has no default network or storage device in that example and explicitly adds devices; its [manual](https://www.qemu.org/docs/master/system/qemu-manpage.html) separately describes default-device creation and `-nodefaults`. The owner selected QEMU defaults as the starting point, so neither the example nor a general manual statement identifies the effective graph. The owner selected versioned machine `virt-11.1` per the v11.1.3 source, pending confirmation in the candidate binary; explicitly chose `cortex-a76` rather than the documented `cortex-a15` default; and chose `virtio-blk` for the persistent root disk. During installation only, a temporary `virtio-scsi` controller and SCSI CD-ROM will attach the read-only installer ISO; review that transient graph separately and remove both after installation. Inspect/document actual realized devices, network interfaces/backends, listeners, storage, USB and display for both configurations once execution is approved. Do not assume 9p, AHCI, semihosting or other device presence/absence without evidence. The effective graphs must be reconciled with unrestricted guest egress, the no-inbound/no-forwarding boundary and advisory findings before approval; device-default selection alone is not a mitigation or security clearance.

Use a dedicated non-administrative host identity, synthetic data, and restricted file access. Store VM disks and state under repository-root `.dev-vm/`, ignored by Git and not shared with the guest; the owner selected explicit Windows ACLs granting access only to the current user, SYSTEM and local Administrators. Implement and verify the ACLs before provisioning. Automatically discard the session overlay and writable VARS after normal QEMU exit, but retain abnormal-exit remnants until explicit cleanup; verify QEMU has exited and released files before any removal. Unrestricted outbound Internet is an accepted design risk, not a control supplied by image authentication. Record artifact, firmware, machine, host and device configuration, review updates and validate boundaries. These measures do not establish physical isolation, production sandbox safety, Raspberry Pi performance, or protection from every QEMU defect.

## Blocking evidence before approval

1. Match the exact signed artifact to versioned source, packaging recipe and provenance; complete independent signing-key trust and review build configuration and firmware.
2. Resolve and authenticate the complete runtime dependency closure from a pinned repository snapshot, including versions, hashes, signatures, licenses, support and advisories. Review firmware and host components too.
3. Perform an up-to-date advisory review, including issues outside the eight displayed matches. Resolve each applicable finding against the source, build and proposed devices; record residual risk and review any proposed mitigation with the owner.
4. Inspect and document QEMU's effective default ARM64 launch/device graph and verify unrestricted outbound Internet access alongside the no-inbound/no-forwarding boundary; do not treat a hosts-file edit as restriction. After G-ARCH/G-OPS approval, validate realized devices, clean boot and network behavior with synthetic data. A successful boot does not close the security review by itself.

Evidence is source research only; no package was installed or executed and no VM was booted for this review. The constitution hash above was independently computed at the start of this work.
