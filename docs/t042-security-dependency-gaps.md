## Exact npm tarball inspection (2026-10-31)

The four owner-authorized research candidates were fetched at their exact registry versions and their downloaded bytes matched the npm `dist.integrity` SHA-512 value. The exact direct dependency `@noble/hashes` 2.4.0 declared by `otpauth` 9.5.2 was then examined the same way. The in-memory inspection results, archive SHA-256 values, selected metadata and file hashes are retained in the [artifact evidence](evidence/t014-authorized-npm-artifact-review.json). The tarballs were read as data only; no files were extracted to the workspace, and no package or lifecycle hook was executed. A match against a digest returned by the same registry is integrity evidence relative to that registry response, not independent publisher identity, build provenance, source correspondence or a vulnerability scan.

This inspection narrows, but does not close, candidate gaps:

- `argon2` 0.45.1's exact archive contains 64-bit AArch64 Linux `.node` binaries for both glibc and musl, plus MIT package text and a separate Argon2 reference-code notice offering CC0 1.0 or Apache-2.0 terms. Its `install` script invokes `node-gyp-build`; neither the selected ABI nor native artifact provenance, nested notices, dependency checks or runtime behavior is established.
- `otpauth` 9.5.2's exact metadata declares `@noble/hashes` 2.4.0 as a runtime dependency. The archive's MIT text is present, but that dependency's own artifact/license/advisory review and all TOTP security behavior remain open.
- `react-markdown` 10.1.0's exact archive confirms its React/type peers and parser/rendering dependencies; full closure, hostile-content behavior, URL policy, CSP and configuration review remain open.
- `file-type` 22.3.0's exact `source/index.js` returns `undefined` for unknown and text-based inputs (lines 1481 and 1708 in that archive). It is therefore a best-effort binary signature detector, not a universal MIME classifier. Any use must retain opaque file acceptance, treat undecidable types as `application/octet-stream`, and avoid treating detected MIME as validation or safety. This candidate alone cannot satisfy a claim that every possible file has a definitive MIME type.

The inspection does not select or recommend any candidate. Exact supported-target tests, complete direct/transitive/optional/build closure, provenance, fresh advisories, full notice dispositions and G-ARCH/G-SECURITY/G-CONTRACT decisions are still required; candidates that fail any mandatory project constraint remain ineligible.

### Limited DSSE and workflow verification

The DSSE PAE signatures in those three SLSA bundles were verified with OpenSSL using the ECDSA leaf public keys embedded in the same bundles. The leaf certificate SANs and validity periods were inspected; each certificate was valid at its recorded Rekor `integratedTime`. GitHub Actions metadata reports successful runs for the declared source commits. For `@noble/hashes`, the leaf SAN names the reusable workflow in `paulmillr/jsbt`; the successful release run in `paulmillr/noble-hashes` lists that exact reusable workflow commit, so the SAN difference is explained by the delegated workflow rather than an unexplained repository mismatch.

The [read-only verification script](evidence/verify_t014_slsa_rekor.py) selects the SLSA predicate specifically (not the separate npm publish attestation) and queries Rekor by its declared entry index. For all three SLSA bundles, the live record body matches the bundle's canonicalized body; bundle and live Merkle calculations reproduce their respective roots. Checkpoint-note signatures also verify mathematically against the published Rekor key whose ID matches the key digest. However, the Sigstore trusted-root file supplying that key was fetched from the root-signing GitHub repository and was not TUF-authenticated, so this is not an authenticated trust decision.

Each inclusion-proof index differs from its entry `logIndex`: argon2 `2093242011` vs `2215146273`; otpauth `2582699781` vs `2704604043`; noble-hashes `2495478085` vs `2617382347`. Looking up each proof index returns a different body even though the supplied Merkle path recomputes to the checkpoint root for the bundle body. This leaves an unresolved index/body inconsistency; signed entry timestamps, trusted-root authenticity and the explanation for the index discrepancy remain unverified. Do not treat this as fully authenticated provenance. The corresponding retrieval timestamp and digests are in the [artifact evidence](evidence/t014-authorized-npm-artifact-review.json).

This is a bounded signature check, not a Sigstore trust decision. The Fulcio certificate chain/root and revocation state, authenticated Rekor checkpoint/SET, and a project-specific provenance policy remain unverified. These attestations therefore provide stronger evidence than an unsigned metadata claim but are not independently authenticated provenance or package approval. npm metadata did not advertise provenance for `react-markdown` or `file-type`. No candidate is selected or cleared for use.
