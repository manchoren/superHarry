On 2026-11-02 the owner accepted the upstream ARM64 test-coverage gap for `cryptography==50.0.2`, retaining it as the candidate and choosing ARM64-emulated validation plus the full T014/G-ARCH review before installation; this does not authorize installation or implementation. On 2026-11-02 the owner also approved the specific fail-closed behaviors recorded in "Approved fail-closed behavior" below for active sessions, new enrollment, infrastructure-caused confirmation failures, administrative factor revocation and external error disclosure; these approvals do not extend to key generation/provisioning, rotation, the AEAD dependency, schema implementation or deployment. On 2026-11-02 the owner also approved a key-lifecycle policy baseline (256-bit OS-CSPRNG key, one-time OS-admin provisioning, host credential excluded from application backups, explicit re-enrollment rather than automatic replacement on irrecoverable loss, annual rotation with immediate rotation/re-enrollment on suspected compromise), recorded under "Approved key-lifecycle policy baseline" below; it does not extend to operator identity/command controls, credential-backup existence, TPM presence, systemd unit directives, rotation/re-encryption procedure details or target-image verification. ## Proposed boundary

Use the approved host-bound systemd-credential direction to deliver a dedicated key to the Django service at startup. The candidate key is 256-bit, random, and distinct from session, backup and memory keys; its generation/provisioning is not approved. The application would use a separately reviewed authenticated-encryption implementation to encrypt TOTP seeds before storing them in the database. A systemd credential protects delivery of the key to the service; it does not itself encrypt TOTP database fields.

Store only authenticated ciphertext and the metadata needed to decrypt it, including a unique nonce and an account-bound authenticated-data value. Keep the key and plaintext seed out of the database, logs, downloadable backups and agent/model context. Only the service should be able to read the decrypted credential. Never fall back to plaintext or generate a replacement key when the credential is missing, invalid or unavailable.

The host-bound option is not a hardware-backed guarantee. It may not protect against privileged access to the host, and losing the host credential may make existing TOTP seeds unrecoverable. Do not assume TPM availability or copy a host-bound credential to another device as a recovery method.

## Authenticated-encryption dependency candidate

The owner selected PyCA [`cryptography==50.0.2`](https://pypi.org/project/cryptography/50.0.2/) as the preferred AEAD candidate on 2026-11-02, with alternatives to be researched only if implementation or platform problems arise. This is not completion of the T014/G-ARCH dependency gate or authorization to install/use the package. A bounded upstream evidence review on 2026-11-02 made no package download, installation, execution or dependency resolution.

[PyPI metadata](https://pypi.org/pypi/cryptography/50.0.2/json) records release date 2026-09-30, `Requires-Python >=3.9` (excluding 3.9.0 and 3.9.1), and license expression `Apache-2.0 OR BSD-3-Clause`. CPython runtime metadata requires `cffi>=2.0.0`; the complete dependency closure, including `pycparser`, remains unreviewed.

PyPI lists multiple ARM64 Linux wheels rather than one uniquely applicable artifact. For example, the CPython 3.11 stable-ABI wheel `cryptography-50.0.2-cp311-abi3-manylinux2014_aarch64.manylinux_2_17_aarch64.whl` is 4,731,146 bytes with SHA-256 `79def8d059362e7831389ed3be0ecdf58a89386e1271e35dd9f5af84e81bffd0`; other `cp311-abi3` variants require glibc 2.28 or 2.34, and `cp39-abi3` variants also exist. PyPI lists Python 3.12 and 3.13 support, and the stable ABI tags are consistent with those versions. Actual pip artifact selection and compatibility on the target were not tested. A publisher-listed artifact and digest do not establish trusted provenance.

The [official installation guide](https://cryptography.io/en/latest/installation/) lists Debian Bookworm, Trixie and Sid as tested on x86-64, and ARM64 for Ubuntu rolling; it does not explicitly list Debian ARM64. The Debian ARM64/Python 3.13 target therefore remains an upstream test-coverage gap, even though the published manylinux glibc floors appear compatible by tag.

The [official AEAD documentation](https://cryptography.io/en/latest/hazmat/primitives/aead/) specifies that `ChaCha20Poly1305` uses a 32-byte key, 12-byte nonce and 16-byte appended tag, and warns that nonce reuse with a key compromises security. `AESGCM` supports 128-, 192- or 256-bit keys, recommends a 12-byte nonce for performance, and gives the same non-reuse warning. Neither algorithm nor nonce-allocation method is selected.

The [50.0.2 changelog](https://cryptography.io/en/latest/changelog/) states that Linux wheels were built with OpenSSL 4.0.3. The bounded advisory review found no queried OSV/GHSA/PyCA advisory open against 50.0.2; it identified [PYSEC-2026-3552](https://osv.dev/vulnerability/PYSEC-2026-3552) as fixed in 50.0.0, [PYSEC-2026-3553](https://osv.dev/vulnerability/PYSEC-2026-3553) and [PYSEC-2026-3554](https://osv.dev/vulnerability/PYSEC-2026-3554) as fixed in 49.0.0, and [GHSA-537c-gmf6-5ccf](https://osv.dev/vulnerability/GHSA-537c-gmf6-5ccf) as fixed in 48.0.1. This is a time-bound negative search result, not proof of absence. A current OpenSSL 4.0.3 advisory check was not performed. The wheel's third-party notices/license files were not fetched or inspected.

T014/G-ARCH work remains before installation or implementation: review the complete `cffi`/`pycparser` and bundled OpenSSL component graph, exact notices and license disposition, current PyCA and OpenSSL advisories, publisher artifact evidence under the project's trust policy, actual pip resolution, and ARM64 runtime compatibility. The owner accepts that official PyCA test coverage does not include Debian/Raspberry Pi OS ARM64; the selected validation path is the existing ARM64 emulator, not a requirement for upstream certification. Emulator evidence does not establish Raspberry Pi hardware or deployment behavior. Official Django documentation reviewed on 2026-11-02 confirms its signing API provides integrity, not confidentiality/AEAD, and therefore is not a direct substitute for encrypting TOTP seeds. If this candidate has implementation or platform problems, review an alternative AEAD package before adoption; do not treat Django signing as encryption. The bounded review did not install or execute an artifact.

## Approved fail-closed behavior (2026-11-02)

The owner approved these precise behaviors for when the host credential, key or `key_version` is missing, invalid, corrupted or unavailable. They do not approve key generation/provisioning, rotation, the AEAD dependency, schema implementation or deployment; T029's audit event shape, storage and failure semantics remain a separate, unapproved design.

- **Login for an enrolled account:** treat the failure as the same generic credential failure already used for a wrong TOTP code; create no session. This extends, without changing, the generic-failure behavior already accepted in the [T027 authentication flows proposal](t027-authentication-flows-proposal.md) to explicitly cover the key-unavailable/key-version-mismatch case.
- **Existing authenticated sessions:** do not revoke or sign out an already-authenticated session automatically because the key later becomes unavailable. Deny only the specific TOTP-dependent operation that needs the unavailable key; the session itself stays valid until it expires or is revoked through an existing separate control.
- **TOTP-dependent operations in an authenticated session** (for example a step-up verification required before a sensitive action): deny the specific operation with a generic external failure while the key is unavailable; never fall back to skipping the TOTP check.
- **New enrollment:** if the seed cannot be encrypted because the key is unavailable, block enrollment entirely and do not create a pending `TOTPDevice` row. No placeholder, empty-ciphertext or later-fill record is created.
- **Confirmation of a pending enrollment:** if the key becomes unavailable while decrypting the pending seed to check the submitted code, that failure does not count as a wrong user-submitted code against the user's attempt/rate limit; the device stays `pending` and unconfirmed. A wrong code (key available, authentication fails on content) still counts normally.
- **Administrative revocation/disablement:** an admin may revoke or delete an enrolled user's `TOTPDevice` without decrypting its stored seed, even while the key is unavailable, because revocation does not require reading the secret. This does not change the existing requirement for recent reauthentication, explicit confirmation and mandatory audit before an admin reset; record in the required audit trail (T029, still pending design) that the action happened while the key was unavailable, for later review.
- **Error disclosure:** every case above returns the same generic external error already used for other credential failures; the response never distinguishes key-unavailable, `key_version` mismatch, ciphertext-authentication failure or corruption. The specific cause is recorded only in the internal audit event (T029, still pending design), never in the response body or in logs reachable by the affected user.

Still open and not approved by this section: key generation/provisioning and rotation mechanics, the AEAD dependency and schema implementation, and any operational alerting threshold for repeated fail-closed events. Pending-enrollment expiry/cleanup, including when the delay is caused by a key outage, is resolved as policy on 2026-11-02 in the [TOTP storage schema proposal](t027-totp-schema-proposal.md#approved-pending-enrollment-expiry-and-disablereset-deletion-policy-2026-11-02): a 10-minute expiry from `created_at`, cleaned up both opportunistically in the enrollment flow and via the daily Q-13 reconciliation job, regardless of whether the key was available; implementing that cleanup remains open.

## Approved key-lifecycle policy baseline

Under G-SECURITY, the owner approved the following key-lifecycle policy baseline on 2026-11-02, at policy level only, responding to the proposed baseline in the decision form: a 256-bit key generated with the OS CSPRNG; one-time OS-admin provisioning; the host-bound systemd credential stays out of application backups; explicit re-enrollment (never automatic key replacement) on irrecoverable key loss; annual rotation as the proposed rotation period; and immediate rotation with re-enrollment on suspected compromise.

This is a policy-level approval only; it does not authorize key generation, dependency installation, systemd configuration or implementation. It also does not resolve: operator identity and command controls for key generation and provisioning; whether a separate administrative backup of the host credential exists and how it would be custodied; TPM presence or availability on the target host; exact systemd unit directives (for example `LoadCredentialEncrypted=`, sandboxing options); the concrete rotation/re-encryption procedure, `key_version` concurrency and transition-window limits; and verification of this behavior on the selected Raspberry Pi OS image. These remain open under G-OPS, G-SECURITY and G-ARCH as applicable.

## Decisions and evidence still needed

- Select and verify the actual target OS, systemd version, credential directives, service identity, filesystem permissions and behavior after restart. The Debian ARM64 development guest is not proof of Raspberry Pi OS behavior.
- Complete the T014/G-ARCH review for the candidate dependency above or select a different reviewed implementation. No encryption package is selected or approved.
- Approve the TOTP storage schema under G-CONTRACT. The existing T023 approval covers only `Conversation` and `Message`; the reset-grant approval does not cover TOTP fields or recovery-code records.
- Specify secure initial key generation/provisioning, permission boundaries, replacement/rotation, backup/restore treatment and failure recovery. A credential outage or authentication failure must not silently disable MFA or create an empty key. Policy-level direction for generation/provisioning method, backup exclusion, loss/recovery and rotation cadence is now resolved in "Approved key-lifecycle policy baseline" above (2026-11-02); the concrete provisioning command/operator identity, credential-backup existence, TPM presence, systemd unit directives and rotation/re-encryption procedure remain open.
- Resolved for the specific cases listed in "Approved fail-closed behavior" above (2026-11-02): generic login failure with no session, no automatic session revocation, blocked new enrollment, confirmation failures excluded from the user's attempt count, administrative revocation without decryption, and generic external error disclosure. On 2026-11-02 the owner also resolved abandoned-pending-enrollment cleanup and disable/reset record deletion as policy (see the TOTP storage schema proposal link above). Key generation/provisioning, rotation and alerting thresholds remain open.
- Preserve the selected TOTP policy: 30-second steps, six digits, the current step plus one adjacent step on each side, rate limiting, atomic rejection of an accepted step, verification before enrollment activation, and ten single-use 128-bit recovery codes stored only as verifiers. These selections do not approve their schema or implementation.
- Require a separate, audited OS-admin recovery flow for an administrator who loses all factors. Ordinary-user recovery codes do not replace that process; T031 remains separately gated.

The candidate field set and semantics are documented in the [T027 TOTP storage schema proposal](t027-totp-schema-proposal.md); they are not yet approved.

## Validation after approval

Before any deployment, test authenticated-ciphertext integrity, account binding, nonce uniqueness, unavailable/wrong credentials, corruption, service restart, backup exclusion, key rotation/re-encryption failure and recovery behavior. Confirm through negative OS-level access checks that other processes cannot read the decrypted credential. Run dependency and ARM64 checks only after the exact package and environment receive their approvals. No key was generated, package installed, schema changed, secret provisioned or TOTP test run for this proposal.
