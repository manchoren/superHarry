# HTTPS, service privileges and LAN/VPN deployment proposal

Status: T011 preliminary design only, 2026-10-30. T003 is complete at design-proposal scope; T008 and T011 remain incomplete, and G-OPS and relevant G-SECURITY decisions remain open. No service, firewall, certificate or VPN has been configured. Constitution baseline 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`.

## Exposure and trust boundaries

The accepted policy is LAN/VPN access only, without public exposure or port forwarding. Propose Caddy as the TLS edge, with application listener restricted to explicitly approved LAN and Tailscale interfaces/addresses, and host firewall default-deny inbound with a narrow approved exception. The allowed LAN interfaces and IPv4/IPv6 subnet rules, Tailscale authorization policy, firewall technology and persistence must be selected and verified under G-OPS. Restrict VPN peers by explicit tailnet policy; Tailscale access does not replace application login or authorization. Do not assume router NAT or tailnet membership alone enforces this boundary. Tailscale [ACL documentation](https://tailscale.com/docs/features/access-control/acls) describes tailnet access policy; verify the deployed policy and client identity without granting application roles from it.

Caddy forwards only application routes to a non-public access-server endpoint. Automatic HTTPS can also create an HTTP redirect listener; explicitly constrain or disable any such listener and include it in exposure tests rather than assuming only the HTTPS listener exists. The setup listener is a separate loopback-only HTTPS listener, reachable on the Pi or via authenticated SSH local port forwarding, never routed through the LAN listener. Ensure IPv4 and IPv6 loopback, DNS, listener and reverse-proxy configurations cannot expose it indirectly. Authenticated bootstrap remains subject to [T008](bootstrap-recovery-proposal.md). For the core and broker, restrict local connections to approved service identities and use their approved authenticated trust contracts; loopback alone is not authentication.

## Local CA lifecycle

Before setup, provision Caddy's local CA and matching leaf certificates for localhost and the configured LAN hostname. [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https) documents local certificate issuance and renewal; local trust installation can fail or apply only to some stores, so independently verify every relevant browser and OS trust store. Explicitly review local issuance configuration, storage and listener bindings against the deployed Caddy version; do not rely on automatic public-CA issuance for a chosen name. Do not expose the Caddy administration endpoint beyond approved local administration.

Protect CA private and intermediate keys with least-privilege filesystem access; never include them in downloadable backups, logs or runtime-agent access. Transfer only the public root certificate to clients through an authenticated integrity-verified channel and compare its fingerprint with the authenticated OS administrator session. For headless bootstrap use SSH forwarding and verify the `localhost` certificate; for LAN/VPN use a reachable name matching its certificate. No warning bypass or unverified IP fallback is acceptable. If mDNS is unavailable or a name conflicts, require the admin to configure a reachable matching name. The concrete VPN DNS/name strategy is unresolved.

Monitor expiration and renewal failure, test renewal before expiry and reissue when hostnames change. On compromise or replacement, revoke/remove old client trust, provision a new protected CA, securely distribute its public certificate, verify the replacement on each client and document outages and recovery. Avoid claiming public revocation infrastructure for this local CA. Caddy's [TLS directive documentation](https://caddyserver.com/docs/caddyfile/directives/tls) describes the internal issuer, but no configuration is approved here.

## Service and secret separation

Propose dedicated unprivileged OS identities for the access service and core, a separate Caddy identity and an independently restricted network broker, plus explicit ownership of sockets, mutable data and keys. No runtime task code or sandbox may access host credentials, CA keys, the main database, broker socket or service management interface. The access server can request network operations only after authenticated admin authorization; broker verifies its OS peer and exposes a fixed validated operation set. T012 must design transactionality and peer verification. User-scoped storage enforcement remains an application obligation.

The installer or OS admin, not the agent, provisions privileges and first-run bootstrap. Review systemd unit isolation, restart policy, writable paths, process/resource restrictions and secret delivery after exact OS and versions are selected. The [systemd execution environment documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html) describes available service controls, but its latest-version features are not assumed available on the selected target. Environment variables or an approved secrets manager provide credentials; decide precise delivery and renewal with G-SECURITY/G-OPS. Missing keys, failed audit or unauthorized peer identity fail closed without leaking secret material.

## Approval and validation

G-OPS must approve exact Caddy/Tailscale versions, firewall and DNS mechanisms, listener bindings, accounts, privileges, units, certificate provisioning and replacement. G-SECURITY must approve internal authentication, secret delivery and trusted proxy/origin handling; G-ARCH covers dependencies. T003 and T008 completion precede implementation. Proposed tests: enumerate all IPv4/IPv6 listeners and externally probe LAN, VPN and disallowed interfaces; reject public exposure, unauthenticated/unauthorized clients, forwarded-header spoofing, direct internal access and setup routes from LAN; test wrong hostname, absent CA trust, renewal, reissue and CA replacement; verify inaccessible keys, services, broker and audit on denial. Exercise startup, restart and failure with synthetic data in ARM64; repeat physical-network, HDMI and recovery acceptance on the real Pi. No such tests have been executed.
