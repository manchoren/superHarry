# Resource governance and durable action-state proposal

Status: T010 design proposal, pending G-MODEL, G-CONTRACT and any applicable security/operations approvals. No workload, scheduler or state machine is implemented. Constitution baseline 2026-10-29 SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. Depends on proposed [contracts](contracts-proposal.md) and [model routing](model-routing-proposal.md); they are not approved interfaces. T009 provides public-documentation research but account access, capability and budget decisions remain unresolved.

## Admission and single heavy-job slot

One trusted coordinator arbitrates local inference, STT, TTS, OCR and heavy sandbox executions across all entry points. A job must obtain the single slot before work starts and release it only after the worker actually stops; cancellation or lost connection is not proof that compute has stopped. On restart, reconcile worker processes before admitting another job; if absence cannot be established, remain blocked and surface a recoverable error. A loaded idle model may remain resident only when memory budgets permit; it is not inference. No independent channel, scheduled job or admin operation bypasses this coordinator. Lightweight work is classified conservatively; unclassified or uncertain heavy work fails closed until classified.

Proposed admission sequence: authenticate and authorize requester and current operation; validate inputs, mandatory context fit and budget; evaluate queue and memory availability; enqueue with owner, job class and deadline; atomically assign the slot to one eligible job. A worker reports start/stop to the coordinator with a generation identifier, so stale completions cannot free a newer job's slot. Memory and CPU admission measurements, headroom, bounded queue capacity, sampling method, worker isolation, priority ordering beyond accepted guest policy and fairness require G-MODEL/G-OPS review and real-Pi measurements. If metrics are unavailable or the required headroom is unknown, fail closed for new heavy admission instead of assuming capacity. Preserve UI/API responsiveness and bounded control-plane capacity when saturated.

Guest work starts only while otherwise idle, has at most one pending or running question per session, and has an initial configurable ten-minute queue timeout; a running guest answer may finish when higher priority work arrives. User/admin work takes precedence for new starts. Queue timeouts, worker deadlines, cancellation and overload return stable localized error codes and release reservations when safe. Do not block authentication, health, cancellation or audit processing behind heavy work. Exact classification, starvation prevention, capacity, per-class limits and non-guest deadline values remain open.

## Required context and local requests

Before every runtime agent invocation, including delegated agents and every model/channel, count complete current constitution, mandatory protected instructions, required tool definitions, user input and output reserve using the selected model's tokenizer. Measure overhead again after model, prompt format or constitution changes. Trim only optional history, retrieved data or non-mandatory context and preserve trust labels. If mandatory content cannot fit, tokenization fails, or complete protected delivery cannot be verified, block agent action and return an explicit error; never truncate the constitution silently. Enforce permissions in code regardless of prompt content. Local inference queues behind the shared slot, streams responses and uses configurable connection, queue and execution deadlines; exact timeout and cancellation semantics need approval and measurements. Stop or quarantine a worker that cannot honor cancellation; do not reuse its slot until termination is confirmed.

## Proposed durable operation lifecycle

Persist an opaque operation ID, owner and authorization revision, validated intent reference, creation time, idempotency key, current state, attempt and an audit-safe outcome. Do not persist secrets or unnecessary prompt contents in audit metadata. States and allowed transitions:

| State | Transitions and conditions |
|---|---|
| `queued` | `running` only after admission and current permission checks; `cancelled` before dispatch; `expired` on deadline. |
| `running` | `completed` on confirmed success; `failed` on definitive failure; `cancelling` on requested cancellation; `awaiting_provider` if premium-dependent work cannot continue locally; `unknown` when an external side effect may have happened but its outcome cannot be established. |
| `cancelling` | `cancelled` only after the worker is stopped and any side-effect outcome is known; `completed` if completion won the race; `unknown` when dispatch outcome is uncertain. |
| `awaiting_provider` | `queued` after provider/budget recovery and renewed authorization; `cancelled` by owner; no new action without valid confirmation. |
| `unknown` | Remains blocked from automatic retry; notify owner and reconcile with authoritative evidence if available. A new consequential action requires current authorization and fresh confirmation where required. |
| `completed`, `failed`, `cancelled`, `expired` | Terminal for this operation; an explicit new operation is subject to normal checks. |

Persist a dispatch-intent record before a side effect, then persist definitive outcome; if crash occurs between these points, mark `unknown` unless a trustworthy idempotency protocol or authoritative reconciliation proves the outcome. Do not assume transport timeout equals failure. Internal idempotency keys are scoped to owner and validated payload; reuse with different payload is rejected. A worker crash, audit failure, cancellation race or lost provider response cannot be treated as successful cancellation. State transitions and mandatory audit must share a transaction or a reviewed durable fail-closed protocol; physical storage and contract choices remain pending. SSE events report persisted states and cannot promise that disconnect cancels work. Retention and reconnect behavior need agreement with T005.

## Routing, budgets and retries

Guests never reach the premium provider. For authorized requests, follow the [routing proposal](model-routing-proposal.md): atomically reserve approved worst-case budget before premium dispatch and settle verified actual usage; uncertain charges stay reserved until reconciliation. On premium outage, timeout, rate limit or exhausted budget, directly attempt local continuation only if capability, mandatory context, current authority and side-effect safety permit. Otherwise notify the owner, retain premium-dependent work in `awaiting_provider`, allow cancellation, and resume only when provider, budget and permission permit. No alternate premium provider is implied. Use a circuit breaker with bounded exponential backoff for recovery probes, within a reviewed probe budget. Retry only safely repeatable work or verified idempotent operations; do not repeat unknown consequential actions or duplicate charges silently.

Open decisions include retry counts and backoff ceilings, queue and execution deadlines, fallback eligibility and model capability mapping, RAM thresholds, fairness and starvation, token/cost limits and reservations, reconciliation, audit durability, retention, and crash handling mechanisms. None is numerically approved here; approval and actual hardware evidence must precede enabling selected policies.

## Verification obligations

Mocked tests must cover concurrent admissions across all heavy classes, cancellation with delayed worker exit, stale generation completion, restart with an orphan worker, unavailable metrics, guest priority and expiry, queue starvation, required-context overflow, inaccessible tokenizer, failed protected delivery, provider timeout and local fallback, exhausted budget, simultaneous reservations, unknown charge, stale permission, duplicate requests, crash before/after side-effect dispatch and confirmation invalidation. Check API responsiveness under synthetic load and audit persistence failures. Emulation verifies behavior, not Pi performance or physical isolation. T010 is a design artifact only; no tests or measurements were run.
