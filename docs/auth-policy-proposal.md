# Authentication, authorization and guest policy proposal

Status: T007 design proposal, pending G-SECURITY and related contract approval. Constitution baseline 2026-10-29 SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. This design builds on [contracts](contracts-proposal.md) and [threat model](threat-model.md); no changes to roles or implementation are approved by this document.

## Identity and session lifecycle

The access service derives identity and effective role from authenticated, revocable server-side sessions, never from a model, client-supplied role or forwarded identity header. Account creation is administrator-only. Authenticate using Argon2id password verifiers, with an approved minimum-length and breached-password strategy; exact parameters and dependency selection require review. Login failures use generic responses, rate limits and progressive lockout without revealing whether an account exists. TOTP is optional for admin and user, with encrypted/restricted seed handling; enrollment, disabling, recovery and account changes require authenticated, recently verified credentials and auditable confirmation. No guest MFA or passkeys are introduced.

Propose a random opaque session identifier in a Secure, HttpOnly, SameSite=Strict cookie over trusted HTTPS, with server-side expiration and revocation. Rotate it after authentication and privilege changes; revoke affected sessions on logout, password reset, account disablement or role change and re-evaluate active work before privileged execution. Prevent fixation, reject expired/revoked sessions, and protect state-changing requests against CSRF with a server-validated token and strict CORS. Exact durations, token construction, breached-password method, MFA drift/replay handling and encryption scheme are G-SECURITY decisions, not established values.

Password reset uses short-lived, single-use, stored verifier-backed tokens through an approved authenticated recovery path, with generic responses and atomic redemption. No unauthenticated reset endpoint or unapproved delivery channel is authorized. Reset invalidates old sessions and outstanding tokens; MFA loss is treated separately and cannot silently bypass MFA. Administrator loss requires the distinct OS-admin recovery design in [bootstrap proposal](bootstrap-recovery-proposal.md). Tokens and credentials must never appear in logs, URLs, process arguments, model context or downloadable backups.

## Role and object enforcement

Deny by default at every API, core, tool and storage boundary; bind authenticated requester, effective role, verified channel and owner before authorization. Validate capabilities per operation and object rather than trusting hidden UI or model output. Guests may use only local chat and session-scoped temporary context: no memory, tools, file upload, sandbox, cron, skill, messaging, external model or display. Users access only their own data and allowed actions; admins have the plan's explicitly enumerated privileges in the web app. Channel requests use the linked identity and at most user privilege even for an admin. Recheck access at execution time and on reconnect, cancel, account change and channel unlink. Users retain delete-all access to their own memory when visibility is hidden.

## Guest admission and proxy trust

Guest sessions expire after 24 hours and their temporary conversation context is deleted. Initial admin-configurable limits: three guest session creations per hour per origin, ten questions per hour per session, one queued or running question per session and ten-minute queue timeout. Guests are low priority and begin when the device is otherwise idle; an already running guest response may finish. Rate limit and queue enforcement occur outside the model. Expiry, restart and cleanup behavior must not retain guest context or reset limits in a way that silently grants unlimited access.

Propose an explicit allowlist of proxy identities and trusted network endpoints in deployment configuration. Only when the immediate connection is from an approved proxy may the server derive origin from a validated forwarding chain generated by that proxy; strip untrusted incoming forwarding headers at the edge. Direct callers cannot assert their own origin. Reject ambiguous, malformed or untrusted chains rather than choosing an attacker-controlled value. Define IPv4/IPv6 normalization, address changes, NAT sharing, privacy, storage retention and fail-closed behavior in T011 and G-SECURITY; do not rely on an unvalidated header as a unique person identifier. Exact proxy configuration requires G-OPS.

## Confirmation and audit

Administrative operations run through the web app, with server-enforced role checks. For sensitive operations, propose a recent password and, if configured, TOTP verification bound to the authenticated session; a one-use confirmation binds actor, action, target, parameters and expiry and is invalidated on changed state or session revocation. Thresholds and precise operations require G-SECURITY approval; existing stronger plan requirements prevail. Browser consequential actions require confirmation by the authorized controller under display rules and may not be elevated by a channel. Log redacted privileged attempts and outcomes independently of optional diagnostics; missing audit persistence must not silently permit privileged mutations.

## Review and negative tests

T026–T035 should cover session fixation/replay/revocation, concurrent reset redemption, invalid/expired MFA and reset tokens, guessed user IDs, guest access to every forbidden capability, channel admin escalation, forged proxy headers, IPv6 and shared-origin limits, expired guest cleanup, CSRF, stale confirmations, audit outage, queue cancellation and privileged work after permission changes. TM-01, TM-02, TM-10, TM-11 and TM-13 apply. Approve exact password/MFA/crypto values, origin algorithm, limits' persistence, reauthentication lifetime, confirmation and audit failure behavior before implementation. No tests have run.
