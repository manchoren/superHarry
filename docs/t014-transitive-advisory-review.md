## Method and coverage

A read-only local Python script requested the official MSYS2 package page for each inventory name, extracted the displayed package version and archive SHA-256, compared both against the retained index, and extracted CVE identifiers only from a `Vulnerabilities` section. It did not download or execute package archives. [Machine-readable results](evidence/t014-transitive/catalog-review.json) include each page URL, page-response hash, snapshot and catalog version/hash, extraction status, section presence and CVE IDs; [the script](evidence/t014-transitive/catalog_review.py) is included to make the query method inspectable. The result file records UTC completion at `2026-10-31T23:06:21.615006+00:00`. This is the response retrieval time, **not** proof of the underlying vulnerability database synchronization time or completeness, and cannot by itself meet the owner's 24-hour cache rule.

All **159 of 159** requests and field extractions succeeded, and all 159 displayed the same package version and archive hash as the retained index. **26 records** displayed a vulnerabilities section with CVE identifiers, totaling **92 distinct CVE IDs** across those sections. Four records are the QEMU family (QEMU, qemu-common, qemu-guest-agent, qemu-image-util); excluding them leaves **22 non-QEMU records with 84 distinct CVE IDs**. The exact lists, including duplicate findings shared across packages, are in the JSON. The other 133 pages did not contain a vulnerability section and are **not** thereby classified as safe, cleared, fully scanned, or even covered by a complete advisory dataset. The first attempt failed to parse the catalog's nested `code` element for all pages; the corrected second run yielded the recorded result. A successful HTTP response, matching hash declaration and successful parse are not independent proof of artifact authenticity, actual installed components or advisory-source freshness.

[MSYS2 explains its vulnerability reporting](https://www.msys2.org/dev/vulnerabilities/): it builds a CycloneDX SBOM from package recipe metadata, runs Grype and presents potential findings; package CPE/PURL metadata influences matching. Its catalog is useful for leads, not a proof of binary vulnerability, exploitability, reachability, fix ancestry or no vulnerabilities. In particular, compare the separate [QEMU advisory review](t014-qemu-advisory-review.md), which identifies additional relevant findings beyond the catalog listing. Catalog CVE entries may represent package-level matches, duplicates, false positives, vulnerabilities in code not present or reachable, or real affected components: **each requires individual evidence**.
