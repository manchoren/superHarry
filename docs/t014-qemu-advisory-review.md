## Identity and source limitations

The [MSYS2 catalog](https://packages.msys2.org/packages/mingw-w64-ucrt-x86_64-qemu) currently identifies 11.1.3-1 with archive SHA-256 `72ba6064c81408a8f433859502405da7a93e012d2b9b9bcf7f66f07750882b34` and lists eight potential vulnerabilities. MSYS2 describes its [SBOM and Grype metadata-based process](https://www.msys2.org/dev/vulnerabilities/); its package list is a useful lead, not a complete binary- or configuration-specific disposition. In particular the catalog list did not include the selected-device CVEs below. The retained source and artifact correspondence evidence in [the decision packet](t014-next-decision.md) strengthens examination of candidate source and firmware but does not prove reproducible correspondence of source and Windows binaries. Signing-key identity, revocation and transitive dependency checks remain open.

The owner-selected configuration uses a virtio-blk root, virtio-scsi temporarily for installation and unconstrained outbound guest networking; the effective network adapter and QEMU defaults are not yet verified. The guest does not share host paths or use 9p under the selected design. The exact machine/device graph and actual binary behavior have not been observed, and no exclusions from source configuration can be assumed. The earlier owner acceptance of CVE-2026-93834 applied only to a distinct Debian Trixie Linux-host research scenario and is not acceptance for this Windows artifact.

## Static applicability analysis for the selected Windows/`virt` direction

This analysis uses upstream QEMU v11.1.3 source as published and the selected design; it is **conditional**, not a measurement of the signed MSYS2 executable. The source-only and binary archive signatures were mathematically checked in [the decision packet](t014-next-decision.md), but trusted source-to-binary reproducibility, build options and effective devices remain unverified.

**CVE-2023-1386 (9p passthrough).** The affected path requires a configured 9p passthrough filesystem, and the owner-selected design has no host-directory sharing or 9p device. Upstream v11.1.3 [`meson.build`](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/meson.build) restricts `virtfs` to Linux, macOS or FreeBSD hosts; its [`9pfs/Kconfig`](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/hw/9pfs/Kconfig) makes `FSDEV_9P` depend on `VIRTFS`, and its [`9pfs/meson.build`](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/hw/9pfs/meson.build) gates the filesystem backend on `CONFIG_FSDEV_9P`. This is affirmative source-level evidence that an unmodified native Windows build should not include the standard virtfs path. It does not establish the flags, patches, host detection or contents of the actual MSYS2 artifact, or eliminate unrelated sharing mechanisms. **Conditional conclusion:** the known passthrough route is unlikely under the selected design; retain the finding open until build correspondence and effective runtime devices/options are established. The separate older Debian Trixie host alternative runs on Linux, where this Windows-specific observation does not apply.

**CVE-2019-12067 (AHCI).** The upstream v11.1.3 [`ahci_commit_buf`](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/hw/ide/ahci.c) accesses `ad->cur_cmd->status` without a local null check, consistent with the historical tracker description; this alone does not prove the problematic state is reachable in this version or binary. The selected install/runtime storage is virtio-scsi and virtio-blk, with no AHCI explicitly selected. The upstream [`virt` board source](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/hw/arm/virt.c) initializes a PCIe host bridge and no text match for `ahci` occurs in that board file; this is evidence against a directly hardcoded AHCI device, not a complete default-device proof. Upstream [`hw/ide/Kconfig`](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/hw/ide/Kconfig) can enable the ICH9 AHCI model when PCI devices are built, and the `virt` board supports PCIe. A compiled model is not necessarily instantiated, but a supplied default or explicit PCI device could expose it. **Conditional conclusion:** the selected explicit storage path does not require AHCI; do not mark the CVE not applicable until the exact full command line, defaults, board/device tree and any dynamic device-add path are checked against the actual approved executable.

**Related network correction.** Upstream v11.1.3 [`virt.c`](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/hw/arm/virt.c) sets `default_nic` to `virtio-net-pci` and initializes configured NICs on its PCI bus. This is source-level evidence of the model expected when its default NIC is used, not proof that networking is enabled, the actual MSYS2 device graph or RSC feature state. Consequently CVE-2026-66900 remains relevant for review even if the selected command line does not explicitly name a NIC.

Before a disposition: retain exact reviewed arguments/configuration and binary identity; enumerate effective install and normal-run devices and backend exports after obtaining applicable approval; confirm whether hotplug, monitor/QMP and configuration file loading can add devices or shares; audit that no host-sharing backend exists; review component fixes and scanner findings for the actual artifact. A no-9p/no-AHCI graph would narrow these two exposure routes, but would not establish that the binary, firmware, network or all other devices are safe. No VM was started and no package installed for this analysis.

## Static inspection of the exact candidate package (2026-10-31)

The [MSYS2 main package server](https://repo.msys2.org/mingw/ucrt64/mingw-w64-ucrt-x86_64-qemu-11.1.3-1-any.pkg.tar.zst) supplied the candidate archive as temporary research data; the geo-redirector returned an HTTP verification challenge. The archive SHA-256 was `72ba6064c81408a8f433859502405da7a93e012d2b9b9bcf7f66f07750882b34`, matching the MSYS2 catalog and retained index. The matching hash authenticates neither the catalog nor signing-key identity; prior mathematical-signature and key-trust limitations still apply. No package code was executed or installed.

The archive contains `.BUILDINFO`, `.PKGINFO` and `ucrt64/bin/qemu-system-aarch64.exe`. `.BUILDINFO` identifies package `11.1.3-1`, recorded `pkgbuild_sha256sum` `905771a8d3f3f612d6772cec74d4daa5ba574bdd9378453f513dff7e1019bf8f` and the MSYS2 build job; its value is a package-supplied declaration, not independent attestation. The extracted executable is 31,163,150 bytes with SHA-256 `e7c4e6e70e8e37e635a18775e5312e150daab310b26fd228c713cce2195f7b4d`.

A read-only ASCII byte-string search of the executable found `virtio-9p-pci`, `virtio-9p-device`, `virtfs`, `fsdev`, `ich9-ahci`, `virtio-blk-pci`, `virtio-scsi-pci`, `virtio-net-pci` and `virt-11.1-machine`. In particular both `virtfs support is disabled` and `fsdev support is disabled` appear alongside 9p names and help text. Those strings may represent retained option/help text, disabled paths, device registrations, or other data; their presence does **not** establish that 9p is functional, nor does the disabled message establish that every 9p-related route is unavailable. Similarly the AHCI and virtio strings do not prove that a model is compiled, instantiated, reachable, patched or selected by default. This static observation is consistent with the source-level Windows `virtfs` restriction but does not independently validate runtime behavior or build configuration. The package-extracted files and archive were removed from the temporary research directory after inspection.

Before disposition, match the archive's declared recipe hash to authenticated build inputs, establish signer trust and revocation, review the full package and native dependencies and—only after applicable approvals—inspect the effective device graph and disabled-feature behavior. CVE-2023-1386 and CVE-2019-12067 remain open.
