## Assets, actors and boundaries

Assets include credentials and encryption keys; identity and role bindings; fixed directives and audit history; each user's conversations, memory, files and browser session; scheduled actions and their execution state; application, release and skill integrity; model budgets and device availability. Threat actors include unauthenticated LAN/VPN peers, malicious or compromised users, attackers controlling public destinations or third-party content, malicious skill/package authors, compromised channel identities, and a model following hostile input. Physical or OS administrator compromise and a malicious authorized administrator are not fully prevented by application access controls; protect secrets and require auditable administrative operations even so.

Trust boundaries are: client or channel to access server; access server to Python core; core to model, tools and user-scoped storage; approved download staging to isolated runtime; isolated runtime to host; application to OS/network broker, browser and display; and backup/update inputs to trusted state. Neither a model nor retrieved content is an authority. Authenticated identity, role, channel, ownership and operation are bound and checked by code at each boundary; mismatches and missing context fail closed. All runtime agents receive the complete constitution as protected context; failure or truncation blocks action, while code independently enforces permissions.

Guests have temporary context and local-model access only, with no persistent memory, tools, sandbox, upload, cron, skills, channels or external model. Users access their own scoped data and authorized operations. Admin actions require the web app; linked channels have at most user privilege even for an admin. Display control and capture belong to the current controller, subject to the plan's takeover rules. A request claiming a higher role or another owner is never sufficient evidence of either.

## Open decisions and evidence limits

G-SECURITY remains responsible for unresolved authentication, session/token lifecycle, cryptography, trusted proxy/origin handling and bootstrap/recovery details. ADR 0004 records limited owner approval of specified concrete security proposals; ADR 0006 records only the CSRF direction, investigation of host-bound systemd credentials and Caddy as the proxy direction. These are not overall security approval or closure of their open implementation details. G-CONTRACT covers internal identity and public contracts, storage and manifests; ADR 0002 records limited owner approval of the specified initial contract and storage scopes, not their open details or other contracts. G-SANDBOX covers isolation, mounts, network and resource limits; G-PACKAGES covers guard sources and mandatory checks. G-OPS covers deployment, service privileges and network broker; G-DISPLAY covers OS/browser isolation and handover; G-CHANNEL and G-SPEECH cover each integration and voice choices; G-MODEL covers routing and budgets. Applicable approvals remain specific to their recorded scopes; no proposal or threat inventory implicitly approves implementation. T005–T012 and the later gate-specific design tasks develop remaining decisions.

No sandbox, authentication, threat test, integration, hardware behavior or security acceptance has been verified in this documentation task. The linked S01–S15 fixture descriptions remain candidates pending T015 maintainer review; none has been executed. Emulation can exercise functional cases but cannot establish real Pi performance, HDMI behavior, physical isolation or thermal behavior. Review and maintain this inventory as implementation proceeds, including new attack paths and regression evidence.
