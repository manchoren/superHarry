## Phase 1 — Freeze the candidate

1. Review `docs/owner-attention.md` and confirm the existing D1, D2 and release
   authorization boundaries. Obtain any new approval required for package-tool
   installation or changes outside the already approved production scope.
2. Resolve the ARM64 full-suite failure before freezing a release. The current
   failure is `home_heavy_job_governor...test_second_waits_when_seat_busy`
   with `database table is locked: home_heavyjob`.
3. Reproduce it on an isolated DB, identify the transaction/connection left by
   the preceding test, and fix the actual isolation or transaction boundary.
   Do not change the production DB or hide the error with an unbounded timeout.
4. Run the full suite twice consecutively on ARM64 and record both results.
5. Create a clean commit and archive from that commit only. Record the source
   commit, archive SHA-256/SHA-512, size and file manifest. Confirm that no
   `.env`, database, credential or temporary test artifact is included.

## Phase 2 — Verify package provenance and package guard

1. Obtain the approved release archive's detached GPG signature, trusted
   key/fingerprint and SLSA/in-toto provenance for the exact digest.
2. Install or invoke a version-pinned `slsa-verifier` only under the applicable
   package/owner approval. Record tool identity and checksum.
3. Verify GPG and SLSA against the exact archive bytes. Modify one byte and
   prove both checks fail.
4. Feed the verified evidence into the package guard. Confirm that score alone
   cannot authorize installation.
5. Run T193-style offline installation with `--no-index` and `--no-deps`.
6. Recalculate the installed artifact digest and compare it with the approved
   digest. Preserve the installation log, evidence record and audit event.
7. Repeat negative cases: missing signature, missing provenance, stale evidence,
   wrong digest and changed artifact must all block installation.

## Phase 3 — Execute the T179/T229/T230 integration matrix

Use an isolated copy of the application DB and the installed gateway. Every
case must record request ID, provider, model, connection/account, HTTP result,
response ID, usage, reservation before/after, cost, durable state and audit
event. Secrets and prompt contents must not be recorded.

Required cases:

1. Successful OpenRouter, OpenAI, Gemini and Groq routes where the selected
   account/model is actually eligible.
2. Model not eligible, account unavailable, zero-cost requirement violated and
   insufficient context: reject before dispatch.
3. Success with trustworthy usage: settle once and release only proven unused
   capacity.
4. Missing usage, malformed usage, timeout after dispatch and cancellation after
   possible dispatch: retain conservative unknown reservation and do not replay.
5. Timeout before proven dispatch: release only the safe reservation.
6. Authorized fallback: reserve again, correlate attempts and account each
   consuming attempt. Local fallback must not replay an unknown external call.
7. User/global daily and monthly limits, 80% warning, overage, UTC rollover,
   provider/model quota and concurrent admission.
8. Memory-agent calls: permitted context, excluded guests, bounded input/output
   and accounting against the initiating user.
9. Restart worker and gateway during pending work; verify durable recovery and
   absence of duplicate dispatch.

3. Execute security boundary, recovery/unknown-outcome, resource-enforcement

## Phase 6 — Production deployment and acceptance

Only the already approved release scope may be deployed. Before deployment:

1. Record active service identity, queue state, DB digest and gateway contract.
2. Stop admission/worker and confirm no in-flight durable work.
3. Create and verify a closed-DB backup and SQLite integrity.
4. Apply migrations only after candidate checks pass.
5. Install the effective systemd wiring and start gateway-dependent services.
6. Run Django checks, migration dry-run, HTTPS/admin smoke, authenticated
   gateway contract and one application-level provider call.
7. Verify queue, reservation, usage and audit state.
8. Preserve rollback commands and pre/post digests. Do not claim acceptance if
   any gate fails.

## Phase 7 — Independent audits

Use a fresh context and the frozen release. Do not let the implementer approve
their own evidence. Produce three signed/dated reports:

- **Security/routing:** T179 and T226–T230.
- **Supply chain:** T231 and T193 integration.
- **VM/release:** T237, migration, recovery and production acceptance.

Each report must list inspected files/commands, artifact and release digests,
runtime results, missing evidence, exclusions and a verdict for every task:
`Closed`, `Open`, `Blocked` or `Insufficient evidence`.

## Closure rule

A task may be marked closed only when its implementation tests, applicable owner
authorization, target-VM evidence, deployment/acceptance evidence and required
independent audit all agree. Otherwise leave it open and record the exact next
evidence needed in the corresponding evidence file.
