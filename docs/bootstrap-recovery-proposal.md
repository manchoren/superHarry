# First-admin bootstrap and later recovery proposal

Status: independent draft for T008, not ready for completion while T003's environment proposal remains incomplete. G-SECURITY and G-OPS approval and OS-specific verification are required except for the limited MFA recovery decision recorded in [ADR 0003](adr/0003-lost-mfa-recovery.md). Constitution baseline 2026-10-29 SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. The accepted plan section 10.2 establishes the first-run baseline; this document proposes how to assess its recovery gap, without claiming implementation.

## First-run boundary

An authenticated OS administrator explicitly initiates bootstrap on an uninitialized installation. Generate a cryptographically random token of at least 128 bits, one active verifier at a time, valid for ten minutes and one redemption; issue it only on the authenticated terminal, never in arguments, logs, backups or model context. Redemption is limited to the separate loopback HTTPS setup listener, directly on the Pi or through authenticated SSH local forwarding; it is never proxied by the LAN listener. Replacing a token invalidates the prior verifier. Expiry, restart and successful creation invalidate it. Serialize concurrent attempts and atomically create at most one first admin while consuming its token. If a crash interrupts setup, inspect durable initialization state and fail closed; never permit a partial admin or second bootstrap.

The operating-system identity is separate from the application admin. An ordinary OS user, guest, sandbox, agent and remote unauthenticated peer cannot initiate the OS-admin operation or redeem through a non-loopback listener. Normal password, rate-limit and audit requirements apply. For headless use, forward to localhost over authenticated SSH. A public local CA certificate is transferred through an authenticated, integrity-verified channel, and its fingerprint compared against the OS session; verify the listener hostname and certificate rather than bypassing warnings. CA private keys remain protected and outside downloads. T011 must verify actual CA provisioning, trust stores, listener separation and rotation on the chosen OS.

## Later credential and MFA recovery

Once any administrator exists, bootstrap stays closed permanently until an explicitly approved reinstallation or separate destructive administrative procedure. Propose a separate local recovery operation initiated only by an authenticated OS administrator with explicit elevation. It identifies an existing target application administrator, records the request and outcome, and requires a new strong password through protected interactive input. On success invalidate that account's sessions and outstanding reset tokens atomically with the credential update; do not disclose the existing password, reset token or TOTP seed. Never permit the agent or an unauthenticated remote caller to initiate recovery.

The owner approved recovery of a lost MFA factor by an authorized operating-system administrator, with explicit confirmation, audit and mandatory new MFA enrollment; see [ADR 0003](adr/0003-lost-mfa-recovery.md). This approves the recovery outcome, not an implementation mechanism. Define how the operator proves OS-admin identity, the exact authority required, factor revocation and re-enrollment mechanics, notification, reauthentication, locking/serialization and audit behavior under G-SECURITY and G-OPS before implementing. If authorization, durable audit, secrets or integrity checks are unavailable, deny and preserve existing state.

Recovery operates on an existing account; it never creates a replacement administrator or deletes user data. Serialize with bootstrap and other recovery attempts. Stage changes, validate all prerequisites, atomically commit account credentials and revocations where possible, and recover after interruption by determining whether the commit occurred; do not expose a usable partial state. Where audit is in a separate store, design a durable fail-closed transaction protocol before implementation, without assuming cross-store atomicity. Notify the affected administrator through an approved mechanism only; no new messaging channel is implied.

## Required verification and decisions

T030/T031 must test no-admin and already-initialized states, ordinary OS user and remote denial, concurrent token creation/redemption, expiration and restart, interrupted commits, wrong TLS hostname/CA, old-token replay, role changes, lost MFA, session revocation and redaction. Test recovery audit failure and preserve existing usable state. Emulated ARM64 establishes functional behavior; HDMI, physical access and network recovery require real Pi testing. T003 must first complete and have its environment evaluated; T011 must specify HTTPS and service privileges. The OS privilege mechanism, recovery authorization details, token lifecycle for recovery, MFA recovery and enrollment mechanics, exact transaction design and confirmation interface remain proposals requiring approval. No recovery operation or security test was run.
