## Candidate: Debian Trixie AAVMF image

Debian lists [`qemu-efi-aarch64` 2025.02-8+deb13u1](https://packages.debian.org/trixie/qemu-efi-aarch64), sourced from edk2, as UEFI firmware for 64-bit ARM VMs. It is an architecture `all` package containing AArch64-targeted firmware, not a Windows executable. Its [file list](https://packages.debian.org/trixie/all/qemu-efi-aarch64/filelist) includes code and variable-store images, multiple Secure Boot variants, a combined firmware image, firmware descriptors, documentation and a snakeoil key. Do not use or treat the packaged snakeoil key as a trusted production credential. Choosing the exact matching code/variable pair, its size, variable store lifecycle, Secure Boot policy and host file permissions requires explicit review.

The [Debian download page](https://packages.debian.org/trixie/all/qemu-efi-aarch64/download) lists `qemu-efi-aarch64_2025.02-8+deb13u1_all.deb` with SHA-256 `a00b2411a79c8aeafd95a7c868ac3cd1aab592f1af9fff965f02d81a625276ed`. This is published metadata, not an independently verified artifact. Debian package authenticity should be established from a validated signed `InRelease` and its index chain, followed by the package checksum, while retaining and checking the key trust and revocation evidence. The existing guest snapshot must be checked for this exact version; a current package page cannot establish membership in an earlier snapshot. No package was downloaded or inspected here. A Windows-host workflow to extract individual firmware files from the archive would need a separately reviewed tool and safe extraction procedure; `.deb` architecture `all` does not itself prove compatibility with QEMU on Windows.

The [Debian copyright file](https://metadata.ftp-master.debian.org/changelogs/main/e/edk2/edk2_2025.02-8%2Bdeb13u1_copyright) declares BSD-2-Clause-Patent for general EDK2 and other notices including BSD-3-Clause and OpenSSL for specific sources. This source-wide file is a starting point, not an image-specific SBOM or completed redistribution review. Compare the actual binary package notices, included modules and upstream/downstream source patches before use.

The [Debian edk2 security tracker](https://security-tracker.debian.org/tracker/source-package/edk2) lists Trixie as fixed for several older issues, including CVE-2023-45236 and CVE-2023-45237, but lists CVE-2026-97631, CVE-2024-38798 and CVE-2024-13745 as vulnerable (`no DSA`). Debian's source-package status is not a proof of reachability in a specific AArch64 image; investigate affected modules and patches, actual device/network/boot configuration, and updated advisories. A newer maintained source does not establish that all risks are resolved.

[QEMU's ARM virt documentation](https://www.qemu.org/docs/master/system/arm/virt.html) specifies that `virt` supports flash and requires selecting a 64-bit CPU for an AArch64 guest. The presence of Debian QEMU firmware descriptors is evidence of intended integration, not proof that the exact Debian images boot with QEMU 11.1.3-1 on Windows or that the descriptors' paths work there. The owner selected a fresh writable copy of the bundled VARS template per VM session as the rollback design. VM disks and state will be kept under repository-root `.dev-vm/`, ignored by Git and not guest-shared, with explicit Windows ACLs for the current user, SYSTEM and local Administrators only. Discard the overlay and writable VARS after normal QEMU exit; retain abnormal-exit artifacts until explicit cleanup, only after confirming QEMU has exited and released its files. Intentional baseline updates will be rebuilt from pinned instructions and sources rather than promoted from an overlay. Implement and verify `.dev-vm/` ACLs, VARS creation, permissions and reset behavior. Verify firmware code, flash geometry, CPU, device graph, network-boot policy and VM boot only after approved environment and dependency decisions. Neither Pi hardware equivalence nor Secure Boot isolation follows from an emulated boot.

## Alternatives and decision

- **Bundled MSYS2/QEMU images:** provisionally selected by the owner as the design candidate for continued review; they match files in the QEMU 11.1.3 source tree, but their recorded EDK2/OpenSSL provenance, licensing and advisory exposure remain open. Candidate selection is not approval or acceptance merely because they are bundled.
- **Debian AAVMF candidate above:** separately maintained distribution source and identifiable package/checksum, with open advisories and cross-platform extraction/boot questions. It adds an external artifact and requires G-ARCH/G-OPS approval.
- **Reproducible custom build:** potentially permits a narrowly scoped module set and fresh source, but exact EDK2 commit, compiler/build tools, patches, reproducibility, notices, provenance and maintenance would all need review and approval. No build inputs or commands are approved.

Before any approval, obtain current signed artifact metadata, review applicable advisories and licenses, document how the candidate is updated and reproduced, and assess a concrete configuration and residual risks. Revisit an external candidate if a blocking issue is identified, and obtain scoped G-ARCH/G-OPS approval before acquisition or execution. This provisional design selection is not security acceptance and has not established independent key trust, actual module composition, artifact integrity or boot compatibility.

## CVE-2026-97631: upstream patch and exposure conditions

As of 2026-10-30, TianoCore's [GHSA-99cj-7hg9-mp4m](https://github.com/tianocore/edk2/security/advisories/GHSA-99cj-7hg9-mp4m) describes corruption in `NetworkPkg/UefiPxeBcDxe` during IPv4 or IPv6 PXE boot when an unauthenticated attacker can deliver an ICMP error to the client. The vulnerability can affect pre-OS execution. The advisory lists EDK II master as of 2026-09-14 as affected and states that no patched version is currently listed. Its linked [PR #13302](https://github.com/tianocore/edk2/pull/13302) merged on 2026-10-15 and describes boundary and offset fixes plus unit tests. This establishes an upstream change, not that Debian sid `2026.08+ds-2` or either candidate AArch64 image incorporates it; [Debian's tracker](https://security-tracker.debian.org/tracker/CVE-2026-97631) must be refreshed at selection time.

For the proposed local VM, excluding network boot and preventing firmware from receiving untrusted network traffic are candidate exposure reductions consistent with the advisory's conditions. Merely placing the disk before PXE in boot order is insufficient evidence: a failed or missing disk, interactive boot selection, persistent firmware variables or configuration changes may still trigger another boot path. Before claiming protection, inspect whether the exact firmware image contains the module; specify and test the complete device, boot and writable-variable configuration and every fallback path, including disabled NIC or enforced pre-boot isolation where feasible. Verify that later guest networking and required installer access remain possible under separately approved operations. No configuration was applied, no module inventory or negative test was performed, and this proposal does not establish that the candidate is safe or patched. A patched, authenticated and maintained image remains the preferred candidate subject to normal G-ARCH/G-OPS review.

## RPM signature-header inspection (2026-10-30)

The Koji `-16` RPM was downloaded again over HTTPS and its SHA-256 matched the previously observed `46c7e2a3d8c13d016a75b23c55d7d1a77d8252a398cdc7dc7f06360e5cf6cd5b`. A read-only inspection using Python's standard `struct` module of the RPM signature-header index reported tags `62, 269, 273, 1000, 1004, 1007, 1008`; none of the documented version-4 RSA/DSA header-signature tags `268`/`267` or legacy PGP/GPG tags `1002`/`1005` appeared. [RPM's v4 format documentation](https://rpm.org/docs/6.0.x/manual/format_v4.html) identifies tag 1008 as reserved space, not a signature, and describes those signature tags. This is preliminary evidence that this particular Koji download lacks the conventional v4 package signature, not a cryptographic verification or proof about any other Fedora artifact. The inspection did not validate RPM structures through the RPM library, which the specification explicitly recommends; no RPM verifier is installed on this host. Hashes and HTTPS transport alone do not authenticate a package.

[Koji's signing documentation](https://koji.readthedocs.io/en/latest/signing.html) explains that Koji retains unsigned RPMs and stores imported signatures separately. Search for a signed copy in a signed Fedora repository or Koji signed-artifact path and verify it with an approved RPM verifier and independently trusted Fedora key. Do not treat a signature-header observation as approval or select this artifact for use. No package was installed or executed. The temporary download was removed after inspection.
