## Accepted policy and current boundaries

These are existing requirements from the constitution and project plan, not new decisions introduced by this proposal:

- Network configuration and credential changes are administrative actions through the authenticated web app. Only an authenticated superHarry administrator may make them; the OS administrator and superHarry administrator are separate identities. Authentication, current role/session checks, reauthentication, confirmation, revocation and mandatory audit follow T007 and the constitution. Guests, ordinary users, linked channels, runtime agents and sandboxes do not gain this capability.
- The native service direction has a dedicated unprivileged API identity and a separate, restricted network broker. The API reaches the broker over an access-controlled Unix-domain socket; the broker checks its OS peer and accepts requests only from the API service. The broker does not expose a general command, shell, path, host-control or arbitrary NetworkManager interface. T011 has not selected exact identities, UIDs/GIDs, socket ownership, privilege mechanism, or internal authentication contract.
- The defined operations are: list available Wi-Fi networks; view Ethernet and Wi-Fi status; connect to an administrator-selected WPA2/WPA3-personal Wi-Fi network; and configure DHCP for Ethernet or Wi-Fi. Other network types and static IP settings are unsupported. Credentials use OS-managed, access-restricted storage; they must never be exposed to a model, logged, copied to application storage, or included in downloadable backups.
- A disruptive change uses a NetworkManager checkpoint, with a 120-second rollback deadline where supported, and is committed only after confirmation through a still-authenticated admin session. If the checkpoint or persistence cannot be made safe, reject the mutation and offer authorized OS-level recovery. Verify persistent configuration after restart or retain the prior configuration.
- Connectivity status distinguishes local link/network access from Internet availability. Internet loss does not invalidate a functioning local network. Preserve local-model operation, show the localized offline/local-model indicator on web and HDMI, and reconnect only with administrator-configured profiles without changing settings or inventing credentials. Increase retry intervals gradually up to five minutes and reset after verified connectivity.
- Without Wi-Fi, recovery uses the local HDMI path or Ethernet with a preconfigured, authenticated OS remote-access method. Do not enable an open setup access point or default credentials. The ordinary app remains LAN/VPN-only with no public exposure or router/public port forwarding; a local broker socket is not an exposed network listener.

The accepted operation set is intentionally narrow. Authentication rules for read-only network information, DHCP address-family policy, exact retry intervals, and the precise reachability test are not settled by these requirements.

### Proposed read-only discovery and acceptance evidence

The following is a proposed evidence procedure, not a finding about the selected image. A package list, a running NetworkManager process, or generated Netplan files alone do not identify a sole authority. Distinguish the **runtime device controller** from the **persistent configuration owner**; a renderer may control a device at runtime while another layer owns the persistent source.

1. Establish the exact artifact and installed OS identity first. Record the authenticated image digest and OS release, then inventory installed package versions, enabled and active network-related services, NetworkManager's D-Bus service owner if present, and available manager status interfaces. These observations identify candidates, not authority.
2. For each Ethernet and Wi-Fi interface, record whether it is managed, which component currently controls link/association/address state, and whether more than one daemon or service can write or reconfigure it. Inspect effective renderer/backend selection and trace persistent settings to their originating source, including Netplan YAML and generated/cloud-init inputs where present, NetworkManager profiles/plugins, and any `dhcpcd` or `wpa_supplicant` configuration that is active. Identify generators, symlinks, drop-ins and boot-time reapplication that can overwrite runtime changes. Do not copy secrets into the evidence record.
3. Produce a per-interface evidence record with image identity, package/service versions and states, runtime controller, persistent source and writer, renderer, competing writers, relevant version-matched documentation, and unresolved behavior. Mark a single authoritative runtime controller and persistent owner only when the evidence agrees; otherwise classify the interface as ambiguous and mutation-disabled. Do not select a manager based on package presence, preference, or an unverified assumption.
4. Before proposing a mutator for any interface, demonstrate read-only discovery is repeatable after reboot and that the identified owner actually supplies effective settings. G-OPS/G-SECURITY must separately approve any state-changing test. If evidence shows multiple active authorities or generated state that cannot be safely reconciled, stop and retain authorized OS-level management rather than adding, disabling, or reconfiguring a manager.

**Feasibility disposition:** official sources document NetworkManager checkpoint APIs, Netplan's separate timeout-based `try` behavior and caveats, and the selected Raspberry Pi OS candidate's published packages/configuration direction. This supports candidate investigation, not safe implementation feasibility. Target-specific platform feasibility—exact authenticated image, per-interface runtime controller and persistent owner, and approved restart/crash recovery evidence—is deferred to T169; until then, do not install Netplan, add a manager, or overwrite another configuration source as a workaround.

## Proposed broker and peer-identity design

The following is proposed detail for G-OPS/G-SECURITY review, coordinated with T011's API/broker separation and T011's LAN/VPN/firewall boundaries:

1. Keep the broker local-only and expose one permission-restricted Unix **stream** socket. Do not add a TCP listener, firewall exception, public/VPN route, or listener through Caddy. Filesystem permissions on both the socket and its containing directory admit only the intended API service identity and broker/OS administration; exact owner, group, mode, ACL and systemd sandbox settings await T011/G-OPS.
2. At each connection, verify Linux kernel peer credentials (`SO_PEERCRED`) and require the one explicitly approved API service UID. The [unix(7) documentation](https://man7.org/linux/man-pages/man7/unix.7.html) states these credentials identify the process at connection time, not the end user. Socket ACLs and peer credentials are complementary; neither proves that the human requester is an administrator.
3. The web/API layer authenticates the session, checks current admin authorization and applicable T007 reauthentication/one-use confirmation, and audits the request. It submits only a bounded assertion and operation data to the verified API peer's broker connection. The broker accepts no direct guest, user, channel, agent or sandbox request. The assertion format, integrity protection, replay handling, API/broker contract and audit transaction are not yet selected; G-CONTRACT/G-SECURITY approval is required. Do not claim that `SO_PEERCRED` validates the end-user assertion or protects against API compromise.
4. The broker parses a versioned, size-bounded schema; allowlists operation names, managed device identifiers and required fields; rejects duplicate/unknown fields and invalid encodings; serializes mutations; and applies finite deadlines. It invokes only the selected backend's documented, narrowly required methods. Never interpolate input into a shell, accept arbitrary D-Bus method names/settings maps, or permit arbitrary files, plugins, routes, DNS, interface modes or commands.
5. Restrict credentials to the WPA2/WPA3-personal connect operation. Send them only over the local protected socket into OS-managed storage, minimize their in-memory lifetime, and ensure responses, exceptions, diagnostics and audit records contain no credential values. Do not return or duplicate stored credentials. If the OS cannot satisfy this handling or a secure mutation audit cannot be written durably, reject the operation.

**Allowed mutation data:** a selected managed Wi-Fi device, selected SSID from a fresh scan or explicit administrator selection, one supported WPA2/WPA3-personal credential, and DHCP-only connection configuration for managed Ethernet/Wi-Fi. DHCP family/dual-stack behavior must be explicitly approved. Listing scan results and reporting link/association/address status do not authorize any settings mutation.

**Fail-closed exclusions:** open or enterprise Wi-Fi, WEP, access-point/hotspot creation, static IPv4/IPv6, static routes, user-supplied DNS, bridges, bonds, VLANs, VPNs, proxies, arbitrary device control, changing the active network manager, and any unrecognized operation or authentication mode. On an unsupported or ambiguous backend, unmanaged/conflicting device, unknown setting, missing capability, malformed request, privilege mismatch, unavailable required audit, or failed persistence preflight, return a structured failure without mutation. No automatic fallback to shell commands or direct file edits.

## Proposed 120-second transaction and reachability checkpoints

The following is a proposal, not a claim that the selected OS implements these semantics. NetworkManager's checkpoint timer and Netplan's `try` timeout are separately documented rollback mechanisms, not a shared transaction coordinator. Do not start both and assume they cover each other's state: choose one version-matched owner for runtime rollback and one explicit persistent commit/restore protocol, then demonstrate that they agree across failures.

The design uses an explicit 120-second NetworkManager rollback checkpoint, not an assumed tool default. Treat the 120 seconds as the total transaction window from before the first state-changing action through verified persistent/runtime commit. Create the checkpoint before applying a candidate and cover every affected device; no persistent candidate write may precede it unless the selected backend demonstrably includes that write in the same recoverable window. Same-session confirmation, persistent commit and verification must finish before the deadline. Exact API call, flags and timeout semantics must be verified against the installed NetworkManager version. Do not extend the deadline to hide a slow or uncertain commit. If a valid checkpoint cannot be created, monitored or kept valid through commit, reject the mutation.

1. **Authorize and preflight.** Require the authenticated administrator's current web session, the action confirmation required by T007, and a durable redacted audit intent before side effects. Serialize changes. Identify exactly one authoritative manager and persistent source for each affected device; check that the backend can stage a candidate, restore the previous persistent and runtime states, and recover interrupted transactions. Refuse before mutation if any source of truth, checkpoint, audit sink, or restoration capability is unknown or unavailable.
2. **Prepare without an application-side secret shadow.** Create a durable transaction record with a random transaction ID, actor/session references, selected device, operation class, checkpoint deadline, backend identity and state (`prepared`). It contains no Wi-Fi credential. Preserve the prior configuration through the selected OS/backend's protected rollback mechanism, not an application copy or downloadable backup. Prefer an OS-supported pending/runtime-only stage that leaves prior persistent state intact until confirmation. If the actual backend cannot stage and later commit safely, or cannot restore persistent state without an application-held credential copy, disable the operation.
3. **Apply and check at bounded intervals.** Create the 120-second NetworkManager checkpoint, then apply only the requested change. Re-check at each state transition: Ethernet carrier or Wi-Fi association; assigned DHCP address and required local route; then reachability of the authenticated web/API session through the admin's current approved access path (LAN/VPN or approved local HDMI UI). Check again immediately before confirmation. Do not treat association, DHCP, a public Internet response, or a broker response as proof that the administrator can still reach the service. A local-network or service reachability test must be approved and privacy-preserving; no public probe is implied. If an address/route change breaks the current session, that session cannot confirm, so the change rolls back.
4. **Confirm before deadline.** The same still-authenticated admin session must receive the result and explicitly confirm the exact actor, device, operation and configuration before the 120-second deadline. Recheck session validity, authorization, confirmation freshness and unchanged transaction state. No confirmation, session loss/expiry, timeout, DHCP/association failure, loss of required admin reachability, cancellation, audit failure or any backend error causes rollback. There is no confirmation through an unauthenticated endpoint, channel, agent or stale/replayed token.
5. **Commit both state layers before expiry.** After valid confirmation, commit the candidate to the backend's one authoritative persistent source and reconcile the live NetworkManager state while the checkpoint remains valid. Record commit progress in the durable journal before each non-atomic boundary. Re-read the persistent source and compare it with the intended live profile; mark `committed` only when both agree and the backend's documented restart/persistence behavior has been validated, all before the same 120-second deadline. If the commit cannot finish inside the window, roll back rather than extend the checkpoint or report success. T011/T007 contract and audit transaction details remain approval items. A partially completed commit is not success.
6. **Rollback and interruption recovery.** On any failure or missing confirmation, invoke NetworkManager rollback and restore the prior persistent source using the backend's protected transaction mechanism, then verify both runtime and persistent state. On broker, NetworkManager or host restart, inspect the durable journal and roll back every non-committed transaction; never assume a NetworkManager checkpoint survives a daemon or host restart. Validate the recovery path before enabling changes. If either state is uncertain or rollback fails, stop further mutations, preserve the redacted journal/audit evidence, report a distinct recovery-required state, and require authorized OS-level recovery. Never silently erase the failure or report success.

### Offline and interrupted-transaction invariants (proposal)

- Use at most one network mutation transaction at a time. Persist a redacted journal with explicit phases such as `prepared`, `applying`, `awaiting_confirmation`, `committing`, `committed`, `rolling_back` and `recovery_required`. Record intent before each non-atomic side effect and durable completion afterward. The journal stores transaction identity, device/backend identifiers, deadline, prior-state reference and progress, but no Wi-Fi credential or secret-bearing configuration.
- Start the rollback deadline before the first disruptive side effect. Its enforcement and rollback path must be local and independent of browser connectivity, the API request lifetime, Internet access and the remote administrator session. Only the same still-authorized session may confirm; losing that session means no confirmation and therefore rollback at deadline. Do not treat a disconnected browser or an unavailable Internet check as a successful commit.
- Prefer a candidate runtime change while the previous persistent configuration remains intact until confirmation. If a backend necessarily persists before confirmation, it must provide an OS-controlled, access-restricted, recoverable copy of the exact prior state, including credential references, without placing secrets in the application journal or downloadable backups. If it cannot, reject the mutation.
- Startup recovery must inspect any nonterminal journal and restore the last confirmed state before accepting another mutation; where a candidate may be re-applied at boot, restore must happen before the network manager consumes that candidate. Recovery must be idempotent across repeated crashes. If this ordering cannot be guaranteed on the target, leave the operation disabled.
- Treat live checkpoint rollback and persistent-file restoration as separate compensating actions. A journal or checkpoint does not make separate writes atomic. Do not mark `committed` until both the one authoritative persistent source and effective live state have been re-read and agree, audit/journal completion is durable, and the backend's restart behavior is documented and validated. Any uncertainty becomes `recovery_required`; preserve the prior state and require authorized OS-administrator recovery rather than reporting success.
- A loss of Internet alone does not trigger a configuration change or invalidate a healthy local session. The recovery path must not depend on public reachability probes. If neither HDMI with normal admin authentication nor the preconfigured authenticated OS remote-access path is available, rollback still proceeds locally; OS-level intervention is only needed if rollback cannot be verified.

For each supported backend, test that persistent state survives the approved service/system restart, and that recovery restores the old state after process, NetworkManager and host interruption at every write boundary. In particular, heed Netplan's documented caveat that `netplan try` timeout/cancellation may not actually revert the network and that the on-disk configuration must be checked before reboot; do not treat timeout alone as rollback evidence. If a safe transaction requires a restart that would prevent same-session confirmation, or if the selected backend cannot provide demonstrated crash-safe restore, the affected operation stays disabled. A checkpoint alone is not transactional persistence.

## Offline behavior and authorized recovery

- Keep the local model available regardless of Internet status. Report separate link, Wi-Fi association, DHCP/local-network, authenticated web-service reachability and Internet-status signals where available; do not infer Internet availability from link or DHCP. The exact Internet probe or other verification method needs approval and must not send secrets or content.
- Automatic reconnection may activate only existing administrator-configured profiles, with no credential prompts, settings edits, new profile creation, or broker privilege escalation. Increase retry delay gradually to a maximum of five minutes and reset only after the approved connectivity check succeeds. Exact intervals and the definition of verified Internet recovery remain owner decisions.
- With HDMI, present the accepted local network-recovery options and Ethernet status, but retain normal superHarry admin authentication for every mutation. Do not create an offline auth bypass. T011/T008 must settle how the local interface remains reachable and TLS-trusted when DHCP or the LAN route is unavailable; the bootstrap listener is not repurposed as a general network-management bypass.
- Headless recovery uses Ethernet and a preconfigured authenticated OS remote-access method, as the plan specifies. A failed or unconfirmed network transaction rolls back without requiring Internet access. If that path is unavailable or rollback cannot be verified, use an authorized OS administrator at the local console or the separately approved authenticated OS recovery channel. No open access point, default credential, public listener, router forwarding or unauthenticated broker mode is allowed.
- Keep transaction recovery state and mandatory redacted security audit locally durable through offline periods. Failure to durably record audit intent blocks new mutations; loss of remote connectivity is not a reason to disable audit or weaken authorization.

3. **Operations proposal:** once the inventory identifies a coherent backend, present the owner a concrete G-OPS/G-SECURITY proposal covering supported devices and DHCP address families, socket and service identities, privilege and secret handling, management access and reachability checks, reconnection schedule and transaction recovery. Present the API/broker assertion, confirmation, journal and audit boundary under the applicable G-CONTRACT gate as well. Clearly mark each selection as proposed until explicitly approved.
4. **Validation authorization and evidence:** prepare a reversible, isolated test plan with failure injection and a known OS-admin recovery path before requesting the approvals needed for network mutation and service changes. Record image identity, operation, expected and observed live/persistent state, restart boundary and redacted result for each case. Do not infer hardware support or physical isolation from emulation. Failed or missing cases block the affected operation.

At each step, an unavailable image or unresolved choice is a blocker with a named next action, not an implicit selection. The checkpoint and persistence evidence must show both successful commit and restoration of the previous configuration after failed or interrupted changes; a package list or a documented D-Bus method alone does not satisfy that requirement.
