# Network provisioning and offline recovery proposal

Status: T012 preliminary design, 2026-10-30. T011 and T007 are not formally complete, and the selected OS and environment remain unresolved. This document is not approval or evidence of implementation, network safety, emulation or hardware testing. Constitution baseline 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. The [constitution](../constitution.md) and [plan section 10.2](../project_plan.md#102-authentication) prevail. G-OPS and G-SECURITY decisions, contract and dependency approval remain required.

## Feasibility and unresolved platform facts

[NetworkManager's D-Bus API](https://networkmanager.dev/docs/api/latest/gdbus-org.freedesktop.NetworkManager.html) provides checkpoint operations, and its [checkpoint flags](https://networkmanager.dev/docs/libnm/latest/libnm-nm-dbus-interface.html) include deletion of new connections on rollback. Per-device rollback can fail or encounter missing/unmanaged devices; a checkpoint alone does not prove persistent storage and restart recovery are safe. The intended rollback deadline is explicitly 120 seconds, not a tool default. Assess actual installed version, devices, flags and behavior in the approved emulated ARM64 image and real Pi before enabling an operation.

[Netplan's NetworkManager integration](https://netplan.readthedocs.io/en/stable/netplan-everywhere/) documents a Netplan persistence backend on Ubuntu Desktop 23.10 and later; [NetworkManager's configuration reference](https://www.networkmanager.dev/docs/api/latest/NetworkManager.conf.html) says settings plugins and write ordering vary by distribution. This does **not** establish that Debian ARM64 or Raspberry Pi OS uses Netplan, which backend is active, or whether it provides atomic restoration. Inspect the actual approved image and profile ownership. Do not add Netplan or overwrite another source of truth without G-ARCH/G-OPS approval. If the backend cannot demonstrate restore of both persistent and runtime state, reject the affected mutation and offer authorized OS-level recovery.

## Authority and narrow interface

Only an authenticated administrator, through the web API, can request network configuration or credentials changes. Propose a separate local broker under a dedicated OS identity, reachable through a permission-restricted Unix stream socket. The API account alone can connect; the broker checks kernel-provided peer credentials with `SO_PEERCRED` in addition to filesystem access controls. Linux documents that these credentials reflect those at connection establishment ([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)); they identify the local process, not the end user. The API must authenticate the session, enforce admin role and current authorization, bind request and confirmation to that session and audit the operation. The broker trusts a bounded admin assertion only from the verified API peer and revalidates its operation and data; it must not accept direct guest, agent, sandbox or channel requests. Confirm trusted UID, service permissions and OS policy under G-SECURITY/G-OPS. Kernel credentials alone cannot protect against a compromised API service.

Allow only predefined operations: list available Wi-Fi networks; report Ethernet/Wi-Fi status; connect to an admin-selected WPA2/WPA3 personal network; configure Ethernet or Wi-Fi for DHCP. Validate device identity, mode, required fields and bounded input. Do not pass input to a shell or accept arbitrary D-Bus calls, raw profile maps, paths, options or commands. Reject enterprise Wi-Fi, access point creation, static addressing, VPN configuration and other unsupported operations. Authentication requirements for read-only network information and exact request schemas remain open; deny by default. Wi-Fi credentials transit only protected channels to OS-managed access-restricted storage; never return stored secrets, expose them to models, log them, duplicate them in application data, or include them in downloadable backups. Define ownership, OS secret-agent behavior, backups and privileged audit before implementation.

## Proposed transaction and recovery

1. Serialize network mutations; require a live authenticated admin session, a bound one-use confirmation and durable redacted audit intent before side effects. Validate selected managed devices and detect conflicting configuration writers. Refuse if capabilities, audit, checkpoint creation or a restorable persistent baseline are unavailable.
2. Create the NetworkManager checkpoint covering every affected device with an explicit 120-second rollback timeout and review appropriate flags. Prove that the affected persistent source of truth is recoverable without the API or broker persisting a second copy of Wi-Fi credentials, and without placing credentials in downloadable backups, general logs or application storage. The OS-managed mechanism, protection, cleanup and crash consistency remain design and approval gates; reject the mutation if those requirements cannot be met. Test configurations in temporary state where the backend actually supports this; do not assume the backend will avoid persistent writes.
3. Apply only the validated operation. Check actual link and DHCP state separately from Internet reachability. Local network success does not require public Internet. Do not claim connectivity solely from association or an unverified probe; exact privacy-preserving probe destination and semantics require approval. If the requester loses the session, timeout, verification fails, or any write fails, trigger rollback and verify results rather than claiming success.
4. The admin must confirm through a still-authenticated session before the checkpoint expires, bound to the same actor, target and proposed configuration. No unauthenticated or stale confirmation succeeds. Before discarding the checkpoint, reconcile the selected backend's persistent state and verify consistency with the live profile, ensuring recovery of both is demonstrable. Any failed operation or interruption triggers reconciliation to the previous verified state; if state is uncertain, fail closed, preserve evidence and require authorized OS-level recovery. Do not mark success if restoration or persistence cannot be verified.
5. On broker or system restart, recover or roll back from a durable transaction record without logging credentials; do not assume NetworkManager checkpoints survive its own restart. Define the crash-safe commit protocol, recovery journal, secret storage and atomicity across the OS backend and audit store before implementation. Verify persistence by an approved restart test; if this cannot be guaranteed, keep the affected operation disabled. Report rollback failure distinctly and never silently erase it.

Automatic reconnection uses only existing admin-configured profiles and never modifies credentials or network settings. Retry with increasing intervals capped at five minutes; reset backoff only after verified connectivity. Keep local model operation available and distinguish network link, local access and Internet status. Present the localized offline/local-model indicator on web and HDMI. Without Wi-Fi, local authenticated HDMI access or Ethernet plus a preconfigured authenticated OS remote-access method provides recovery; no open setup access point or default credentials. TLS trust and the loopback-only bootstrap path follow T011 and T008, not this proposal.

## Decisions and tests

G-OPS/G-SECURITY must settle selected OS backend, broker identity and polkit/D-Bus permissions, durable journal and secret protection, atomic rollback/persistence protocol, connectivity probes and session/confirmation behavior. Versioned dependencies and public/internal contracts need their own approvals. Do not implement or enable configuration changes until prerequisites and applicable gates are satisfied.

T033/T034 should test socket ACL and peer spoof attempts, unprivileged/guest/channel/agent denial, session expiry, stale or replayed confirmations, malformed and unsupported settings, overlapping changes, unavailable audit, wrong WPA credentials, DHCP failure, no Internet with healthy LAN, cancellation and checkpoint expiry. Inject failure and process/NetworkManager/system restart at every persistence boundary; verify previous runtime and persistent state, profile secrets, audit redaction, rollback failure reporting and authorized recovery. Test IPv4/IPv6 behavior and reauthentication across network transitions. ARM64 emulation covers functional behavior only; repeat real Wi-Fi, Ethernet, HDMI, physical isolation and restart acceptance on the Pi under T156. No tests have been executed.
