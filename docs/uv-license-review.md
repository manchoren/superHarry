## Candidate method to obtain an artifact-specific inventory

Publisher confirmation of an SBOM tied to the archive digest is the preferred evidence; request its provenance and verify the subject before relying on it. If unavailable, a separate approved investigation can capture the build's exact Cargo toolchain, target, feature flags, profile, environment, build-script inputs and native libraries, then compare a reproducible output digest against the attested upstream archive. A digest mismatch does not identify which components differ and cannot establish equivalence; request publisher build records or other provenance in that case. Review build-time tooling separately from material included in the distributed executable.

The official [Cargo metadata reference](https://doc.rust-lang.org/cargo/commands/cargo-metadata.html) explains that `--filter-platform` narrows the resolved graph but does not filter the `packages` array; counting that array as the ARM64 binary inventory would be incorrect. The [Cargo tree reference](https://doc.rust-lang.org/cargo/commands/cargo-tree.html) supports target filtering and feature inspection but explicitly says its graph does not guarantee exact equivalence with a build. Both are supporting evidence, not proof of the linked artifact. Build scripts and native linking require separate inspection; verify source and license text for each component and record unresolved evidence. These operations may require fetching dependencies or running builds and remain subject to the applicable toolchain, network and environment approvals.
