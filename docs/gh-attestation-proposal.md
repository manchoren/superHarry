## Proposed controlled process

1. Obtain approval for the exact temporary verifier and review its provenance and notices; no system installation, PATH changes, package manager or persistent configuration is proposed. Download only official exact ZIP and checksum file to an isolated temporary directory, verify recorded digest and independently authenticate provenance using an already trusted method. A checksum or GitHub-hosted attestation alone does not bootstrap trust independently; verifier provenance must be resolved before execution.
2. Fetch the exact uv archive and confirm its digest. Review the expected repository, workflow, source commit and ref from the official release and source separately. Do not derive the expected policy solely from the unverified attestation. GitHub's [verification manual](https://cli.github.com/manual/gh_attestation_verify) documents `--repo`, `--signer-workflow`, `--source-digest` and `--source-ref`; use exact reviewed values for all applicable options. The expected workflow/commit/ref are not yet established here.
3. Subject to approval and the preceding validation, run a command of this shape with reviewed literal values: `gh attestation verify <uv-archive> --repo astral-sh/uv --signer-workflow <reviewed-workflow> --source-digest <reviewed-source-commit> --source-ref <reviewed-source-ref> --format json`. Angle-bracket terms are placeholders for reviewed values, not an executable command. Require a successful cryptographic result matching the expected subject digest, identity and provenance. Save only redacted evidence. No uv binary is executed.
4. The prior unauthenticated GitHub API request for this subject returned HTTP 401. Online verification may therefore need authenticated GitHub access, but no account or token availability has been established. Do not create, print, transmit or store credentials in repository or evidence; use the user's existing authorized authentication only if available. Alternatively, an authenticated party may supply a bundle for [offline verification](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline) with a separately validated trusted root. A bundle is untrusted until cryptographically verified and matched to the expected identity. Do not assume offline verification removes the need to authenticate the root.
5. Remove only the isolated temporary artifacts after review, subject to filesystem safety checks. Report failures instead of weakening identity constraints. A verified attestation establishes provenance for the verified subject under the trust policy; it does not prove the executable is safe, compliant with licenses or functional on ARM64.
