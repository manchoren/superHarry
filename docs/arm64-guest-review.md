Status: T003 research, 2026-10-30. Constitution baseline 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. This is not an approved environment, a verified image, or evidence of a successful boot.

## Candidate and image authentication

The [official Debian installer page](https://www.debian.org/releases/stable/debian-installer/) identifies Debian 13.7 `trixie` and links an ARM64 netinst image at `https://cdimage.debian.org/debian-cd/current/arm64/iso-cd/debian-13.7.0-arm64-netinst.iso`. The `current` path can change; preserve the exact version, release media and signed metadata when a candidate is selected. The page says checksum files are available alongside the image. An installer is not a locked guest filesystem: package selection, network repositories, firmware and installer settings affect its output.

Debian's [image authenticity instructions](https://www.debian.org/CD/verify) specify verifying the signed checksum file using its Debian CD signing key and then comparing the image's own checksum. The official page lists multiple keys; select the actual signature's key and establish key trust with an independently verified Debian keyring and fingerprints. Record signature result, key fingerprint, revocation/trust evidence, exact checksum-file digest, ISO digest and location. A checksum read from the same source without a trusted signature establishes consistency, not authenticated provenance.

The browsing tool initially reported a restricted URL/robots and a timeout for these sources; these were ordinary tool access failures, not automatic approval rejections. PowerShell's request to the Belgian mirror failed TLS trust. A subsequent `curl.exe` request to the official `cdimage.debian.org` host succeeded without disabling TLS. Its `SHA256SUMS` lists `debian-13.7.0-arm64-netinst.iso` as `6e93fa1759bd9d4b0fc11e938987de6967ee7de5297dac1be27c3a75cc17024b`; the checksum file itself has SHA-256 `6f768053b16f25cd8de528fc716bcbd43a365e70b44a09cb02d86e24cc2f7618`.

The detached checksum signature was verified with `gpgv`, exit 0, against the Debian CD public key downloaded from the [official Debian verification page](https://www.debian.org/CD/verify) using the fingerprint `DF9B9C49EAA9298432589D76DA87E80D6294BE9B` listed there. This verifies the metadata signature against that key and its correspondence with the official page, not an independently established web-of-trust or revocation check. The 701.2 MiB ISO was subsequently downloaded over TLS from the official current release URL, hashed locally using SHA-256, and matched the verified checksum `6e93fa1759bd9d4b0fc11e938987de6967ee7de5297dac1be27c3a75cc17024b`. The temporary ISO was removed after verification; no boot or install is claimed. The checksum file, signature and public key were retained temporarily under `superharry-debian-metadata` for audit, and no private keys or credentials were used.

## Snapshot and reproducibility

[Debian Snapshot](https://snapshot.debian.org/) provides dated copies of the main and security archives; it documents that requests for a timestamp not actually imported resolve to the latest available import before that time. Record the actual import timestamps separately for `debian` and `debian-security`, suite/component/architecture, signed `InRelease` or `Release` and signature, trusted archive keys, and exact hashes of authenticated indexes and selected packages. A time alone is not a package lock. Define package sources, bootstrap tools, exact installation inputs, artifact retention, dependency closure and license/security review before requesting G-ARCH/G-OPS approval.

Snapshot documents that historical `Valid-Until` metadata can be expired and provides a per-source override. That weakens freshness/replay protection: do not disable freshness checks globally or silently. Any proposed use must be restricted to the exact pinned, authenticated snapshot, recorded and separately reviewed with a policy for security updates and re-approval. Verify the selected snapshot's actual archive metadata and package availability, including the security archive; do not assume historical content is currently patched. Rebuild from a clean snapshot and record both exact inputs and resulting package inventory after approval.

## Emulator and target boundaries

The candidate is generic Debian ARM64 on QEMU `virt`, not Raspberry Pi OS or Pi hardware. CPU, UEFI firmware/variable store, machine type, virtual disks, networking, installer choices and their exact versions require separate selection and G-OPS review. See [environment proposal](../environment_proposal.md). Record differences in kernel, firmware, desktop, device and package configuration against the chosen Raspberry Pi OS image. An emulated smoke test cannot establish HDMI/GPU, thermal behavior, physical isolation or Pi performance.

## Signing-key cross-check (2026-10-30)

Debian's [verification instructions](https://www.debian.org/CD/verify) recommend validating the CD key using the Debian keyring and web of trust. Over TLS, the separately hosted [Debian keyring service](https://keyring.debian.org/) returned the key by full fingerprint. `gpg --show-keys --with-colons --fingerprint` reported `DF9B9C49EAA9298432589D76DA87E80D6294BE9B` and the Debian CD signing identity, agreeing with the verification page and checksum signer. This cross-check uses two Debian-operated services and is not an independently authenticated web-of-trust. The current returned key had no key-revocation packet detected in a packet listing; this is not proof that no revocation exists elsewhere or that the response is fully fresh. Certification validity and the trusted-keyring chain remain unverified. `gpg --show-keys` created a default `trustdb.gpg` on the host; it did not import the key into the default keyring.

A second public key service returned the same 64-bit key ID within a primary-key packet but no usable identity output under `gpg --show-keys`; we did not treat this as an independent fingerprint, certification, revocation or owner-identity verification. Before final trust, use an already trusted Debian role keyring with independently validated origin and current revocation information, verify the relevant certification chain, and document the assessment. Do not equate the mathematically valid detached signature with fully established key trust.

## Effective snapshot timestamps (2026-10-30)

Debian Snapshot documents its [timestamp listing API](https://snapshot.debian.org/) and the rule that a request between imports resolves to the latest earlier available import. The official `https://snapshot.debian.org/mr/timestamp/` response was retrieved over HTTPS; the full response had SHA-256 `3f22892f756faccb1e60f54650a80acdd6c6411fbd4b63f38861083bf72524cb`. From its respective ordered archive lists, the greatest available timestamp at or before the requested `20261029T000000Z` was `20261028T204034Z` for `debian` and `20261028T214216Z` for `debian-security`. These are the effective archive timestamps indicated by the listing at inspection time; this research does not approve them as deployment pins. The API response is not itself a signed Release document; its authenticity relies on the observed HTTPS connection, and the service may later change its available history.

Requests for `dists/trixie/InRelease` at the main effective timestamp and `dists/trixie-security/InRelease` at the security effective timestamp returned redirects to Snapshot content IDs `aa33cb317177428f33c9ff72fc3e9b634645f6ae` and `f3f31f1da00348dd19a0af488fb351797b0930e2`, respectively. Those IDs match the SHA-1 of the previously retained, signature-checked files. Their SHA-256 hashes also still match the main and security hashes recorded above. SHA-1 is only Snapshot's content identifier here, not a security integrity decision; rely on signed metadata and the recorded SHA-256. The separate `file/<content-id>/info` responses report `first_seen` values `20260912T080811Z` and `20261028T214216Z`; `first_seen` describes the file and should not be mistaken for the main archive's effective timestamp.

At or after expiry, follow a separately reviewed snapshot freshness/update policy rather than silently weakening APT checks.
