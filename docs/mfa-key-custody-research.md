## Verified capabilities and platform limits

The upstream [systemd 257 credential documentation](https://www.freedesktop.org/software/systemd/man/257/systemd-creds.html) describes host, TPM2 and combined protection. Host protection depends on a host filesystem secret: an attacker with sufficient access to that filesystem can decrypt credentials. TPM2 protection additionally depends on the original TPM and configured policy; do not assume a TPM is present on the Pi. The `auto` mode can select different protection depending on detected hardware and persistent storage; `null` provides neither confidentiality nor authentication. Neither automatic selection nor null protection is approved. The exact mode and fallback must be explicit and tested.

[systemd.exec 257](https://www.freedesktop.org/software/systemd/man/257/systemd.exec.html) describes `LoadCredentialEncrypted=`: systemd authenticates and decrypts a stored credential before supplying plaintext to processes in a read-only per-unit credential directory, exposed through `CREDENTIALS_DIRECTORY`. The unit's OS user and superuser can access it; non-swappable backing is conditional. A compromised access-service process or sufficiently privileged host administrator can read it. A missing credential may not be fatal when a path is omitted or a credential identifier is used: the application must verify presence and validity and fail closed rather than assume systemd always enforces it. Service account reuse, process inheritance, diagnostics, core dumps and swap require separate assessment.

[Debian Trixie currently lists systemd 257.13-1~deb13u1](https://packages.debian.org/trixie/systemd). This does not establish the exact package, build options or credential behavior in the selected Raspberry Pi OS image. Verify the installed image and selected package snapshot, version-specific manuals, persistent host storage and ARM64 behavior before proposing a deployable unit. No TPM, secure boot, hardware protection or physical isolation has been established.

## Proposed lifecycle for review

1. An authenticated, authorized OS administrator provisions a fresh, dedicated random TOTP encryption key on the target after prerequisites and audit availability are checked. Key material must not appear in shell arguments, logs, repository files, model context or downloadable backups. The exact generation, encrypted-credential creation and secure input path need review; no command is authorized here.
2. An explicitly approved unit supplies the credential only to a dedicated access-service identity. The application checks credential availability and length at startup, restricts MFA operations on failure, and does not generate a replacement key for existing encrypted factors. A separate application AEAD encrypts TOTP seeds with unique nonces and account-bound associated data; its algorithm, dependency, storage schema, associated-data format and key versioning remain unapproved. Encryption of the systemd credential alone does not encrypt stored TOTP seeds.
3. For rotation, stage a new credential and version, re-encrypt seeds under controlled transactional or resumable semantics, verify integrity and preserve recovery until the transition succeeds. Define durable audit, concurrent enrollment/login handling and interrupted rollback before implementation. Do not delete the old key while data still depends on it; do not promise secure erasure on microSD.
4. Downloadable backups exclude TOTP seeds and all secret keys and tokens. Define how restored accounts with MFA enabled enter an authenticated, audited re-enrollment flow; never silently disable MFA or make an account usable without its required factor. Same-device restoration and migration require separate design and tests. A host-bound credential is not automatically transferable to another OS installation or Pi.
5. If a key is lost or fails authentication, block affected MFA verification and preserve the existing ciphertext. Use only the separately approved OS-admin lost-factor recovery outcome: explicit confirmation, audit and mandatory fresh MFA enrollment; its detailed authorization and transaction mechanics are still open. If the host protection secret is compromised, treat affected key and factors as compromised and use an approved incident/re-enrollment process rather than assuming rewrapping repairs exposure.

## Choices and acceptance evidence still needed

- Select host-only, a verified hardware-bound mechanism or a separately specified secret manager; weigh offline availability, compromise resistance, portability and unrecoverable key loss. The present authorization only permits investigation.
- Approve host service identity, storage paths, protection mode, key lifecycle, availability and audit-failure behavior under G-OPS/G-SECURITY; approve actual crypto library, versions and data migration separately. Decide legitimate account restoration without copying TOTP secrets into downloadable archives.
- Test synthetic credentials in ARM64: authorized and unauthorized unit access, missing and tampered credentials, restart, OS update, wrong host secret, interrupted provisioning and rotation, service crashes and concurrent factor enrollment. Confirm logs, crash artifacts and archives contain no secrets. Test real Pi behavior, including storage persistence and physical threat assumptions, before hardware acceptance.

Evidence is documentation review only. No service configuration, packages, actual keys, crypto implementation, tests or hardware acceptance are claimed.
