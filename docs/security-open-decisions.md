## Reverse proxy and client origin

Candidate: one Caddy instance is the only permitted application-facing reverse proxy. It listens only on explicitly approved LAN and Tailscale interfaces; the access server listens on an isolated loopback endpoint. Enforce that access server traffic can originate only from this local proxy using an OS boundary and an authenticated internal boundary, not loopback address alone. At the edge discard incoming forwarding headers and set a single client-address header from the actual accepted connection. Trust only that fixed header from the authenticated proxy; normalize mapped IPv4 and IPv6 addresses, reject multiple or malformed values, and fail closed where origin is required for guest admission. Do not interpret arbitrary `X-Forwarded-For` hops. This is an application design, not a claim that default Caddy behavior implements it. Caddy's [reverse_proxy documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) describes its forwarding header behavior and trusted proxies; select and verify exact configuration under G-OPS/G-SECURITY. Tailscale packet source address, address translation, listener binding, proxy authentication and fail-closed firewall behavior require emulator and Pi verification.

Alternative: a formally specified trusted proxy chain may support another reverse proxy, but adds hop-count and spoofing complexity. IP address is a rate-limit signal, not identity; shared NAT and address changes can disadvantage users. Tests must inject forged/multiple headers and malformed addresses, connect directly to the internal listener, and cover Tailscale, IPv6, proxy restart and misconfiguration.

## CSRF

Candidate: use a server-generated 256-bit random synchronizer token per pre-authentication or authenticated browser session, stored server-side. Deliver it only to the same-origin page over HTTPS, submit it in a dedicated request header on every cookie-authenticated state-changing request including login and guest creation, and verify it against the current session with a constant-time comparison. Rotate the token and session on authentication and role changes, invalidate on logout, and never place it in a URL or logs. `GET`, `HEAD` and `OPTIONS` must be safe; check exact configured Origin on state-changing browser requests, allow no wildcard credentialed CORS and reject missing or null Origin unless a separately specified non-browser authenticated path exists. Use the existing Secure, HttpOnly, SameSite=Strict session cookie; SameSite and Origin are defense in depth, not a replacement for the token. [OWASP's CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) describes synchronizer tokens and their session-bound validation.

Decision needed: endpoint for token issuance and its precise public contract, pre-authentication session lifecycle, reset/recovery paths and token rotation across tabs. Test cross-origin forms/fetch, missing/wrong/replayed token, login CSRF, origin spoofing, stale tab, session rotation, SSE and legitimate concurrent tabs; CSRF defenses do not prevent same-origin script injection.

## MFA key custody

Candidate: generate a dedicated random 256-bit encryption key for TOTP seeds, distinct from session, backup and memory keys. Store only authenticated ciphertext with a unique nonce per key and account-bound associated data; never export seeds or this key in downloadable backups. Provision the key through an OS-admin-controlled systemd encrypted credential to the access service only, and fail closed for MFA operations when key authentication or availability fails. [systemd-creds](https://www.freedesktop.org/software/systemd/man/256/systemd-creds.html) documents host, TPM and combined encryption modes; the host-only mode is recoverable by an attacker with sufficient OS/filesystem access, while TPM binding can make loss of the original device unrecoverable. Neither protects against privileged host compromise. Select the mode only after verifying target hardware, systemd version, key lifecycle and recovery; do not assume the Pi has a TPM. Choose and review the AEAD implementation, nonce generation, rotation and atomic re-encryption separately with exact dependency and schema approval.

Decision needed: host-bound systemd credential versus an explicitly approved external secret manager or optional hardware-backed key; enrollment and loss recovery, permissions, rotation, backups and account migration. Losing the key prevents verification of affected TOTP seeds: the separately approved OS-admin lost-MFA flow must be used, with audit and mandatory re-enrollment. Test unavailable/wrong key, changed account binding, corruption, nonce uniqueness, startup/restart and rotation failure without exposing keys or factors.

## Local password blocklist

Candidate: maintain a versioned, locally stored dataset comprising common and compromised full-password values plus documented service-specific entries; compare the complete NFC-normalized candidate locally, with no password sent to a remote service. The project administrator installs or updates it using an authenticated, integrity-verified release process. Missing or invalid required data blocks password creation/change but does not deny existing login, as already approved. NIST's [SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html) recommends comparing the entire prospective password against common, expected or compromised values. Decide the source, dataset version, provenance, distribution rights/license, update cadence, format and integrity mechanism only after verification; no specific corpus has been approved or established as legally redistributable. Treat compromised-password source data as sensitive: do not place raw passwords in logs, telemetry or repository history. Test normalization, common/compromised matches, missing/corrupt lists, updating during checks and offline use.

## Password and MFA recovery

Accepted direction: on 2026-10-30 the owner chose password reset for an ordinary user account through an authorized operating-system administrator, while retaining configured MFA and auditing; see [ADR 0005](adr/0005-user-password-recovery.md). The alternative admin-assisted web reset with a human-delivered code was not selected for that scope. This choice does not authorize an email or messaging integration. Exact OS identity verification and privilege, the reset mechanism and credential delivery, MFA interaction, session and token revocation, confirmation, atomicity, audit failure and interruption recovery remain to be designed and approved. Existing stronger accepted requirements continue to apply; do not silently bypass MFA. For an admin whose second factor is lost, the separately accepted outcome requires explicit OS-admin confirmation, audit and compulsory new MFA enrollment ([ADR 0003](adr/0003-lost-mfa-recovery.md)).

Test unauthorized OS users and wrong-account requests, attempts to bypass MFA, concurrent or interrupted resets, revocation and audit failures, and any approved credential or token mechanism's expiry and replay. Do not assume a particular token or delivery flow is part of this decision.

## Review gates and evidence

Review each choice individually; approval of a security direction does not approve the exact implementation, library, schema, service configuration or network exposure. T003 is complete at design-proposal scope; T008 remains incomplete and T011 remains a draft; T026–T035 also depend on the approved toolchain, contracts and checks. These proposals are design only: no services, credentials, applications, tests or hardware acceptance are claimed; only the limited approval recorded in ADR 0005 applies here. When the source documents or constitution change, reassess scope and record the decision in a new ADR.
