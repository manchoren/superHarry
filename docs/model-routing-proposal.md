## Official provider evidence and unknowns

[OpenAI's model page](https://developers.openai.com/api/docs/models/gpt-6.1-terra) lists `gpt-6.1-terra`, supports `reasoning.effort` values `none`, `low`, `medium`, `high`, `xhigh`, `max`, defaults to `medium` if unspecified, and requires the Responses API for tool calling. The accepted project default is explicitly `low`; therefore the request must set it rather than rely on the provider default. Streaming, function calling and structured outputs are listed; image input is supported, audio input is not. Provider features do not authorize application tools or override local-only STT.

The same page lists standard text prices per million tokens as $1 input, $0.05 cached input, $1.25 cache write for 30 minutes ($2.50 for 12 hours), and $5 output. Over 272K input tokens, input/cache rates double and output is 1.5 times the standard rate for the full request. Fast mode is twice the standard rate; regional processing can add 10%. Additional tool charges may apply. These are documentation observations, not a budget approval or billing guarantee. [Reasoning tokens count as output tokens](https://developers.openai.com/api/docs/guides/reasoning); do not charge them twice. The [pricing page](https://developers.openai.com/api/docs/pricing) and applicable account terms must be rechecked before enabling a priced option.

[Fast mode documentation](https://developers.openai.com/api/docs/guides/fast-mode) describes per-request `service_tier: fast` or `priority`, project-level defaults, and possible downgrade to `default` under rapid traffic increases; the response's service tier identifies actual processing. The [Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create) states responses show `priority` for either request spelling; the guide specifically describes that normalization for GPT-5.6 and earlier, so exact returned values for Terra should be verified against the actual account before use. Display and bill the actual reported mode, not the requested mode; if absent or unknown, disclose uncertainty and reserve conservatively. Do not assume Fast mode availability or guarantees from public docs alone.

No account, project, credentials, region, spending limits, rate limits or model entitlements were inspected. Public model documentation is not proof this project's account has access. Before deployment an authorized operator must verify account/model availability and supported request settings using approved credentials and a separately controlled budget; do not put credentials or private prompts in evidence. No substitute model or unsupported setting should be silently chosen.

## Proposed behavior for G-MODEL review

- Guest requests always remain local; enforce before provider adapter invocation. Authenticated users and admins choose local or automatic, with supported reasoning controls constrained by approved model capabilities and budget. Admin controls premium model and supported defaults; unsupported selections return a structured error rather than silently altering intent.
- Automatic mode uses the approved OpenAI model when its account, capability and budgets permit. On provider failure, rate limit, timeout, or exhausted hard limit, fall directly to local mode, never an economy provider. A circuit breaker probes recovery with bounded exponential backoff; its parameters are unresolved. If local cannot safely satisfy the task, preserve and queue premium-dependent work subject to permissions, notify its owner and permit cancellation. Never replay an uncertain consequential action blindly.
- Provide full constitution as protected context for every agent on both paths; if it cannot fit or delivery fails, block actions. Tool authorization, identity and input validation are independent of model output. Do not enable provider-hosted shell, code execution, network or other tools merely because the provider supports them; all actions need the project's authorized tool boundary and sandbox policy.
- Maintain a versioned capability record for each approved model, request mode and account. Refresh it before enabling a changed model or capability; describe actual result model and mode in the UI. Model selection and local capability remain provisional until approved real-Pi tests.

## Accounting proposal and open decisions

Track daily and monthly token and cost usage per user and globally. Before dispatch, atomically reserve a conservative upper bound using input, configured maximum output, applicable cache, context, service tier, regional and approved tool charges; reject or fall back locally if either relevant hard limit cannot accommodate the reservation. Reservations prevent concurrent admission from silently overspending; settle actual returned usage and actual processing tier once available, retain unresolved reservations when usage is unknown, and reconcile against provider billing. Handle cancellation, retries and partially charged failures explicitly; never assume a timeout means zero cost. Alert at admin-defined warning thresholds and enforce hard limits. Time zone/reset rules, reservation calculation, unknown-usage reconciliation, probe budget, exact currency/rounding and price versioning need owner approval; no numerical threshold is proposed as accepted.

The accounting system cannot guarantee a provider invoice hard cap without verified upper bounds for every applicable charge and reconciliation semantics; if the bound is unavailable, fail closed for premium admission rather than claiming a guarantee. Admin must review any price update or newly billable tool before use. Synthetic mocked tests should cover simultaneous reservations, changing rates, actual Fast downgrade, missing usage, cancellation, duplicate settlement and provider failure. T010 specifies durable action states and resource admission; T044–T049 implement only after G-MODEL and relevant contract approvals. No model request or paid operation was made for this design.
