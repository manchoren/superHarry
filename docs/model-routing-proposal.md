## Official provider evidence and unknowns

[OpenAI's GPT-6.1 Terra model page](https://developers.openai.com/api/docs/models/gpt-6.1-terra) lists the public model ID `gpt-6.1-terra` and supports `reasoning.effort` values `none`, `low`, `medium`, `high`, `xhigh`, and `max`; its documented default is `medium`. The accepted project default is explicitly `low`, so requests must set it rather than rely on the provider default. The [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning) separately says GPT-6 models support `reasoning.mode` values `standard` and `pro` in the Responses API; mode and effort are independent. This is a public capability, not project approval to expose or choose `pro`; exact model/account support and whether to offer this additional control remain subject to G-MODEL review. Tool calling requires the Responses API. The model page lists streaming, function calling, structured outputs and image input; it lists audio and video as unsupported modalities. Provider capabilities do not authorize application tools or override local-only STT.

The model page lists standard text prices per million tokens of $1 input, $0.05 cached input, $1.25 cache write for 30-minute retention ($2.50 for 12-hour retention), and $5 output. For requests above 272K input tokens, it lists doubled input/cache rates and 1.5× output rates for the full request. It lists Fast mode at 2× Standard and a 10% regional-processing premium where available. The [pricing page](https://developers.openai.com/api/docs/pricing) is the authoritative current price table; these are public documentation figures, not a budget approval, account quote, or billing guarantee. The [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning) says reasoning tokens are billed as output tokens; do not charge them twice. Recheck prices and applicable account terms before enabling a priced option.

[Fast mode documentation](https://developers.openai.com/api/docs/guides/fast-mode) documents per-request `service_tier: fast` and a project-level default. It says the response's `service_tier` identifies the processing tier and that rapid traffic increases can downgrade requests to `default`, charged at Standard rates; cached-input discounts still apply. The guide says Fast mode can deliver up to 2.5× faster speeds, not a guaranteed per-request latency. It specifically mentions GPT-6.1 Terra support in the EU-data-residency context, while also stating availability depends on jurisdiction. The public model page lists Fast pricing, but none of these facts establish that this project's account, project, region, or model entitlement can use it. Use only a verified supported request setting; display and account for the actual returned tier, not the requested tier. If the returned tier or usage is absent or unknown, disclose uncertainty and reserve conservatively. The [Responses API create reference](https://developers.openai.com/api/reference/resources/responses/methods/create) documents the response contract; verify the exact returned tier for the approved model/account before implementation.

No account, project, credentials, region, spending limits, rate limits or model entitlements were inspected, and no external API was called. Public model documentation is evidence of documented capability and published pricing only; it does not prove this project's account access, rate limits, Fast-mode entitlement, regional availability, or effective price. Before deployment an authorized operator must verify account/model availability and supported request settings using approved credentials and a separately controlled budget; do not put credentials or private prompts in evidence. No substitute model or unsupported setting should be silently chosen.

## Proposed behavior for G-MODEL review

- Guest requests always remain local; enforce before provider adapter invocation. Authenticated users and admins choose local or automatic, with supported reasoning controls constrained by approved model capabilities and budget. Admin controls premium model and supported defaults; unsupported selections return a structured error rather than silently altering intent.
- Automatic mode uses the approved OpenAI model when its account, capability and budgets permit. On provider failure, rate limit, timeout, or exhausted hard limit, fall directly to local mode, never an economy provider. A circuit breaker probes recovery with bounded exponential backoff; its parameters are unresolved. If local cannot safely satisfy the task, preserve and queue premium-dependent work subject to permissions, notify its owner and permit cancellation. Never replay an uncertain consequential action blindly.
- Provide full constitution as protected context for every agent on both paths; if it cannot fit or delivery fails, block actions. Tool authorization, identity and input validation are independent of model output. Do not enable provider-hosted shell, code execution, network or other tools merely because the provider supports them; all actions need the project's authorized tool boundary and sandbox policy.
- Maintain a versioned capability record for each approved model, request mode and account. Refresh it before enabling a changed model or capability; describe actual result model and mode in the UI. Model selection and local capability remain provisional until approved real-Pi tests.

## Accounting proposal and open decisions

Track daily and monthly token and cost usage per user and globally. Before dispatch, atomically reserve a conservative upper bound using input, configured maximum output, applicable cache, context, service tier, regional and approved tool charges; reject or fall back locally if either relevant hard limit cannot accommodate the reservation. Reservations prevent concurrent admission from silently overspending; settle actual returned usage and actual processing tier once available, retain unresolved reservations when usage is unknown, and reconcile against provider billing. Handle cancellation, retries and partially charged failures explicitly; never assume a timeout means zero cost. Alert at admin-defined warning thresholds and enforce hard limits. Time zone/reset rules, reservation calculation, unknown-usage reconciliation, probe budget, exact currency/rounding and price versioning need owner approval; no numerical threshold is proposed as accepted.

The accounting system cannot guarantee a provider invoice hard cap without verified upper bounds for every applicable charge and reconciliation semantics; if the bound is unavailable, fail closed for premium admission rather than claiming a guarantee. Admin must review any price update or newly billable tool before use. Synthetic mocked tests should cover simultaneous reservations, changing rates, actual Fast downgrade, missing usage, cancellation, duplicate settlement and provider failure. T010 specifies durable action states and resource admission; T044–T049 implement only after G-MODEL and relevant contract approvals. No model request or paid operation was made for this design.
