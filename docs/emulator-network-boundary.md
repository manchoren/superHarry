# Proposed network boundary for ARM64 emulation

Status: design and test proposal for T003/T014, updated 2026-10-30. The owner superseded the earlier repository-allowlist direction: unrestricted outbound Internet access for the development guest is selected, while inbound connections and port forwarding remain disallowed. This does not change the product's separate LAN/VPN-only deployment policy. The owner selected explicit CPU `cortex-a76` and a versioned `virt` machine compatible with candidate QEMU 11.1.3-1; verify the exact machine identifier from that build before use. QEMU defaults are the selected device-profile starting point, with effective devices to be documented after inspection. A suggested hosts-file edit is not an enforcement mechanism; hosts files map names and do not control all network destinations. No network policy, firewall rule, QEMU invocation, tool, guest image or service is approved, installed or tested. Constitution baseline 2026-10-29; SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. The [environment decisions](environment-decisions.md), [firmware options](qemu-firmware-options.md), and [dependency security review](qemu-transitive-security-review.md) remain prerequisites to selecting a candidate. ## Scope and threat boundary

A first emulator smoke test is intended to use authenticated guest media and synthetic data. The current owner direction permits unrestricted outbound Internet access from the guest; inbound connections and port forwarding remain disallowed. The previous package-repository allowlist and offline package-ISO plans are superseded. Authenticating the guest image does not constrain its network behavior: any process running in the guest can make outbound connections. This proposed development configuration does not establish production sandbox isolation, software safety, dependency approval or Raspberry Pi hardware behavior. Host compromise, untrusted image parsing and emulator vulnerabilities remain risks.

QEMU's [invocation reference](https://www.qemu.org/docs/master/system/invocation.html) states that when no other network option is given a default NIC with a user-mode host backend is activated, and that `-nic none` overrides that default. QEMU defaults are the selected starting device profile, so an implicit user-mode NIC and unrestricted guest egress are expected. The owner accepts unrestricted guest outbound access; no firewall or hosts-file restriction is selected. Inbound connections and port forwarding remain disallowed and must be verified against the actual QEMU defaults and host configuration before an approved boot. `-nic none` is not the selected network direction, and by itself neither disables host-process network access nor prevents a later management operation from adding a device.

## Proposed layered controls

- Launch only the approved binary and firmware, with reviewed arguments and an exact approved, local image and disk graph. Reject URLs, protocol-backed storage and backing references outside the authorized staging area; inspect backing chains and image metadata through a separately reviewed process. Do not trust a filename extension or initial path as proof that the whole backing chain is local. Authentication, traversal and symlink handling, and image validation remain open.
- Disable or tightly restrict monitor, QMP, HMP and device hotplug interfaces unless a specific local management channel is necessary and separately reviewed. QMP can modify block and device state, so a safe startup command cannot protect an exposed management interface. QEMU's [QMP reference](https://www.qemu.org/docs/master/interop/qemu-qmp-ref.html) documents block and device management. No network-facing monitor, migration, debug, console or graphical listener is authorized here.
- No outbound destination restriction is selected. A hosts-file change is not a substitute: it changes name-to-address resolution for some lookups but does not prevent connections to literal IP addresses, alternate resolvers, or other destinations and services. It can also break repository/CDN resolution. If the owner later wants restricted egress, design and approve a real network enforcement boundary separately. No firewall changes are authorized here.
- QEMU defaults are the owner-selected device-profile starting point. Record and assess the exact realized devices, default network backend, listeners, block graph, display and management interfaces for the pinned QEMU build and versioned machine. Do not assume that default devices are minimal, safe or compatible with the selected unrestricted guest egress and no-inbound/no-forwarding boundary. The owner selected `virtio-blk` for the normal root disk and a temporary `virtio-scsi`/SCSI CD-ROM for the read-only installer ISO; review the transient installation device graph separately and detach the controller and media after installation. QEMU warns in its invocation reference that semihosting can expose the host filesystem to a guest; determine whether it is enabled by default and do not proceed if an unacceptable host-access path is present. Use least privilege and no production credentials. The selected rollback design is a read-only base disk plus disposable QCOW2 overlay and fresh writable firmware VARS copy per VM session; store these VM artifacts under repository-root `.dev-vm/`, ignored by Git and not shared with the guest. The owner selected explicit Windows ACLs granting access only to the current user, SYSTEM and local Administrators; implement and validate them before provisioning. This is a host storage choice, not approval of a file-sharing device. Automatically discard the overlay and writable VARS after normal QEMU exit; preserve abnormal-exit artifacts until explicit cleanup after verifying QEMU is no longer running and has released file handles. Intentional baseline updates are rebuilt from pinned instructions and sources, never promoted from session overlays. Permissions, cleanup safety, rebuild and reset behavior remain to be reviewed. Exact device/default behavior, local console, disk writes and host filesystem permissions need review.
- Debian netinst and the installed guest may use unrestricted outbound Internet under the selected direction. Package-repository ISO staging is no longer selected. Preserve the separate no-inbound/no-port-forwarding boundary, and do not confuse image authenticity or package signature verification with network confinement. Any later change to restrict egress requires a new owner decision and applicable G-OPS/security review.

## Acceptance tests after approval

1. Confirm actual command line, effective machine devices, NICs, block graph, backing chains, monitor endpoints, host privileges and executable/firmware digests, including after restart and configuration changes. Record QEMU default behavior for the exact approved build; do not infer safety from omitted options.
2. Verify that outbound guest Internet access matches the selected unrestricted direction. Attempt inbound connections and port forwarding and verify they remain unavailable under the actual host/QEMU configuration. A hosts-file entry must not be counted as a network restriction. Record that unrestricted egress allows guest processes to contact arbitrary outbound destinations.
3. Attempt remote HTTP, HTTPS, FTP, FTPS and SSH/SFTP image references, remote or nested backing files, protocol aliases and unauthorized management attachment; deny before access. Test local path traversal, symlinks and malformed image metadata within the approved staging boundary.
4. Attempt hotplug and unauthorized monitor/QMP access, semihosting and host sharing. Ensure that a later operation cannot silently introduce networking or remote storage; authorized maintenance must use a separate reviewed workflow.
5. After approval, demonstrate installation/update with unrestricted guest outbound access, then install, start and stop the minimal approved application with synthetic data. Record OS, package versions, configuration, limitations, audit evidence and failures; no hardware acceptance is implied.

These are test obligations, not completed tests. Source-level restrictions on QEMU's SSH and curl block drivers reduce specific suspected paths only; they do not establish binary safety, eliminate vulnerabilities in libssh/libssh2 or close [the transitive security review](qemu-transitive-security-review.md). No emulator, firewall, package or firmware was executed or configured in producing this document.
