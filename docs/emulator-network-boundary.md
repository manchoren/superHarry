Constitution baseline 2026-10-29; SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. The [environment decisions](environment-decisions.md), [firmware options](qemu-firmware-options.md), and [dependency security review](qemu-transitive-security-review.md) remain prerequisites to selecting a candidate. G-ARCH and G-OPS, and applicable security approval, must precede setup or network changes.

## Scope and threat boundary

A first emulator smoke test could use authenticated, locally staged guest media and synthetic data, with no remote disk image, network boot, forwarded guest port, external management listener or guest network. This proposed development configuration does not establish production sandbox isolation, software safety, dependency approval or Raspberry Pi hardware behavior. Host compromise, untrusted image parsing and emulator vulnerabilities remain risks even without guest networking.

QEMU's [invocation reference](https://www.qemu.org/docs/master/system/invocation.html) states that when no other network option is given a default NIC with a user-mode host backend is activated, and that `-nic none` overrides that default. Merely omitting network options is therefore insufficient evidence of an offline guest. A future reviewed configuration should explicitly disable default guest networking and avoid adding a network backend, network device, host forwarding or other network-capable device. Verify the exact approved QEMU version and machine configuration: `-nic none` alone neither disables host-process network access nor prevents a later management operation from adding a device.

## Proposed layered controls

- Launch only the approved binary and firmware, with reviewed arguments and an exact approved, local image and disk graph. Reject URLs, protocol-backed storage and backing references outside the authorized staging area; inspect backing chains and image metadata through a separately reviewed process. Do not trust a filename extension or initial path as proof that the whole backing chain is local. Authentication, traversal and symlink handling, and image validation remain open.
- Disable or tightly restrict monitor, QMP, HMP and device hotplug interfaces unless a specific local management channel is necessary and separately reviewed. QMP can modify block and device state, so a safe startup command cannot protect an exposed management interface. QEMU's [QMP reference](https://www.qemu.org/docs/master/interop/qemu-qmp-ref.html) documents block and device management. No network-facing monitor, migration, debug, console or graphical listener is authorized here.
- Independently enforce an OS boundary on the emulator process for outbound and inbound traffic, including IPv4, IPv6, DNS and loopback as appropriate; do not rely solely on guest NIC settings or a checked argument. For Windows, [Microsoft's firewall documentation](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure) states outbound traffic is allowed by default and describes program-specific outbound rules. A program-path rule is a candidate for assessment, not proven complete process isolation: verify child processes, paths and replacement, profile, privileged bypass, local sockets, rule precedence and failure behavior. No firewall changes are authorized here. WSL/Linux alternatives need their own separately specified and approved boundary; Windows application rules must not be presumed to protect processes inside WSL.
- Disable semihosting, unneeded host file shares, remote block backends, migration endpoints and device passthrough; QEMU warns in its invocation reference that semihosting can expose the host filesystem to a guest. Use least privilege and no production credentials. The exact device set, local console, disk writes, snapshots and host filesystem permissions need review.
- Stage verified packages outside the emulator if offline provisioning is chosen; a Debian netinst image ordinarily needs an available package source, so no claim of a usable offline install follows from `-nic none`. A reviewed local package medium and complete signed dependency snapshot would be required. Any online provisioning or later networking is a separate G-OPS/security decision with its own egress, DNS, update, logging, supply-chain and recovery rules. Do not weaken offline boundaries silently to make installation work.

## Acceptance tests after approval

1. Confirm actual command line, effective machine devices, NICs, block graph, backing chains, monitor endpoints, host privileges and executable/firmware digests, including after restart and configuration changes. Test default behavior separately so absence of explicit network arguments cannot be mistaken for isolation.
2. Attempt DNS, loopback, private/public IPv4 and IPv6 egress from guest and emulator process, and attempt inbound connections and configured forwarding; deny under the intended OS policy. Include missing, disabled, modified or failed policy and confirm startup fails closed. Exercise process replacement and child-process cases where relevant.
3. Attempt remote HTTP, HTTPS, FTP, FTPS and SSH/SFTP image references, remote or nested backing files, protocol aliases and unauthorized management attachment; deny before access. Test local path traversal, symlinks and malformed image metadata within the approved staging boundary.
4. Attempt hotplug and unauthorized monitor/QMP access, semihosting and host sharing. Ensure that a later operation cannot silently introduce networking or remote storage; authorized maintenance must use a separate reviewed workflow.
5. Demonstrate clean offline provisioning using a verified complete package source, then install, start and stop the minimal approved application with synthetic data. If online provisioning is later authorized, separately test its restrictions and restore offline state. Record OS, versions, configuration, limitations, audit evidence and failures; no hardware acceptance is implied.

These are test obligations, not completed tests. Source-level restrictions on QEMU's SSH and curl block drivers reduce specific suspected paths only; they do not establish binary safety, eliminate vulnerabilities in libssh/libssh2 or close [the transitive security review](qemu-transitive-security-review.md). No emulator, firewall, package or firmware was executed or configured in producing this document.
