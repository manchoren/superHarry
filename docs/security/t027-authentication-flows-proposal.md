## Scope

T027 covers admin-created user accounts, optional TOTP for admins and users, expiring single-use password-reset tokens, and secure account/role changes and revocation. It does not implement object authorization (T028), audit storage and retention (T029), later administrator recovery (T031), bootstrap, guest admission, deployment or any additional role/capability.

The current application uses Django's built-in user, login/logout, session and CSRF mechanisms. `AuditedUserAdmin` implements admin-managed user creation, deactivation and role changes with T029 audit events, and hard deletion is disabled. `AuditEvent` storage, its closed-vocabulary writer, the login/logout audit integration, and the bounded admin audit read/export interface are implemented under T029. The current implementation adds TOTP and password-reset flows, encrypted MFA secret storage, local password validators and Argon2id configuration; the independent security/contract review is recorded in the backlog. Operational key provisioning remains open.

## Accepted constraints

- Account creation remains admin-controlled; there is no public self-registration.
- TOTP is optional for both `admin` and `user`. WebAuthn/passkeys remain deferred.
- Login uses a username, password and optional TOTP in one submission. Use generic credential failures; do not reveal whether an account exists or has TOTP enabled.
- A wrong-password attempt for a known account increments a durable account counter in a separate committed database operation before audit append. Five failures within a rolling 15-minute window lock that account for 15 minutes from the fifth attempt. Password-audit failure returns generic 503 but cannot erase the counter. For an invalid, missing, replayed or unexpected TOTP code, commit the counter increment and `auth.totp_verification_failed` event together; if the audit write fails, roll back both and return generic 503. The owner confirmed this TOTP-specific atomic behavior on 2026-11-06, resolving the prior conflict with the password-failure sequence. Successful login clears the counter in the same transaction as session creation and required success events. Unknown-account attempts remain generic and are not retained as arbitrary identifiers. Key-unavailable TOTP failures follow the separately approved fail-closed behavior and do not increment this counter.
- The owner-selected TOTP starting policy specifies a unique random seed, 30-second step, six digits, acceptance of the current step and one adjacent step on each side, rate limiting, and atomic rejection of a previously accepted step. Enroll only after recent reauthentication, explicit confirmation and verification of a valid code. Provide ten single-use recovery codes per account, each with 128 bits of randomness, shown once and stored only as verifiers. An application admin may reset an ordinary user's TOTP only after recent reauthentication, explicit confirmation and mandatory audit; that user must re-enroll. Recovery codes do not replace the OS-admin path for an admin who loses all factors. On 2026-11-05 the owner decided that enrollment, disablement or reset preserves existing sessions; TOTP requirements take effect on the next login. These directions do not approve implementation or bypass audit requirements.
- Passwords use configured local Django password validators; HIBP screening is postponed. The approved local policy also requires a 15-code-point minimum, support for at least 64 code points, NFC normalization, Unicode and spaces, and common-password checks; current settings implement these validators. Password reset does not bypass those validators or send passwords remotely. The owner explicitly approved installation of `argon2-cffi==25.1.0` on 2026-11-06 after package-guard review and accepted Argon2id at 19 MiB/t=2/p=1 the same day. The selected Debian guest recorded one sample at 0.244 seconds for 19 MiB and 0.376 seconds for 32 MiB; representative load/capacity validation remains part of operational acceptance. No HIBP corpus is required or authorized for this scope.
- The owner selected an OS-admin-issued, single-use reset token with 256 bits of randomness and a ten-minute lifetime, issued through a dedicated local management command for direct in-person handoff on 2026-11-02 (amendment to ADR 0005). The command must require effective UID 0 under the OS's existing sudo policy; `SUDO_UID`/`SUDO_USER` are for audit attribution only, not authorization. Do not add a custom sudoers rule. Display the token once through the controlling TTY only, never through argv, redirected stdout, logs or a file. Verify the actual target image's sudo/group policy before implementation. A successful reset revokes every authenticated session belonging to the affected account, preserves its TOTP factor and requires a fresh sign-in; unrelated accounts' sessions are untouched. G-SECURITY/G-OPS, token verifier/rate-limit/cleanup details, audit-failure behavior and implementation remain open; no email or messaging channel is approved.
- The active ADR 0007 amendment specifies Django native session and CSRF mechanisms with one host-only session cookie and the approved strict-Origin policy. T027 must use the existing middleware and must not restore the superseded two-cookie/pre-authentication endpoint design.
- On 2026-11-02 the owner approved fail-closed behavior for a missing, invalid or `key_version`-mismatched host credential/key: login treats it as the existing generic credential failure with no session created; an already-authenticated session is not revoked automatically and only the dependent operation is denied; new enrollment is blocked without creating a pending device row; a decrypt failure during confirmation does not count against the user's attempt/rate limit (unlike a wrong code); an admin may revoke/delete the device without decrypting it, subject to the existing reauthentication, confirmation and audit requirements; and every case returns the same generic external error, with the specific cause recorded only in the internal audit event. See the [T027 TOTP key-custody proposal](t027-totp-key-custody-proposal.md#approved-fail-closed-behavior-2026-11-02). This does not approve key generation/provisioning, rotation or T029's remaining audit event call sites. The exact schema is approved for additive reversible implementation under the constitution. On 2026-11-06 the owner explicitly approved installing `cryptography==50.0.2` and `argon2-cffi==25.1.0` after direct package guard review; see the exact platform lock files and results above.
- Required security events must not contain credentials or TOTP material. T027 cannot claim audit approval or bypass the independent T029/G-SECURITY/G-CONTRACT decisions.

## Candidate password-reset grant schema

The owner approved this exact field set and semantics on 2026-11-02 for G-CONTRACT only. This approval is separate from T023's Conversation/Message approval. It fixes the reset-grant field contract; it does not approve external HTTP semantics or OS configuration. The constitution authorizes additive reversible development models/migrations and internal API changes; dependency guard, Argon2 review and required audit behavior remain prerequisites for a complete flow.

| Field | Candidate type and semantics |
|---|---|
| `id` | Django `BigAutoField` primary key |
| `user` | One-to-one foreign key to `settings.AUTH_USER_MODEL`, `on_delete=CASCADE`, related name `password_reset_grant`; at most one current grant per account |
| `token_digest` | Unique 64-character lowercase hex SHA-256 digest of the 32 random token bytes; never store the raw token |
| `issued_at` | `DateTimeField(default=timezone.now, editable=False)` |
| `expires_at` | Required `DateTimeField`; issuance sets it to ten minutes after `issued_at` |
| `consumed_at` | Nullable `DateTimeField`; set atomically with a successful password update |

Issuing a replacement overwrites the single grant and invalidates the previously displayed token. A successful reset updates the password and consumes the matching unexpired grant in one database transaction; an expired, consumed or unknown token produces the same generic public failure. User deletion cascades to the grant. Keep no raw token, token URL, or user-supplied password in logs. T029 audit events and actor identity are separate and must not be added as fields here without review.

The schema intentionally does not choose an OS identity field because the authorized OS administrator may not be a Django user. It also does not define the selected command's target OS/group membership check, token display safeguards, reset throttling, audit transaction policy, or how every authenticated session is synchronously invalidated. Review concurrency/SQLite failure behavior before approving the consume-and-update guarantee. Approval of these fields alone would not satisfy G-SECURITY, dependency review, session/CSRF contract approval or authorize implementation.
