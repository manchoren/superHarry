## Proposed boundary

Use the approved host-bound systemd-credential direction to deliver a dedicated key to the Django service at startup. The candidate key is 256-bit, random, and distinct from session, backup and memory keys; its generation/provisioning is not approved. The application would use a separately reviewed authenticated-encryption implementation to encrypt TOTP seeds before storing them in the database. A systemd credential protects delivery of the key to the service; it does not itself encrypt TOTP database fields.

Store only authenticated ciphertext and the metadata needed to decrypt it, including a unique nonce and an account-bound authenticated-data value. Keep the key and plaintext seed out of the database, logs, downloadable backups and agent/model context. Only the service should be able to read the decrypted credential. Never fall back to plaintext or generate a replacement key when the credential is missing, invalid or unavailable.

The host-bound option is not a hardware-backed guarantee. It may not protect against privileged access to the host, and losing the host credential may make existing TOTP seeds unrecoverable. Do not assume TPM availability or copy a host-bound credential to another device as a recovery method.

## Approved fail-closed behavior (2026-11-02)

The owner approved these precise behaviors for when the host credential, key or `key_version` is missing, invalid, corrupted or unavailable. They do not approve key generation/provisioning mechanics, rotation or deployment; the exact AEAD package was separately authorized subject to package review, and the exact schema is approved for additive reversible implementation under the constitution. Apply T029's accepted audit event and transaction behavior; remaining call sites are still required.

- **Login for an enrolled account:** treat the failure as the same generic credential failure already used for a wrong TOTP code; create no session. This extends, without changing, the generic-failure behavior already accepted in the [T027 authentication flows proposal](t027-authentication-flows-proposal.md) to explicitly cover the key-unavailable/key-version-mismatch case.
- **Existing authenticated sessions:** do not revoke or sign out an already-authenticated session automatically because the key later becomes unavailable. Deny only the specific TOTP-dependent operation that needs the unavailable key; the session itself stays valid until it expires or is revoked through an existing separate control.
- **TOTP-dependent operations in an authenticated session** (for example a step-up verification required before a sensitive action): deny the specific operation with a generic external failure while the key is unavailable; never fall back to skipping the TOTP check.
- **New enrollment:** if the seed cannot be encrypted because the key is unavailable, block enrollment entirely and do not create a pending `TOTPDevice` row. No placeholder, empty-ciphertext or later-fill record is created.
- **Confirmation of a pending enrollment:** if the key becomes unavailable while decrypting the pending seed to check the submitted code, that failure does not count as a wrong user-submitted code against the user's attempt/rate limit; the device stays `pending` and unconfirmed. A wrong code (key available, authentication fails on content) still counts normally.
- **Administrative revocation/disablement:** an admin may revoke or delete an enrolled user's `TOTPDevice` without decrypting its stored seed, even while the key is unavailable, because revocation does not require reading the secret. This does not change the existing requirement for recent reauthentication, explicit confirmation and mandatory audit before an admin reset; use T029's approved audit writer and transaction contract to record the action and key-unavailable condition without exposing details to the affected user.
- **Error disclosure:** every case above returns the same generic external error already used for other credential failures; the response never distinguishes key-unavailable, `key_version` mismatch, ciphertext-authentication failure or corruption. Record the specific cause only through T029's internal audit writer, never in the response body or in logs reachable by the affected user. Login records the key-unavailable event; the independent T029 contract review remains outstanding.

Historical proposal-stage open items: key generation/provisioning, operator identity/command controls, systemd directives and rotation mechanics were recorded above. They were later implemented and exercised on the selected test VM, as documented in the runtime-validation entries below; formal G-CONTRACT/G-SECURITY and broader T149/G-OPS acceptance remain open. The repeated fail-closed alerting threshold remains a separate unresolved operational choice. AEAD choice and per-encryption nonce policy are now selected; implementation remains gated on the dependency review and guard. Pending-enrollment expiry/cleanup, including when the delay is caused by a key outage, is resolved as policy on 2026-11-02 in the [TOTP storage schema proposal](t027-totp-schema-proposal.md#approved-pending-enrollment-expiry-and-disablereset-deletion-policy-2026-11-02): a 10-minute expiry from `created_at`, cleaned up both opportunistically in the enrollment flow and via the daily Q-13 reconciliation job, regardless of whether the key was available; implementing that cleanup remains open.

- Do not require TPM for this VM. The selected target is a QEMU guest and existing inventory does not establish a virtual TPM; the host-bound systemd credential direction already accepted is sufficient for this deployment. Explicit host-only binding avoids accidental TPM-dependent lockout. - Keep the encrypted systemd credential on the VM and exclude it, `/var/lib/systemd/credential.secret`, and all plaintext working material from application/database/downloadable backups. Do not create a second backup copy of the encrypted credential: it is tied to this system installation and is not a portable recovery mechanism. Recovery from irrecoverable loss follows the already-approved path: mark existing TOTP factors unusable, use the separately authorized OS-admin recovery process, and require user re-enrollment. This deliberately favors a bounded recovery path over adding an offline copy with a second high-value custody chain. A different backup decision would require a separately specified restore test and custodian.
