# Base storage and migration ownership proposal

Status: T006 proposal with owner-selected migration direction in [ADR 0009](adr/0009-migration-owner.md): Python core is the sole migration owner; migrations use versioned SQL files and a Python runner. On 2026-10-31 the owner selected Python core as the sole SQLite reader/writer-service host; TypeScript must access data only through the Python service and must not open the database or associated files directly. Separate OS service identities and ACLs must enforce this process boundary; fail closed if it cannot be demonstrated. This is design direction only and requires G-ARCH/G-CONTRACT/G-SECURITY approval and technical enforcement evidence. No third-party tool/library, schema, implementation or deployment is approved. ADR 0002 records the earlier limited approval of logical ownership and transaction principles; these selections do not expand that approval. Constitution baseline 2026-10-29 SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. The [constitution](../constitution.md), [architecture proposal](../architecture_proposal.md), [contracts proposal](contracts-proposal.md) and [threat model](threat-model.md) govern scope.

## Proposed logical ownership and record concepts

Python core is the sole logical migration owner. The selected direction is to keep migrations as versioned SQL files and use a Python runner; neither a third-party runner/library nor an in-repository implementation has been selected. On 2026-10-31, the owner selected Python core as the sole SQLite reader/writer-service host; TypeScript must access data only through a typed Python service interface and must not open SQLite, WAL or other associated files directly. Separate OS identities and ACLs must prevent TypeScript from accessing the database files or running migrations; if not demonstrable, fail closed. The Python service must enforce requester-scoped authorization and return only validated results, rather than expose arbitrary cross-domain SQL. Its read API, authenticated caller interface, transaction and audit semantics remain subject to G-ARCH/G-CONTRACT/G-SECURITY review. The table is a logical inventory, not approved SQL, a physical database layout, a field-level schema, or an implementation schema. Database/file layout, IDs, timestamp representation, constraints, indexes, deletion and retention remain subject to reviewed schemas and migrations.

**Owner-selected resolution to SQLite WAL access constraint (2026-10-31):** SQLite's official [WAL documentation](https://www.sqlite.org/wal.html#readonly) says a read-only WAL connection may require write permission to an existing `-shm` file, or to the containing directory if `-shm` is absent. URI [`mode=ro`](https://www.sqlite.org/uri.html) is not an OS permission boundary. To avoid granting TypeScript access to SQLite shared-memory coordination files, the owner selected routing all database reads through the Python service; TypeScript must not open the database or associated files. The service API, authorization, error/failure handling and tests remain unapproved and gated.

The accepted proposal scope is logical domain ownership, authorization, transaction intent, guest scope, and migration/recovery principles. The owner-selected migration and process-access directions above do not select transaction implementation or cross-store atomicity. Concrete schemas, migration ordering, compatibility and failure policy remain unresolved. Nothing below selects those mechanisms.

The logical change and mandatory security audit must be coordinated; whether a shared physical transaction is available is unresolved. Secret material and keys are not returned to models. |

Treat routine `last_activity` updates during successful `auth.resolve_session` calls as session metadata, not business-effect audit events. The owner selected lifecycle audit events for session creation/login, explicit logout and revocation, but not automatic expiry; include canonical lowercase hyphenated UUIDv4 `session_id` for correlation, never the cookie token. Evaluate a single SQLite transaction for the event and session transition when both records share the same database. On required audit failure, abort the transition and return `UNAVAILABLE`/503; a failed logout leaves the session unrevoked. Do not assume cross-database atomicity; require separately reviewed durable recovery if stores differ. Guest session duration is 24 hours. **Owner-selected T167 audit-data direction (2026-11-01):** business-effect audit events for idempotent operations do not include target/object IDs. This is scoped to those events and does not settle the general audit schema or the fields required for other domains.

**T029 authentication audit/storage transaction proposal (2026-11-01; not approved):** the owner selected a service-wide login admission limit before password verification, using a continuously refilled token bucket with bounded burst; numeric rate/burst remain open; after restart, initialize the bucket empty and refill continuously, accepting temporary login unavailability; when exhausted, reject generically without verifying a password, creating a session, incrementing per-account failure state or recording a failed-verification event. The owner selected HTTP 503/`UNAVAILABLE`, a generic error body and no `Retry-After`; numeric limits, reset behavior and exact body schema remain for synthetic-volume and G-SECURITY/G-CONTRACT review; do not depend on client IP/Origin. For a failed password verification on an existing account, commit the throttle-counter update in one SQLite transaction, then attempt the required security-audit append separately. This preserves the counter if the append fails while SQLite remains available; return `UNAVAILABLE`/503 and do not authenticate. If the counter transaction or shared database itself fails, return `UNAVAILABLE`/503 without claiming the attempt was counted. For a successful login outside a delay, evaluate one transaction containing session creation, counter reset and lifecycle audit append when co-located; abort all state changes on failure. For qualifying failed `auth.resolve_session` signals, evaluate temporary per-account failure timestamps plus the last-emitted signal marker, and append the signal in one transaction with the marker update. Expire timestamp entries outside the rolling 15-minute window. The owner selected fail-closed behavior if saturation prevents maintaining the active rolling count or persisting a qualifying signal: do not discard active timestamps; return `UNAVAILABLE`/503 with no context or idle update. Numeric bounds and capacity evidence remain open for synthetic-volume/ARM64 review. These directions require exact schemas, concurrency/locking, cleanup, crash-recovery and fail-closed tests under T029/G-CONTRACT/G-SECURITY/G-ARCH; do not implement a timestamp ledger until its safe numeric bounds are approved.

**T029 event protection/retention proposal (2026-11-01; not approved):** define a closed typed event envelope and event-specific allowlists in the contract; exclude free-form strings and arbitrary metadata. Restrict event insertion and normal reads to authorized core operations, with no model/skill read path and no direct TypeScript SQLite access. The owner selected evaluating the existing application `admin` role for a narrowly scoped read/export path with documented purpose, constrained time-range/type filters, redaction and an audit record for each query/export, authorized by the currently authenticated admin session without additional password/TOTP step-up. Revalidate session and admin authorization per request. The owner selected deriving row-count, byte-size and time-range bounds from synthetic-volume/performance testing; no numerical limits are selected and export is not implementable until caps are reviewed. Retention cleanup should be a core-owned operation keyed to event class and must not become a general application delete operation. Keep business-effect events at the selected one-year proposal, security-attempt/lifecycle events at the selected 90-day proposal and diagnostic logs at 30 days; all remain subject to operational/legal review. The broad role and lack of per-export step-up increase exposure if an admin session is compromised and require explicit G-SECURITY risk review; the gate may assess least-privilege alternatives. Exact OS ACLs, filter/export bounds, access-event fields, cleanup implementation, retention evidence and any legal-hold policy remain unresolved and require G-SECURITY/G-OPS/G-CONTRACT review.

**Owner-selected legal-hold scope direction (2026-11-01; not approved):** do not build a general legal-hold feature in the initial scope. This does not resolve whether a preservation duty applies; complete legal review before enabling retention purges. If a legal review finds a hold mechanism is required, pause the affected purge scope and obtain separate approval/design rather than silently deleting or bypassing the requirement.

Python core is the single migration authority even if separate stores are selected. For SQLite, the owner selected Python core as the sole reader/writer/migration service; TypeScript must use its authenticated typed interface and must not access the database or associated files directly. This does not select internal connection/worker concurrency or the physical store boundaries for other services. Two processes must not bypass owner-scoped repositories or independently run migrations. SQLite transactions do not by themselves provide atomicity across independent databases, processes, and files. Designs requiring cross-store effects must specify durable state, recovery and fail-closed behavior; no distributed atomicity is assumed. The selected store boundaries, writer/process ownership, transaction strategy and migration coordination must be reviewed before implementation.

## Memory, guests and secrets

Memory is a separate domain and is not included in the base logical inventory above. Its schema, indexes, embeddings, encryption and conversion are explicitly separate and subject to T058, G-CONTRACT and G-SECURITY; the plan's example SQL is not an approved migration. Only authorized users/admins may retrieve their permitted memory scopes, and guests have none. When user memory visibility is disabled the user can still delete all their own memories. A separate encryption boundary must include memory indexes and derived data or protect them equivalently. Missing required keys fail closed; no empty replacement database is silently created. This does not decide whether memory shares a process or physical SQLite file with another domain.

Guest temporary conversation context is separate from persistent conversation history and memory. It belongs to its guest session, expires after 24 hours and is deleted with that context; its physical store, process ownership and crash/restart cleanup mechanism remain to be designed and verified. Guests are not user accounts and have no persistent memory. Actual secret material, tokens and encryption keys must be held outside downloadable backups and logs, in a secret facility selected and approved through the applicable gates; credential-verifier and secret references are not permission to copy secrets into application records. Exact separation of verifiers from key material needs security review.

## Migrations and recovery

The owner-selected direction fixes Python core as sole migration owner, versioned SQL migration files as the format, and Python as the runner language. It does not select a third-party tool/library, a runner implementation, a versioning convention, a database layout, a migration execution process, or a transaction mechanism.

Remaining gates:

- **G-ARCH:** Decide whether to use any third-party migration tool/library or implement the Python runner in-repository; review any proposed package and its transitive dependencies, exact version, license and compatibility. The owner-selected Python-only SQLite access boundary does not settle physical store layout, access boundaries for any other stores, or internal connection/worker concurrency. The selected Python owner and runner language do not settle architecture or dependency choices.
- **G-CONTRACT:** Approve each concrete schema and SQL migration, including scope/ownership, constraints and retention; define migration identifiers and ordering, compatibility, clean-install/upgrade behavior and supported migration policy. Specify transaction/atomicity requirements, including cross-store effects, failure handling and recovery; this does not presume a particular transaction implementation.
- **G-SECURITY, as applicable:** Resolve credential-verifier separation and memory/key protection; these are not decided by the migration direction.

Before destructive or incompatible migrations, quiesce relevant writers through an approved coordination mechanism and create and verify a consistent recoverable backup of every affected store. Validate upgrades on a staged copy and user isolation before switching; report failures and keep or restore the previous usable state. A reverse migration must be explicitly verified; where safe reversal cannot be guaranteed, restore the compatible backup rather than pretending rollback is lossless. Coordinate scheduler, file staging, memory conversion and backup/restore/update to avoid simultaneous destructive maintenance. Restore secrets separately; missing required encryption keys make affected data unrecoverable.

## Decisions and test obligations

Owner review must resolve the G-ARCH and G-CONTRACT items above, plus verifier separation and audit atomicity across stores where applicable. Approving this document does not approve the memory schema or sandbox, update and encryption implementations. T023 and dependent tasks must test clean installation, ordered upgrades, failed migration and restart, consistent backup during writes, rollback/restore, owner isolation, guest expiry, foreign IDs, concurrent operations, missing keys, file-stage failures, and mandatory audit under failure. TM-02, TM-07, TM-11 and TM-12 in the threat model apply. No migrations, tests, dependencies or hardware checks have been performed for this proposal.
