The npm lockfile format can retain dependencies, optional dependencies, platform restrictions, integrity and license fields, according to [npm's lockfile reference](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/). The complete conditional dependency graph cannot be honestly inferred from a partial direct list. Resolution against registries and inspection of artifacts must account for untrusted metadata, build hooks, network access, and exact versions; no resolver has been run for this record.

## Review sequence and acceptance evidence

1. Identify a bounded first milestone and unresolved direct components, including Python runtime/build backend, TS test environment, security plugins, migration tooling and shadcn components. Separate production, development, build and OS/host scopes. Check whether each component is actually required before proposing it.
2. Collect and independently review exact candidate metadata and notices above. Record observation date and source; refresh mutable vulnerability and support information immediately before approval. For each artifact record version, URL, digest, provenance, architecture, license, dependency role, known advisories, disposition and missing evidence. Preserve evidence without secrets or personal data.
3. Present the exact proposed resolver environment, trust roots, network restrictions, cache, index, command and allowed metadata/build behavior. Resolution can execute build-backend code; no-build flags or offline mode alone are not an isolation boundary. Review the exact execution plan and obtain applicable G-ARCH/G-OPS authorization before running it. A draft graph is evidence for review, not permission to install its members.
4. Review every resolved transitive, optional, platform-specific, build and bundled dependency and its notices and advisories. If metadata is absent, a native ARM64 artifact is missing or a required scan cannot complete, mark the graph unresolved; do not silently omit it or treat an unavailable check as a pass. Review the exact graph and obtain scoped approval before installation.
5. After approved environment and artifacts exist, run clean reproducibility and negative tests with synthetic fixtures; prove hash mismatch and missing inputs fail, measure scanner coverage against approved graph, and test target-specific installs. Separate emulator functional evidence from real-Pi hardware acceptance. Review or approval of a direction, version list or artifact does not automatically authorize unrelated service configuration or deployment.
