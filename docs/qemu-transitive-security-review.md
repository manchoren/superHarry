## QEMU SSH and libssh2 source-path distinction

The tagged [QEMU v11.1.3 SSH block driver](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/block/ssh.c) includes `<libssh/libssh.h>` and `<libssh/sftp.h>` and calls `ssh_connect` and libssh SFTP functions. Its [block build definition](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/block/meson.build) selects the SSH driver through the `libssh` dependency. These files therefore establish that this particular upstream block driver uses **libssh**, not libssh2; prior references to an SSH block driver as a direct libssh2 path must not be interpreted as evidence of one. This distinction does not resolve the separate libssh advisories or prove the behavior of the MSYS2 binary.

The current [MSYS2 UCRT64 curl package](https://packages.msys2.org/packages/mingw-w64-ucrt-x86_64-curl) declares libssh2 as a package dependency. In tagged [QEMU v11.1.3 curl.c](https://raw.githubusercontent.com/qemu/qemu/v11.1.3/block/curl.c), the block driver configures both allowed initial and redirect protocols as HTTP, HTTPS, FTP and FTPS; SSH and SFTP are not in that source-level allowlist. This narrows one candidate route to the libssh2 SSH protocol when this exact QEMU driver and restriction are used; it is not proof that libssh2 cannot be loaded or reached by another QEMU component, a dependency, a modified package, an attacker-controlled host process, or an unexpected configuration. Local ARM64 guest image use is a proposed scenario, not an approved tested invocation or network boundary. A pre-authentication SSH advisory requires an actual relevant client connection and vulnerable parsing path, not merely the presence of a transitive package.

Before disposition, authenticate the exact QEMU, curl and libssh2 binaries and build provenance; inspect imports, enabled block modules, configuration and supported management interfaces; trace any additional libssh2 callers and test actual restrictions under the approved environment. Do not substitute libssh mitigations or findings for libssh2. The source inspection did not execute or install any package and does not close the advisory or license reviews.

## libssh advisory version and QEMU exposure review (2026-10-30)

The authenticated inventory records MSYS2 UCRT64 `libssh` `0.12.2-1`. The [current MSYS2 package page](https://packages.msys2.org/packages/mingw-w64-ucrt-x86_64-libssh) also reports that version, SHA-256 `1be494f5fad8bf1210a1eeaccdd07d3e8319f4d13cd79a9302ae196fcc96da8b`, and lists seven CVEs. The upstream libssh advisories for [59843](https://www.libssh.org/security/advisories/CVE-2026-59843.txt), [59844](https://www.libssh.org/security/advisories/CVE-2026-59844.txt), [59845](https://www.libssh.org/security/advisories/CVE-2026-59845.txt), [59846](https://www.libssh.org/security/advisories/CVE-2026-59846.txt), [59848](https://www.libssh.org/security/advisories/CVE-2026-59848.txt), and [59850](https://www.libssh.org/security/advisories/CVE-2026-59850.txt) state affected versions below 0.12.1 and identify 0.12.1 as a security release; [59851](https://www.libssh.org/security/advisories/CVE-2026-59851.txt) identifies 0.12.0. Thus, **the declared upstream version 0.12.2 is outside these seven stated upstream affected ranges**, despite the package page listing them. This is version-based screening, not binary validation: verify the exact signed source and binary, build provenance, upstream fixes, downstream patches and present advisory data before disposition. A package-page CVE listing should not be treated as proof of either exploitability or a fix.

The [current MSYS2 recipe](https://raw.githubusercontent.com/msys2/MINGW-packages/master/mingw-w64-libssh/PKGBUILD) declares 0.12.2, applies a pkg-config patch, and sets `WITH_GSSAPI=OFF`, but this mutable recipe alone does not prove how the recorded binary was built. The tagged QEMU SSH block driver uses libssh as an SFTP client, and some advisories specifically affect client SFTP or channel processing; disabling or avoiding a remote SSH image is therefore a relevant proposed exposure control, not an established mitigation for all uses. An approved local-only emulator design should reject remote image references and management requests that attach or reopen SSH-backed block devices, independently restrict outbound access at an approved OS boundary, avoid untrusted image backing chains, and test that these restrictions hold after startup and reconfiguration. Exact invocation, local image validation, management socket protection and network policy require G-OPS/G-SECURITY review. Do not infer that the SSH module is absent or that firewall rules already exist. No package was installed or executed and no binary or network test was performed.
