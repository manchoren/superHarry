# Draft browser CSRF and pre-authentication contract

Status: accepted in part by the project owner on 2026-10-30; see [ADR 0007](adr/0007-csrf-contract.md). No endpoint is implemented; database schemas and dependencies remain unapproved. Tasks T005, T007, T024, T026 and T035. Constitution baseline 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. [ADR 0006](adr/0006-security-directions.md) approves the session-bound synchronizer-token and origin-verification direction only. The owner accepted the concrete scope of this public contract as recorded in ADR 0007; it does not amend the partially accepted [chat contract](contracts-proposal.md). The constitution and existing accepted role, session, guest and recovery policies prevail.

## Proposed wire contract

- `GET /v1/session/csrf` returns `200` JSON `{ "csrf_token": "<base64url-token>" }` for the current valid browser session. The token is a cryptographically random 32-byte value encoded as 43 unpadded base64url characters. A session has one active token shared by its tabs. The server retains the token securely as session-associated data; no token appears in a URL, log, audit payload, cookie, model context or browser persistent storage. The response and errors use `Cache-Control: no-store`; do not cache or serve this endpoint from a service worker. Disable cross-origin reading through CORS; allow no credentialed wildcard origin.
- When no valid session exists, this endpoint proposes creating a short-lived anonymous **pre-authentication session** with no user or guest privileges, setting the owner-selected `__Host-superharry_preauth` cookie with `Secure; HttpOnly; SameSite=Strict; Path=/`, no `Domain`, over HTTPS, and issuing its token. This GET may allocate only bounded transient security state; it must not perform user-visible or privileged mutations. The owner selected a pre-auth quota keyed by Origin plus validated client IP, using a fixed reverse-proxy topology; do not enforce it until the configured-Origin allowlist, proxy addresses/hops and trusted client-IP derivation are approved, and never trust arbitrary forwarded-IP headers. Cap its storage independently from guest-session limits. Proposed lifetime: 10 minutes absolute, no idle extension; on expiry discard the session and token. Numeric quota and state retention remain open for G-SECURITY/G-CONTRACT review. A valid existing session is never replaced by this endpoint. Session IDs remain cryptographically random opaque 256-bit values, with server-side verification, per ADR 0004.
- Browser cookie-authenticated state-changing requests, including sign-in, guest creation, logout, session rotation and any approved browser recovery operation, include `X-CSRF-Token` containing the current token and an `Origin` header exactly matching one explicitly configured HTTPS origin. Reject missing, `null`, multiple, malformed or nonmatching Origin and missing, duplicate, malformed or nonmatching token before any business mutation; compare decoded bytes in constant time. Configured origins and trusted-proxy behavior are separate G-SECURITY/G-OPS decisions. Non-browser internal/channel authentication does not inherit a cookie exemption: each path needs its own explicitly approved authentication and contract and must not accept ambient browser cookies as authority.
- `GET`, `HEAD` and `OPTIONS` have no application-side effects. For the token endpoint, the bounded pre-session allocation above is the sole proposed security-state exception. SSE and read-only requests use existing authorization and do not themselves extend account inactivity, as specified in ADR 0004; they do not carry a CSRF token in a URL. All requests still require their operation-specific authorization and ownership checks.
- Failed validation proposes HTTP `403` using the existing structured error envelope: `{ "code": "FORBIDDEN", "parameters": {}, "request_id": "..." }`. Do not expose which check failed or return localized prose. Expired sessions on protected routes use the existing `UNAUTHENTICATED` response; valid-token authorization failures remain independently enforced. The owner selected HTTP 429 `RATE_LIMITED` without `Retry-After` when the Origin-plus-validated-IP pre-auth session quota is exhausted, using the standard error envelope with empty `parameters` and `request_id`, without cap, expiry or quota-key details; enforcement remains blocked on the trust boundaries. Other rate limiting uses `RATE_LIMITED`, and missing session storage or random-number generation returns `UNAVAILABLE`; no failure creates a usable partially initialized session. Exact endpoint and response values require G-CONTRACT approval.

## Transitions and concurrent tabs

1. An unauthenticated page fetches the token endpoint over trusted HTTPS, then performs a validated login or guest-creation request with the `__Host-superharry_preauth` cookie and token. Repeated token fetches in a still-valid session return the same token; they do not rotate it or extend the pre-session lifetime.
2. Upon successful authentication or guest creation, atomically invalidate the pre-session and its token, create a fresh session identifier and independent token bound to the resulting session, and set the owner-selected `__Host-superharry_session` cookie with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` and no `Domain`, over HTTPS. Clear the pre-auth cookie using its same name and `Path=/`, without a `Domain` attribute. Do not elevate or reuse the pre-session. The client fetches the token again before its next mutation. If valid account credentials are verified but the account's active-session quota is reached, do not create a session or evict an existing session; return the same external response as a failed login without quota-specific details, do not count it as a failed credential attempt, and emit an individual security-audit event limited to authenticated `principal_id`, fixed event type/outcome, timestamp and `request_id` without IP, Origin, credentials, token or cap details. Retain this event for 90 days subject to legal/operational review. If the event cannot be persisted, return `UNAVAILABLE`/503. The numeric quota, event schema and failure/transaction behavior remain subject to capacity evidence, T029 and G-SECURITY/G-CONTRACT review. Failed login does not grant privileges; existing rate limits and generic responses apply.
3. Upon logout, revoke the account or guest session and token; clear `__Host-superharry_session` using the same `Path=/` and no `Domain` attributes. On a successful role/privilege change, rotate the session and token consistently with the accepted session policy. An expired, revoked or rotated session never permits a stale request. Initial sign-in, MFA completion, and any later privilege transition must explicitly define the atomic boundary; MFA-pending state and its permissions remain separate security decisions.
4. Tabs sharing one cookie share the token. A stale in-memory token after another tab rotates the session receives `403` and must fetch the current token before an explicit new action. A request rejected by CSRF validation has no business side effect; the UI must not blindly retry ambiguous failures or replay consequential actions. Tabs may independently refresh on a security-state change without exposing tokens across origins. In-flight requests are authorized at their server-side decision boundary; invalidation and mutations require synchronization to prevent stale privilege use.
5. Session storage failure, restart and key loss must never resurrect or silently elevate a pre-session. The exact persistence/restart design, session database schema, token storage representation, maximum outstanding pre-sessions and cleanup are undecided. Guest expiry remains 24 hours and guest role restrictions remain unchanged; pre-authentication state does not create a guest or count as guest access.

## Security assumptions and limits

The server validates its configured target origin independently of attacker-controlled forwarded headers; its proxy authentication and LAN/Tailscale origin list are not approved by this proposal. HTTPS certificate trust is a deployment prerequisite. Session-bound tokens, Origin checking and SameSite cookies do not prevent same-origin script injection: enforce the separately approved CSP, safe rendering and XSS controls. Password-reset and MFA-recovery actions remain unavailable until their exact authenticated paths and contracts are approved; the accepted OS-admin recovery directions are not changed here. Issuing a pre-session can be abused for resource exhaustion; it must be bounded and tested without creating a bypass to guest quotas. Audit authentication and privileged attempts without credentials or tokens; the exact handling of audit storage failure follows the approved security policy.

OWASP documents the [synchronizer-token pattern and origin checks](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). The [Origin header reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin) documents that the header can be `null` and varies by request context; the proposed fail-closed rule therefore needs compatibility testing on supported browsers and recovery flows. The existing proposed interface uses [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0.html); this prose is a review proposal, not a complete OpenAPI document.

## Required negative and lifecycle tests

- Cross-origin form/fetch, omitted/null/duplicate/spoofed Origin, malformed/missing/duplicate/mismatched token, token from another session, login CSRF and guest-creation CSRF all fail without mutation; no token is exposed by CORS, URL, logs or cache.
- Pre-session expiry, simultaneous creation, quota exhaustion, session-store outage and restart fail safely; attacker-generated pre-sessions do not acquire guest privileges or reset guest creation limits.
- Login, MFA and guest transitions rotate session and token atomically; test failure between persistence and cookie response, fixation, old-token replay, logout and role-change races. No revoked session can mutate data, even during concurrent work.
- Multiple tabs use the shared token; after rotation stale mutations fail, token refresh restores intentional actions and no automatic replay occurs. Test refresh racing with logout, expiry and two successful login attempts.
- Authorized same-origin chat creation and cancellation pass with correct headers; unauthorized owners and guests remain denied where applicable. SSE reconnect works under its separate owner checks without the token in its URL or extending inactivity.
- Supported browser and LAN/VPN combinations send the expected Origin; missing Origin fails predictably rather than weakening the check. Verify proxy misconfiguration, IPv6, cross-origin preflight and cache behavior. Tests use synthetic data; no runtime, security or hardware test has been performed.

## Owner-selected alternative for further review (not an ADR 0007 amendment)

The owner selected a Django topology direction for design work: replace the separate `__Host-superharry_preauth` and authenticated-session cookies with a single `__Host-superharry_session` cookie that identifies an anonymous, privilege-free Django session before login and a new authenticated session afterward. At login, explicitly flush the anonymous session so its state cannot be elevated or reused; then create/rotate the authenticated session key and rotate CSRF state. Candidate CSRF storage is Django's session-backed mode, not the current separately defined synchronizer-token format. A mandatory exact configured HTTPS Origin guard must reject missing, `null`, duplicate, malformed and nonmatching Origin values before mutation; Django's default HTTPS Referer fallback is not sufficient for that requirement. The secure cookie remains host-only, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, without `Domain`.

This direction replaces accepted details above and in ADR 0007 only if a revised contract is separately reviewed and approved. The owner selected the topology for proposal development, not the cookie/CSRF schema, implementation or gates. Verify anonymous-session expiry versus the selected authenticated 60-minute idle/24-hour absolute expiry, session/audit transactionality, strict-Origin middleware, lost-response relogin behavior and all old-token/fixation cases before adoption. Until then, the currently accepted ADR 0007 contract remains the approval baseline.

## Review gates

Owner review must decide the token endpoint and encoding, pre-session duration and quota, token exposure and error semantics, MFA transition and multi-tab behavior, plus exact origin policy. Public interface and any schema changes require G-CONTRACT; session/token and authentication mechanics require G-SECURITY; proxy, HTTPS and deployment require G-OPS; package and tool choices require G-ARCH. Record approval scope and document hash in an ADR before implementation. T003, T014 and the backlog prerequisites still apply; no test result, deployment or implementation is claimed.
