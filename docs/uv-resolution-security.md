# uv dependency resolution: security review

Status: research for T003/T014, 2026-10-30; no resolver, dependency, version, lockfile, command, isolation mechanism or installation is approved. The owner requested investigation of uv rather than selection. Constitution baseline 2026-10-29, SHA-256 `426923873e828b7a0e8fd63b88a5a9b5e01b35f9c2e3bb965c322931d1d9835a`. This concerns trusted repository development, not the separate runtime package guard or sandbox authorization.

## Documented behavior and implications

- uv resolves package metadata; if metadata is unavailable for a source distribution, it may build the package to obtain it, potentially invoking a build backend. A resolution-only operation is consequently not necessarily code-free. Providing explicit dependency metadata can avoid a build in specific cases, but uv cannot verify such overrides; incorrect metadata can hide transitive dependencies. Sources: [uv resolution](https://docs.astral.sh/uv/concepts/resolution/) and [build troubleshooting](https://docs.astral.sh/uv/reference/troubleshooting/build-failures/).
- `--no-build` blocks operations that require building source distributions, but uv may reuse previously built cached wheels, and first-party or editable requirements may still invoke arbitrary build-backend code. It is not a sandbox or a complete no-execution guarantee. `--no-cache` uses a temporary cache rather than an existing one; this does not itself verify provenance or provide OS isolation. Verify each option for the exact pinned uv release and command. Source: [uv command reference](https://docs.astral.sh/uv/reference/cli/).
- uv documents automatic locking and syncing for `uv run`; commands such as `uv tree` may update locks automatically. `--locked` errors when the lock is inconsistent with project metadata, whereas `--frozen` skips that freshness check. `--no-sync` avoids synchronization but does not by itself prohibit relocking. These flags are not approval or malware scanners. Source: [locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/).
- By default, uv stops at the first configured index containing a package name, reducing dependency-confusion risk relative to unsafe multi-index search. `--no-index` does not prohibit direct URLs or `--find-links`; `--offline` restricts uv to cached/local data but does not prove other processes or executed build backends cannot access the network. Automatic Python downloads can be disabled; verify configuration precedence and the selected executable for the pinned version. Source: [uv command reference](https://docs.astral.sh/uv/reference/cli/).
- uv's universal resolution may include alternative package versions and artifacts for different platforms and Python versions. Its existence does not establish that the selected Debian ARM64/Python combination has compatible, reviewed wheels or that all other lock branches are safe. A previously reviewed lock can remain up to date despite newly released packages or advisories. Sources: [resolution](https://docs.astral.sh/uv/concepts/resolution/) and [locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/).

## Proposed review controls, not approved

1. Select and obtain explicit G-ARCH approval of exact uv, Python, packages and versions, trusted sources, licenses and a process for the transitive graph before installation. Independently verify the uv artifact provenance, integrity and advisories; do not infer package safety from hashes or a valid signature alone.
2. Develop a separate, reproducible resolver environment with no production secrets, host credentials, application data or persistent shared cache. Restrict network egress using independently enforced OS/network controls to reviewed sources; do not claim uv build isolation is a security sandbox. Select and approve the environment and privileges under applicable G-OPS/G-ARCH gates. No change to the runtime sandbox policy is implied.
3. Review project metadata, index configuration, environment variables, direct URLs, editable/local/VCS sources, overrides and workspace configuration before resolution. Initially propose third-party wheels only, with source builds, metadata overrides and new indexes blocked pending individual review. Use an empty, isolated cache and validate artifact origin and digest. A no-build flag alone does not ensure no code runs; avoid trusting unreviewed first-party or editable build backends.
4. In a separately authorized execution, create a draft graph, inspect every direct and transitive dependency and platform marker, review package names, versions, licenses, provenance, advisories and artifacts, and explicitly verify the Linux ARM64 wheel and Python ABI. If metadata, artifact identity, required security evidence or ARM64 compatibility is missing, stop; do not silently build from source or omit the package. The precise command sequence, target markers, scanner and failure policy remain decisions requiring approval and version-specific testing.
5. After approval of the exact graph, verify lock freshness and required artifact hashes in a clean ARM64 environment and test rejected altered artifacts, absent metadata, incompatible wheels and unavailable sources. Validate the candidate SBOM/auditing tool against the selected graph, including conditional branches. Define a reviewed update process; a lock is not proof that packages are safe or current.
