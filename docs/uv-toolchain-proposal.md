## Exact candidate and provenance

Propose uv **0.13.6** for review, not installation. The [official upstream release](https://github.com/astral-sh/uv/releases/tag/0.13.6) identifies the release and provides published checksums and GitHub artifact attestations. The Linux ARM64 GNU archive `uv-aarch64-unknown-linux-gnu.tar.gz` has published SHA-256 `229e194255c7958d86d56e8790d969a6f74736592133f0dfd0076f754c642c1d`. The archive has not been downloaded, independently hashed, attestation-verified, executed or tested on the target. Confirm these records at approval and acquisition time, the guest architecture and glibc compatibility. A Windows executable is not required by this proposal; approve a separate exact artifact if host execution becomes necessary.

The [upstream PyPI project](https://pypi.org/project/uv/) identifies dual MIT/Apache-2.0 licensing for uv. Review the exact tagged release and third-party bundled notices and redistribution obligations separately; this is not a completed license audit. Review release security advisories, supported versions and vulnerability reports, not just published checksums. An attestation links an artifact to provenance claims but does not prove safety. Do not pipe remote installer scripts into a shell; propose obtaining a versioned artifact and verifying its independently obtained checksum and provenance before any execution.

## Proposed gated workflow

1. **Prepare review:** inventory the selected OS/guest, exact Python interpreter, build backend, uv artifact and proposed direct packages. Specify a read-only source and configuration review, disable inherited credentials and automatic interpreter acquisition, define an empty isolated cache and restrict egress to approved indexes at an independently enforced OS boundary. Identify direct URL, VCS, editable and metadata-override inputs; block them until individually reviewed. Approve exact toolchain and resolver environment under G-ARCH/G-OPS before use. Real credentials and application data must not be present.
2. **Resolve for review only, after that authorization:** in an isolated disposable environment using the exact approved release and interpreter, run a separately reviewed version-specific lock command against reviewed project metadata and sources. Capture the draft lock and resolver logs without secrets. A resolver can invoke untrusted build backends to obtain metadata: only pre-reviewed wheels/metadata are allowed initially; if source metadata or a build is required, stop and seek separate review. `--no-build` and uv cache settings alone do not guarantee that no build occurs. No project installation or authoritative lock is authorized by this draft.
3. **Review every graph branch:** enumerate direct and transitive packages, markers, exact sources, versions, license notices, advisories, wheel filenames and digests. Independently verify that Linux ARM64 wheels match the selected interpreter ABI and OS; universal lock resolution itself does not establish that. Review development and production groups separately and confirm SBOM and vulnerability scan coverage. Missing required evidence blocks acceptance. Review lock ownership and changes, and approve the exact package inventory under G-ARCH before installation.
4. **Reproduce only after graph and environment approval:** verify artifacts against the approved digest and provenance, reproduce the approved lock on a clean ARM64 emulator with an empty cache and synthetic data, fail on inconsistent project metadata and unreviewed lock changes. Use `--locked` rather than assuming `--frozen` checks freshness; verify exact release-specific command behavior and ensure commands do not implicitly synchronize before permission. Demonstrate altered/missing artifacts, missing indexes, unsupported ARM64 wheels and omitted scan coverage fail closed. Label emulator findings separately from Pi performance and hardware acceptance.
5. **Maintenance:** define a single lockfile owner, reviewed upgrades and recurring advisory/license scans; changes in packages, versions, artifacts, build backend, indexes or checks follow applicable approval rules. Runtime-agent package installation remains governed by its distinct package guard and sandbox policy.

## Decisions and validation still required

Choose the approved guest image and interpreter, exact uv version and artifact, acquisition/provenance verification method, security advisory criteria, resolver isolation and network policy, index and certificate trust, package and build-backend inventory, wheel-only exceptions, approved scanners and SBOM validation, and concrete reviewed commands. `uv.lock` may cover multiple conditional environments; scope review to every supported branch, not only the developer host. Approval of the design direction does not approve any of these choices. No dependency graph was generated and no implementation, scanner result, ARM64 execution or hardware validation is claimed.
