For each exact direct, transitive, optional, bundled, native and build input, the conformance record must establish:

- necessity for an accepted T042 prerequisite and compatibility with the approved security, contract and storage decisions; no T057 or unrelated later-feature scope;
- exact identity, version, artifact digest and authenticated provenance/trust, supported Linux ARM64 target/ABI artifact, with no unreviewed source-build or substitution path;

- version-specific license texts, bundled-component attribution and required distribution notices/source obligations; a metadata SPDX label or path-name match alone is insufficient;
- complete, current advisory coverage for the exact artifact and applicable configuration, using an approved source/cache integrity procedure within the owner's 24-hour maximum; findings must have evidence-based dispositions, and incomplete scans block;
- exact approved local-check tools and commands, their coverage and fail-closed behavior, plus applicable G-ARCH and separate G-OPS/G-SECURITY/G-CONTRACT approvals before any installation or execution.

Until every applicable condition is evidenced and the exact scope is approved, do not recommend or characterize a candidate set as compliant. ## Python SBOM from `uv.lock`: unresolved coverage checks (2026-10-31)

A complete SBOM has not been demonstrated. The approaches below are documented research leads, not acceptable or recommended solutions: none has been shown to satisfy all graph, marker, group, build-dependency, provenance, notice and target-coverage constraints. No tool execution or technique selection is approved. These links must be checked against the exact release before any later assessment.

1. **Direct uv export.** The current [uv export reference](https://docs.astral.sh/uv/reference/cli/#uv-export) documents direct CycloneDX 1.5 JSON output and options for extras, dependency groups and workspace members. It says export normally relocks unless `--locked` or `--frozen` is used. Neither option by itself establishes isolation, graph completeness or policy compliance. Exact `uv` 0.13.6 support and flag semantics, group/extra conflicts, workspace scope and behavior in a restricted environment remain unverified. No fixture result demonstrates complete production/development, marker, build-dependency and platform coverage.
2. **Requirements export followed by CycloneDX Python.** The [uv reference](https://docs.astral.sh/uv/concepts/projects/export/) documents export to `requirements.txt`; [CycloneDX Python](https://pypi.org/project/cyclonedx-bom/7.6.0/) accepts requirements but explicitly does not support `uv.lock` directly. Documentation does not establish preservation of all branches, edges, markers, groups or artifact hashes. There is no passing fixture evidence; information loss is a blocker, not an accepted limitation.
3. **Trivy lockfile inventory.** [Trivy's Python coverage reference](https://trivy.dev/docs/latest/guide/coverage/language/python/) documents transitive dependencies for `uv.lock`, excludes development dependencies by default, and explicitly says license detection for uv lockfiles is unsupported. Marker-specific, optional, build-dependency and exact Trivy 0.76.1 coverage remain unverified. [Trivy's SBOM documentation](https://trivy.dev/docs/dev/docs/target/sbom/) warns that SBOMs from other producers may have inaccurate detections because Trivy uses custom properties. It cannot replace direct graph reconciliation or license evidence.

**Disposition:** none of these methods is currently recommended or cleared for use. A method can be considered only after exact tool artifact/provenance and version are reviewed and controlled fixtures demonstrate complete identities, edges, markers/groups, optional and build dependencies for every required target, with independently reconciled license notices and advisory coverage. A failed or untested case blocks the method; do not combine partial tools and call the result complete.
