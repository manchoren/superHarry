## Emulation design

Propose a dedicated ARM64 Linux virtual machine on the development host using QEMU system emulation. Prefer a pinned Debian 13 ARM64 base with documented differences from the target Raspberry Pi OS Desktop if the target image cannot boot suitably under QEMU; verify the QEMU machine, firmware, display, networking and CPU configuration experimentally after G-OPS approval. Record image digest, configuration, host version, package snapshot and bootstrap steps in version-controlled instructions. Reset from a clean snapshot to demonstrate repeatability. Isolate development credentials and use synthetic fixtures. Emulation validates functional ARM64 behavior only, not Pi timing, GPU, HDMI, thermal behavior or sandbox equivalence.

Feasibility evidence: [QEMU's Arm documentation](https://www.qemu.org/docs/master/system/target-arm.html) identifies `qemu-system-aarch64` and the generic `virt` machine for 64-bit Linux; its [virt reference](https://www.qemu.org/docs/master/system/arm/virt.html) requires an explicitly selected 64-bit CPU and notes that graphics requires an explicitly selected display device and guest driver support. The official [system emulation introduction](https://www.qemu.org/docs/master/system/introduction.html) shows TCG, firmware and storage in an AArch64 example. This supports the proposed approach but does not prove a particular image boots on this Windows host. Candidate QEMU upstream 11.1.3 is listed at the [official download page](https://www.qemu.org/download/); the page identifies source releases, not an approved verified Windows binary. Firmware provenance, host binary, checksums, image boot and licensing remain to be verified before setup. Debian's `qemu-system-arm` package `1:10.0.13+ds-0+deb13u1` is a different Linux-host option, not evidence of a Windows installer.

## Windows alternative: WSL 2 host with Debian QEMU (research only, 2026-10-30)

A concrete alternative is a dedicated Debian x86-64 WSL 2 distribution running Debian's `qemu-system-aarch64` with TCG and a separate Debian ARM64 guest. This keeps the Windows host while using Debian's published source-package security tracker; it does not establish stronger security than MSYS2. On this workstation, read-only `wsl.exe --status` reported default version 2 and `wsl.exe --list --quiet` listed only `docker-desktop`. Do not modify or repurpose Docker's distribution. No dedicated Debian WSL distribution was present in that output; availability, host privileges, storage and performance remain to be verified. Microsoft documents [WSL installation](https://learn.microsoft.com/en-us/windows/wsl/install), its [virtualization requirements](https://learn.microsoft.com/en-us/windows/wsl/faq), and [systemd support](https://learn.microsoft.com/en-us/windows/wsl/systemd). Enabling optional features, installing or updating WSL, creating a distribution, and changing global WSL settings require applicable G-ARCH/G-OPS approval; these may require administrator privileges and a reboot.

Debian currently lists AMD64 [`qemu-system-arm` 1:10.0.13+ds-0+deb13u1](https://packages.debian.org/trixie/amd64/qemu-system-arm), which provides `qemu-system-aarch64`, and [`qemu-efi-aarch64` 2025.02-8+deb13u1](https://packages.debian.org/trixie/qemu-efi-aarch64). QEMU's [ARM virt documentation](https://www.qemu.org/docs/master/system/arm/virt.html) makes clear that `virt` is generic hardware, not a Pi.
