## Emulation design

Use a dedicated, minimal Debian 13 ARM64 guest on the Windows development host with the selected MSYS2 UCRT64 QEMU direction. The owner selected Debian 13 ARM64 in QEMU's generic `virt` machine, without a desktop environment; use a serial console in the proposed headless profile. `debian-13.7.0-arm64-netinst.iso` remains an image candidate until its exact artifact and signed checksum chain are authenticated and pinned. This is a generic ARM64 Linux guest, not Raspberry Pi OS Desktop or Pi hardware; document the differences and verify target-OS package/service parity separately. The owner also selected an offline guest network policy: no virtual NIC, inbound connection, NAT or port forwarding. Required base/toolchain/application artifacts are to be prepared outside the guest and transferred on a read-only ISO with a manifest that records source identity, hashes and signature-verification results; do not treat the guest as trusted merely because a staging ISO is read-only. The exact offline repository/index format and package set remain open. The owner selected a design resource profile of 4 vCPUs, 4 GiB RAM and a 32 GiB QCOW2 disk; check host capacity before provisioning. Before provisioning, specify the exact QEMU machine version, supported 64-bit CPU, firmware/code and NVRAM handling, storage and staging-media devices, and reset/rollback procedure. The design default is no host-shared directories and no graphical device; any change must be reviewed against the device/advisory assessment. Record the authenticated image digest, configuration, host build, repository snapshot and bootstrap steps in version-controlled instructions. Use a disposable guest, synthetic fixtures and isolated development credentials. Emulation validates functional ARM64 behavior only, not Pi timing, GPU, HDMI, thermal behavior or sandbox equivalence. Provisioning and any repeatability boot test are T018/T021 work behind G-OPS, not prerequisites to mark the design proposal itself complete.

Feasibility evidence: [QEMU's Arm documentation](https://www.qemu.org/docs/master/system/target-arm.html) identifies `qemu-system-aarch64` and the generic `virt` machine for 64-bit Linux; its [virt reference](https://www.qemu.org/docs/master/system/arm/virt.html) requires an explicitly selected 64-bit CPU and notes that graphics requires an explicitly selected display device and guest driver support. The official [system emulation introduction](https://www.qemu.org/docs/master/system/introduction.html) shows TCG, firmware and storage in an AArch64 example. This supports the proposed approach but does not prove a particular image boots on this Windows host. The owner selected the MSYS2 UCRT64 QEMU `11.1.3-1` candidate as the current route; its package provenance, dependency and license closure, firmware, trust, image boot and servicing remain to be verified. Debian's `qemu-system-arm` package `1:10.0.13+ds-0+deb13u1` remains a separate WSL/Linux-host research option, not an approved fallback.
